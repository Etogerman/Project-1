# ТЗ: Новая карточка контакта

## Цель шага

Перевести карточку контакта из modal-only сценария в отдельную page-level страницу `ViewContact` с layout по мотивам Битрикс24.

Итоговый экран должен дать оператору:
- отдельную страницу контакта вместо модального окна
- понятную шапку контакта
- вкладки `Общее`, `Диалоги`, `Битрикс24`, `История`
- рабочую двухколоночную вкладку `Общее`
- полноширинные вкладки `Диалоги`, `Битрикс24` и `История`

Дополнительно для администратора экран даёт отдельную техническую вкладку `Диагностика`.

При этом доменный принцип сохраняется:
- `Contact` остаётся обзорной карточкой клиента
- `Dialog` остаётся основным рабочим местом оператора для переписки

## Границы

### Что меняется

- основной путь открытия контакта переводится на page-level страницу
- карточка получает новую шапку, вкладки и layout
- вкладка `Общее` собирает рабочие блоки контакта и операторские non-bitrix поля `Contact`
- вкладка `Диалоги` показывает диалоги контакта по каналам связи
- вкладка `Битрикс24` показывает CRM-данные контакта
- вкладка `История` показывает timeline событий контакта
- вкладка `Диагностика` показывает технические webhook/runtime данные контакта

### Что сохраняется

- бизнес-логика `Contact`, `Dialog`, collector, dedup и Bitrix24 sync
- dialog page как рабочее место оператора
- существующие operator/admin права доступа
- текущая доменная модель на этапах 1 и 2

### Следующие темы оформляются отдельными этапами

- комментарии оператора в ленте
- полная история изменений полей в формате `old -> new`
- reply composer внутри карточки контакта
- перенос полного чата в карточку контакта
- расширение `Истории` за пределы `История v1`
- новые Bitrix24 сценарии вне текущего подтверждённого happy-path

## Текущее состояние

- карточка контакта открывается как отдельная page-level страница `ViewContact`
- основной operator entrypoint идёт через page-level карточку, а старый modal-path остаётся только как hidden fallback
- для оператора страница содержит вкладки `Общее`, `Диалоги`, `Битрикс24`, `История`
- для администратора дополнительно показывается вкладка `Диагностика`
- вкладка `Общее` собрана как двухколоночный экран
- вкладка `История` уже реализована как read-only lifecycle timeline `История v1`
- вкладка `Диагностика` уже реализована как отдельная admin-only техническая вкладка

## Шапка страницы

### Состав шапки

Шапка содержит:
- кнопку `Назад к контактам`
- главный заголовок карточки
- кнопку `Редактировать`

### Правило формирования заголовка

Главный заголовок строится из полей контакта по правилу:
- основа: `last_name` + `first_name`
- порядок: `Фамилия Имя`
- если заполнено только одно из полей, показывается оно
- если оба поля пустые, используется fallback `Имя (мессенджер)`

### Роль шапки

Шапка решает две задачи:
- навигация
- быстрое открытие редактирования профиля

Технические подписи полей в операторском интерфейсе не показываются. Если они понадобятся для отладки, это оформляется отдельным dev/debug-режимом и не входит в базовый UI-контракт.

## Вкладка `Общее`

Вкладка `Общее` является основным экраном карточки контакта.

### Правило состава вкладки

Вкладка `Общее` объединяет операторские прямые поля `Contact`, кроме `bitrix24_*` и технических dedup/runtime-полей.

Во вкладке одновременно присутствуют:
- поля, которые уже были видны в карточке
- поля, которые раньше были скрыты или находились в служебных блоках
- связанные рабочие блоки `Телефоны` и `Теги`

Итоговое правило:
- операторские non-bitrix поля `Contact` находятся на вкладке `Общее`
- технические dedup/runtime поля не возвращаются в `Общее` и живут во вкладке `Диагностика`
- поля вкладки `Общее` доступны оператору сразу в составе открытых секций

### Левая колонка

Левая колонка содержит секции:
1. `Данные клиента`
2. `Работа с контактом`

### Правая колонка

Правая колонка содержит секции:
1. `Локация`
2. `Анкета`

### Секция `Данные клиента`

Секция показывает:
- `Имя (мессенджер)`
- имя
- фамилию
- пол
- возраст
- возраст из БД
- возрастной диапазон
- дату рождения

Поля секции:

- `first_name`
- `last_name`
- `gender`
- `effective_age_years`
- `age_years`
- `age_range`

Секция показывает и управляет:

- внутренним ID
- датой создания
- датой последнего обновления
- тегами контакта
- телефонами контакта
- удалением контакта

Поля секции:

- `is_auto_reply_enabled`

- `created_at`

### Секция `Локация`

Секция показывает:

### Секция `Анкета`

Секция показывает:
- статус анкеты
- текущий шаг
- последний заданный шаг
- дату старта анкеты
- дату старта текущего шага

Поля секции:

### Правило по дедупликации

Отдельной секции `Дедупликация` на вкладке `Общее` нет.

Если контакт объединён:
- над формой показывается только минимальный indicator
- indicator ведёт на основной контакт

Поля дедупликации остаются в модели `Contact` и в спецификации полей, но не отображаются отдельным UI-блоком на вкладке `Общее`.

## Вкладка `Диалоги`

Вкладка `Диалоги` показывает карточки диалогов контакта по каналам связи.

### Правило группировки

- одна карточка = один `Dialog`
- так как `Dialog` уникален на пару `[contact_id, channel_id]`, в норме это означает одну карточку на канал

### Состав карточки диалога

Карточка диалога показывает:
- платформу и/или канал
- имя канала
- route context или внешний chat id, если это полезно
- preview последнего сообщения
- `last_message_at`
- `last_inbound_at`
- `last_outbound_at`

### Действие карточки

- `Открыть диалог`

### Empty state

Если у контакта нет диалогов, вкладка показывает пустое состояние.

## Вкладка `Битрикс24`

Вкладка `Битрикс24` показывает CRM-данные контакта.

### Состав вкладки

Вкладка содержит:
- краткий статус Bitrix24 по контакту
- все прямые поля `Contact`, начинающиеся с `bitrix24_`

### Секции вкладки

1. `Контакт в Битрикс24`
2. `Сделка в Битрикс24`
3. `История в Битрикс24`

Все секции открыты по умолчанию.

## Вкладка `История`

Вкладка `История` показывает timeline истории событий контакта.

### Роль вкладки

Вкладка даёт оператору последовательность значимых событий по контакту.

На первом этапе эта вкладка показывает историю событий контакта, а не полный audit всех изменений полей.

### Состав timeline на этапе 2

Timeline включает high-signal события состояния контакта:
- создание контакта
- появление нового диалога у контакта
- старт анкеты
- завершение анкеты
- merge / склейка контакта

### Правило по сообщениям

Timeline включает только события состояния контакта; сообщения остаются в dialog page.

### Событие `Появился диалог у контакта`

Это отдельный тип события timeline.

Он используется в двух сценариях:
- создан новый `Dialog`
- после объединения контактов у root-контакта стал доступен дополнительный диалог

Для этапа 2 действует честный контракт:
- обычное появление диалога строится из существующего источника `dialogs.created_at`
- merge отображается отдельным событием `Контакт объединён`

### Пагинация timeline

- первая порция: 20 последних событий
- следующая порция: ещё 20 событий
- порядок: обратный хронологический
- способ загрузки: кнопка `Показать ещё`

## Вкладка `Диагностика`

Вкладка `Диагностика` показывает технические webhook/runtime данные контакта и не засоряет `Общее`.

### Роль вкладки

Вкладка нужна для технического разбора маршрутизации, inbound payload и dedup-состояния контакта.

### Права доступа

- вкладка доступна только администраторам
- обычный оператор вкладку не видит и не может открыть её query-параметром

### Layout

- вкладка `Диагностика` использует полноширинный layout
- вкладка только read-only

### Блоки вкладки

1. `Последний inbound webhook`
2. `Route context`
3. `Identity`
4. `Дедупликация`

### Границы вкладки

- `ChannelActivityLog` не входит
- полная история всех payload не входит
- редактирование технических данных не входит

## Этап 3: Комментарии и расширенные системные события

### Цель этапа

Добавить write-модель для пользовательских и системных событий timeline.

Новая локальная write-модель хранит события в append-only таблице `contact_timeline_events`.

Минимальный состав записи:
- `id`
- `contact_id`
- `event_type`
- `actor_user_id` nullable
- `body` nullable
- `payload` jsonb nullable
- `occurred_at`
- `created_at`

### Scope этапа 3 v1

В `Историю` добавляется только 1 новый тип события:

### Правила по типам событий

### Out of scope этапа 3 v1

- `questionnaire_resumed`
- история изменений профиля `old -> new`
- phone CRUD события
- tag change события
- включение и выключение автоответов

- удаление контакта

### Render-контракт этапа 3 v1

- комментарий: автор, время, текст

- запись комментария может стартовать из page-level карточки

### Темы этапа

- новое хранилище timeline events
- комментарии оператора
- смешивание comment events с уже существующим `История v1`

### Следующий mini-step после этапа 3 v1

- `ownership_changed`
- `questionnaire_resumed`
- другие system events поверх уже введённой timeline write-модели

### Implementation slice: mini-step после этапа 3 v1 (`ownership_changed` + `questionnaire_resumed`)

#### Цель

- расширить вкладку `История` двумя системными событиями поверх уже существующей timeline write-модели:
  - `ownership_changed`
  - `questionnaire_resumed`

#### Scope

- новые event types в `ContactTimelineEvent`
- запись `ownership_changed` из action/service-слоя:
  - `ClaimContactAction`
  - `ReleaseContactAssignmentAction`
  - `SetContactAssigneeAction`
- запись `questionnaire_resumed` из `ResumeContactDataCollectionAction`
- builder `Истории` начинает рендерить:
  - lifecycle events
  - `operator_comment`
  - новые system events

#### Out of scope

- новая таблица или новая миграция
- edit/delete timeline events
- phone/tag/auto-reply события
- profile field history `old -> new`
- Bitrix24 sync/history события
- новые UI entrypoints
- изменение текущего permission contract

#### Data contract

##### `ownership_changed`

- `event_type = ownership_changed`
- `actor_user_id` = сотрудник, выполнивший действие
- `payload = { from_user_id: ?int, to_user_id: ?int }`
- `body = null`
- событие не создаётся, если `from_user_id === to_user_id`

##### `questionnaire_resumed`

- `event_type = questionnaire_resumed`
- `actor_user_id` = сотрудник, выполнивший действие
- `payload = { field: string }`
- `body = null`
- событие создаётся только если `ResumeContactDataCollectionAction` реально вернул `nextField`

#### Правила записи

- merged-contact не хранит эти события сам; запись идёт только в root-contact
- запись событий живёт в action/service-слое, а не в page-level или modal UI
- `ownership_changed` пишется для:
  - `null -> actor.id` при `claim`
  - `current_owner_id -> null` при `release`
  - `from_user_id -> to_user_id` при `assign/reassign`
- `questionnaire_resumed` пишется только после успешного `startDataCollection()`

#### UI-контракт

- `ownership_changed`
  - title: `Ответственный изменён`
  - description:
    - `Контакт взят в работу`
    - `Контакт освобождён`
    - `Ответственный изменён: A -> B`
- `questionnaire_resumed`
  - title: `Анкета возобновлена`
  - description: `Анкета возобновлена с шага: ...`
- `actorName` рендерится так же, как уже рендерится у `operator_comment`

#### Минимальный write-set

- `ContactTimelineEvent`
- `ClaimContactAction`
- `ReleaseContactAssignmentAction`
- `SetContactAssigneeAction`
- `ResumeContactDataCollectionAction`
- `BuildContactHistoryTimelineAction`
- feature-тесты ownership/resume/history

#### Тестовая стратегия

- claim пишет `ownership_changed`
- release пишет `ownership_changed`
- assign/reassign пишет `ownership_changed`
- сохранение того же самого `assignee` не пишет событие
- merged-contact path пишет событие в root-contact
- успешный resume пишет `questionnaire_resumed`
- `nextField = null` не пишет событие
- merged-contact resume пишет событие в root-contact
- `История` рендерит оба новых event types
- mixed ordering остаётся обратным хронологическим

#### Критерии приёмки

- `История` показывает lifecycle events, comments и ключевые system events в одном timeline
- ownership и resume пишут события один раз в action/service-слое и не зависят от конкретной UI-оболочки
- merged/root поведение остаётся корректным
- новый storage для timeline не добавляется

### Implementation slice: Этап 3 v1 (`operator_comment`)

#### Scope

- новая таблица `contact_timeline_events`
- новая модель `ContactTimelineEvent`
- пока только `event_type = operator_comment`

  - существующие lifecycle events

#### Out of scope

- `questionnaire_resumed`
- любые другие system events

- reactions, mentions, attachments
- audit history `old -> new`
- phone/tag/auto-reply/Bitrix events

#### UI-контракт

- после сохранения комментарий появляется в том же timeline

  - автора
  - время
  - текст
- пустой комментарий не сохраняется

#### Минимальный write-set

- action для записи комментария
- builder `Истории`
- page-level `ViewContact`
- blade/partial вкладки `История`

#### Критерии приёмки

- комментарий хранится локально в новой write-модели
- timeline показывает и lifecycle events, и comments в одном порядке
- `История v1` не ломается

## Критерии приёмки

### После этапа 1

- контакт открывается как отдельная страница
- шапка показывает заголовок `Фамилия Имя` с согласованным fallback
- вкладки `Общее`, `Диалоги`, `Битрикс24`, `История` работают
- вкладка `Общее` использует двухколоночный layout `50/50`
- вкладки `Диалоги`, `Битрикс24` и `История` используют полноширинный layout
- вкладка `Общее` содержит все операторские non-bitrix поля `Contact` из Приложения А
- оператор видит те же рабочие действия, что и в текущей карточке
- modal-карточка перестаёт быть основным способом открытия контакта

### После этапа 2

- вкладка `История` работает как отдельный read-only timeline
- timeline показывает только high-signal события состояния контакта
- timeline включает загрузку следующей порции событий
- первая версия timeline ограничена 5 согласованными типами событий без Bitrix24 и phone capture

### Отдельный реализованный follow-up: `Диагностика`

- вкладка `Диагностика` доступна только администраторам
- webhook/runtime и dedup-данные не возвращаются во вкладку `Общее`
- обычный оператор вкладку не видит и не может открыть её query-параметром

## Известные компромиссы

- этап 1 даёт новый page shell без заполненного timeline
- этап 2 использует только существующие источники данных
- первая версия timeline сознательно не включает Bitrix24 sync-события и phone capture
- полная история изменений требует отдельной event/audit модели

## Следующий шаг после текущего rollout

### Правила группировки

- операторские прямые поля `Contact`, кроме `bitrix24_*`, входят во вкладку `Общее`
