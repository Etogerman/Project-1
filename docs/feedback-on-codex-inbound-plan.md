# Обратная связь по плану Кодекса: приём входящих сообщений

## Что Кодекс правильно поймал

### 1. Разделение `inbound_system_event` от `message_kind`

Это важный момент. Сейчас `message_kind` уже участвует в логике автоответа, анкетирования и Битрикс-экспорта в `DispatchStoredInboundBotMessageAction`, `ProcessAutoReplyJob`, `ProcessDataCollectionResponseJob`. Если добавить `KIND_INBOUND_BOT_BLOCKED` как обычный kind, нужно будет везде проверять «а это не системное событие?». Лучше отдельный тип `inbound_system_event` с подтипом `event_code` (например `bot_blocked_by_user`).

### 2. Хранить статус на `dialogs`, а не вычислять из истории

Согласен. Изначально предлагалось два поля: `bot_blocked_at` + `bot_blocked_status`. Версия Кодекса чище: `bot_subscription_status`, `bot_subscription_changed_at`, `bot_subscription_source_message_id`. Третье поле — связь с источником, полезно для отладки.

### 3. MAX отписка не подтверждена документацией

Кодекс прав — нужно проверить, есть ли в MAX API событие отписки. Изначально предполагалось, что `bot_stopped` — это отписка, но это может быть просто «пользователь нажал стоп», не то же самое что блокировка. Делать `Telegram-first`, для MAX заложить архитектуру, но не обещать функциональность.

### 4. Скачивание не в вебхуке, а через job

Webhook должен только нормализовать метаданные. Файлы могут быть тяжёлыми, а ссылки от Telegram (`getFile`) живут ограниченное время — нужна повторная попытка через очередь.

### 5. Удаление = удаление локального файла, а не записи

Важное уточнение. Запись `attachment` остаётся с `deleted_at`, файл физически удаляется. История диалога не ломается.

### 6. Битрикс-экспорт медиа = отдельный эпик

Это согласуется с правилом проекта: «новые сценарии Битрикс24 вне подтверждённого happy-path требуют отдельного ТЗ» (из `AGENTS.md`). В исходном плане ошибочно был включён экспорт медиа в общий план. Кодекс прав — выносить отдельно.

### 7. Tombstone для удалённого файла

Изначально не было описано что показывать когда файл удалён локально. Кодекс предложил «Файл удалён локально» — простое решение.

### 8. Конкретные ссылки на API документацию

Полезно: ссылки на Telegram `getFile`, `setWebhook`, MAX `Message`, Bitrix `sendMessages`. Реализатору не придётся искать.

## Что нужно поправить у Кодекса

### 1. Нет описания превью видео и стикеров

Стикеры в Telegram — это `webp` или `tgs`. Webp браузер поддерживает, tgs (Lottie) нет — нужна библиотека. Кодекс пишет «превью или fallback», но не уточняет.

**Предложение:**
- Webp стикеры — отображать как картинки
- Tgs (Lottie) — fallback «Стикер: 😀» с эмодзи (если есть в payload)
- Webm видео-стикеры — как видео

### 2. Нет описания альбомов и медиа-групп

В Telegram альбом из нескольких фото — это **несколько отдельных update'ов** с одним `media_group_id`. В системе они должны быть склеены в одно сообщение или показаны как несколько? Кодекс это не описал.

**Предложение:** в первой версии — каждое сообщение обрабатывается отдельно, связь по `media_group_id` сохраняется в `raw_payload`. Группировка для отображения как единого альбома — отдельный будущий шаг.

### 3. Нет обработки ошибок скачивания

Что делать если файл не скачался после N попыток? Показывать как «недоступен»? Перезапускать вручную? Кодекс пишет про job, но не описывает что после отказа.

**Предложение:**
- `download_status`: `pending`, `downloading`, `downloaded`, `failed`
- После 3 неудачных попыток скачивания — `failed`, оператор видит «Не удалось загрузить»
- Истёкшая ссылка платформы не становится отдельным lifecycle-status, а фиксируется как частный случай `failed` через `download_error_code` / `download_error_message`
- В UI: для `failed` показывать тип медиа и кнопку «Перезагрузить»

## Критика моего исходного плана

- Смешал `message_kind` для системных событий и обычных сообщений — нужно разделять
- Не учёл правило «Битрикс расширения только отдельным ТЗ» — включил в общий план
- Не описал tombstone для удалённых файлов
- Не описал что MAX отписка — это гипотеза, а не подтверждённое поведение
- Предложил `bot_blocked_at` + `bot_blocked_status` — Кодекс предложил чище с тремя полями
- Не описал поведение при ошибках скачивания
- Не описал альбомы и медиа-группы Telegram
- Не описал стикеры (webp/tgs/webm)

Принимаю разбивку Кодекса с дополнениями:

| Срез | Что |
|------|-----|
| 1 | Telegram отписка (`my_chat_member`, `inbound_system_event`, статус на диалоге, блокировка отправки) |
