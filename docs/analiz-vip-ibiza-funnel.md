# Анализ: воронка VIP Ибица — что нужно сделать в системе

## Контекст

Клиент хочет реализовать воронку для закрытой VIP-группы. Воронка включает:
- стартовую ссылку с параметром
- приветственное сообщение с кнопкой
- 6 квалификационных вопросов с кнопками
- логику квалификации (сильный/пограничный/слабый)
- сбор телефона и Instagram только для квалифицированных
- запись на конкретное время отборочного созвона
- напоминания за 24 часа и за 2 часа
- три варианта исхода после созвона
- оплату и подтверждение

## Что в этой воронке есть

```
1. Ссылка с параметром (vip_ibiza_apply, vip_ibiza_tg1, etc.)
2. Приветственное сообщение с кнопкой "Начать отбор"
3. Серия из 6 вопросов с кнопками
4. Логика квалификации (сильный/пограничный/слабый)
5. Сбор телефона (только для квалифицированных)
6. Сбор Instagram
7. Запись на конкретное время
8. Подтверждение и напоминания (за 24 ч и за 2 ч)
9. После созвона — три исхода с разными цепочками
10. Ссылка на оплату
11. Подтверждение оплаты
```

## Что есть в системе сейчас

| Возможность | Статус |
|-------------|--------|
| Параметры в ссылках (`?start=...`) | Работает (мы это чинили) |
| Автоответ по параметру | Работает |
| Кнопки в автоответе | Только одна кнопка на правило |
| Сбор анкеты (имя, город, страна, возраст) | Работает, но жёстко зашитый поток |
| Сбор телефона | Работает (phone capture) |
| Условные ветки по ответам | Нет |
| Запись на время | Нет |
| Напоминания по расписанию | Нет |
| Произвольные поля анкеты | Нет (только фиксированные) |
| Цепочки сообщений | Нет — каждое правило это разовое сообщение |
| Условные действия (если/иначе) | Нет |
| Тегирование по ответам | Есть (через автоответ можно ставить теги) |

## Что нужно построить

### Критически не хватает для MVP ядра воронки

#### 1. DB-first runtime сценариев

- Источник истины для сценария: опубликованная `ScenarioVersion` с `schema_payload`
- Блоки: сообщение, вопрос с кнопками, условие, действие, phone capture
- Один generic runtime, который читает сценарий из БД, а не новый PHP-класс под каждую воронку
- Движок выполнения: какой блок сейчас активен у клиента и что лежит в runtime state

#### 2. Богатые сообщения

- Несколько кнопок в одном сообщении
- HTML-форматирование

#### 3. Условные ветки

- «Если ответ = X, иди в блок A; иначе в блок B»
- Расчёт «силы заявки» по сумме ответов

#### 4. Runtime state и сохранение ключевых ответов

- Промежуточные ответы сценария живут в `scenario_runs.state_payload`
- В существующие поля `Contact` или теги промоутируется только то, что реально нужно оператору и другим флоу
- Для MVP не нужен отдельный `custom_fields` на `contacts`

#### 5. Phone capture внутри сценария

- Нужно встроить существующий phone capture flow в generic-сценарий
- После получения телефона сценарий должен продолжаться с нужного блока

#### 6. Уведомления оператору и переход на ручную обработку

- Отправка ссылки/контакта менеджеру
- Уведомление оператора о пограничной заявке

### Следующий этап после MVP ядра

#### 1. Запись на время

- Список доступных слотов
- Бронирование (защита от двойной брони)
- Сохранение выбранного времени к контакту

#### 2. Напоминания по расписанию

- Отложенные сообщения «через 24 часа», «за 2 часа»
- Job в очереди с отложенным запуском

#### 3. Сегментация после созвона и оплата

- Три исхода после созвона
- Ссылка на оплату
- Подтверждение оплаты

### Уже есть, можно использовать

- Параметры из ссылок
- Сбор телефона (можно встроить в нужный момент сценария)
- Тегирование контактов
- Назначение ответственного

## Насколько это сложно

**Сложно.** Это переход от разовых правил автоответов к generic runtime сценариев. В MVP речь не про визуальный конструктор, а про DB-first движок на существующем контуре `scenarios / scenario_versions / scenario_runs`.

## Варианты реализации

### Вариант 1: Полноценный конструктор (правильный, но долгий)

- 3-6 месяцев разработки
- Решает не только эту воронку, а все будущие
- Это путь к собственному SaleBot

### Вариант 2: Хардкод этой конкретной воронки (быстрый, но тупиковый)

- 2-4 недели
- Создать новый класс `VipIbizaApplyScenario`
- Зашить логику ветвления, поля, напоминания, бронирование
- Каждая новая воронка потребует нового хардкода
- 5 воронок = 5 классов = ад поддержки

### Вариант 3: DB-first полу-конструктор на существующем контуре

- 1-2 месяца
- Использовать существующие `scenarios`, `scenario_versions`, `scenario_runs`, `scenario_channel_bindings`
- Описать блоки декларативно в `schema_payload`
- Один generic runtime умеет читать любой DB-сценарий
- Не визуальный: настройка через Filament и редактирование `schema_payload`
- Этой воронкой проверяем подход, потом расширяем

## Моя рекомендация

**Вариант 3 — DB-first полу-конструктор на существующем контуре.**

Почему:
- Вариант 1 слишком долгий — клиент ждёт результата сейчас
- Вариант 2 создаст технический долг, который потом придётся переписывать
- Вариант 3 — реальный фундамент, который расширяет уже существующий сценарный контур без новой параллельной архитектуры

## Минимальный набор для запуска MVP ядра воронки

| Шаг | Что | Сложность |
|-----|-----|-----------|
| 1 | Богатые автоответы (HTML + несколько кнопок) | Средне |
| 2 | DB-first runtime сценариев (`schema_payload` + generic engine) | Сложно |
| 3 | Условные ветки в сценариях | Средне |
| 4 | Runtime state и промоут ключевых ответов в существующие поля/теги | Средне |
| 5 | Phone capture внутри сценария | Средне |
| 6 | Уведомления оператору о пограничных заявках | Просто |

Без шагов 1-3 воронка не запустится как DB-сценарий. Шаги 4-6 дополняют MVP. Запись на время и напоминания — следующий этап после запуска ядра.

## Главный вопрос для решения

**Что важнее сейчас:**

1. Запустить эту конкретную воронку быстро (даже хардкодом)?
2. Или вложиться в фундамент, чтобы любую следующую воронку запустить за день?

От ответа зависит план на ближайшие 1-3 месяца.

## Что не входит в этот документ

- Детальное ТЗ на конструктор сценариев
- Детальное ТЗ на запись на время
- Конкретные тексты сообщений воронки (это контентная часть, не техническая)
- Интеграция с платёжной системой для оплаты
