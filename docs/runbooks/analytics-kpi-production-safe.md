# Безопасный запуск KPI SQL в production

## Назначение

Безопасно получить агрегированные KPI по production-данным AB Connector без
выгрузки персональных данных, текстов сообщений, телефонов, raw payload,
error_message и per-record строк.

Основной SQL-файл:

- `docs/reference/analytics-kpi-production-safe.sql`

## Перед запуском

1. Использовать только read-only DB role с правом `SELECT` и правом создавать
   временные объекты в сессии.
2. Не использовать production superuser/admin credential.
3. Выбрать короткий период для первого запуска: 7 или 30 дней.
4. Указать абсолютные границы периода в часовом поясе `Europe/Moscow`, а не
   относительные формулировки.
5. Не включать подробные connection/debug логи в общий вывод.

Под `read-only DB role` здесь понимается отдельная роль с правами `SELECT` на
нужные таблицы и `TEMP` на database, но без `INSERT`, `UPDATE`, `DELETE` и прав
создания объектов в постоянных схемах. Режим
`default_transaction_read_only=on` с текущей версией SQL несовместим: PostgreSQL
блокирует в нём создание и удаление даже временных views. Если такой режим
обязателен политикой доступа, запуск нужно остановить, а SQL предварительно
переписать без временных объектов.

Для подключения использовать стандартные файлы libpq вне репозитория:

- сервис `ab_connector_production_readonly` в `~/.pg_service.conf` без password;
- отдельный `PGPASSFILE` с правами `0600` для пароля read-only пользователя.

Для прямого TCP-подключения сервис должен использовать проверяемый TLS:
`sslmode=verify-full` и доверенный `sslrootcert`. Если инфраструктура использует
утверждённый защищённый туннель, параметры подключения должны соответствовать
его регламенту. Режимы `disable`, `allow` и `prefer` для прямого подключения к
production запрещены.

Не передавать содержимое этих файлов в чат, issue, PR или отчёт. Не использовать
URI с password как аргумент `psql`: после раскрытия shell-переменной credential
может быть виден в списке процессов.

## Команда запуска

Пример запуска 2026-07-08 в 00:05:00 по Москве за полные семь предыдущих дней:

```bash
PGSERVICE=ab_connector_production_readonly \
PGPASSFILE="$HOME/.pgpass-ab-connector" \
psql \
  --no-psqlrc \
  --set ON_ERROR_STOP=1 \
  -v period_start="2026-07-01 00:00:00" \
  -v period_end="2026-07-08 00:00:00" \
  -f docs/reference/analytics-kpi-production-safe.sql
```

Перед запуском проверить, что сервис использует именно production DB и
read-only пользователя без прав изменения постоянных объектов.
SQL устанавливает для текущей сессии часовой пояс `Europe/Moscow`. Период
полуоткрытый: `period_start` включается, `period_end` не включается. Для полного
дня верхняя граница указывается как полночь следующего дня. SLA-граница
вычисляется как `snapshot_at - 1 hour`. `snapshot_at` автоматически фиксируется
в начале единой транзакции `REPEATABLE READ`; вводить его вручную не нужно. Все
секции читают один согласованный снимок базы. SQL читает текущие стадии,
назначения и runtime-статусы и не восстанавливает их историческое состояние на
произвольную дату.

## Определения метрик

- `dialog_to_usable_contact_rate` — доля подходящих диалогов, созданных в
  периоде, для которых к моменту снимка подтверждён телефон или завершён сбор
  данных.
- `operator_manageability_score` — доля текущих диалогов, требующих ответа, у
  которых последнее входящее сообщение не старше одного часа на момент снимка.
- `bitrix24_crm_happy_path_rate` — доля корневых контактов, впервые ставших
  подходящими в периоде, у которых текущие статусы синхронизации контакта,
  сделки и истории равны `synced`.
- Секции 2 и 3 используют когорту подходящих диалогов, созданных в периоде, и
  их текущее состояние на момент снимка. Поэтому результат за прошлый период
  может измениться после более позднего получения телефона или завершения
  сбора данных.
- `bot_blocks` — все события `bot_blocked_by_user`, полученные в периоде от
  корневых контактов. Метрика не ограничивается диалогами, созданными в том же
  периоде, и совпадает с временной семантикой аналитики приложения.
- В секции 9 Telegram account получает `health_flag = ok`, только если runtime
  существует, авторизация готова, синхронизация работает в live-режиме,
  heartbeat свежий и gateway подтвердил возможность исходящих ответов.

## Что можно передать обратно

Можно передать только агрегированный вывод между явными заголовками секций,
которые печатает SQL-файл:

0. контекст запуска и область данных;
1. сводка основных KPI;
2. агрегированная воронка;
3. воронка по платформе и типу подключения;
4. агрегированная очередь оператора;
5. очередь оператора по возрастным группам;
6. распределение статусов Bitrix24;
7. ошибки Bitrix24 по операции и коду;
8. привязка и live-режим Открытых линий;
9. состояние runtime каналов;
10. контрольные показатели ИИ и сборщика.

Перед отправкой проверить, что в выводе нет:

- connection string, host, user, password, token;
- `dialog_id`, `contact_id`, `channel_id`, `message_id`;
- телефона, имени, email, текста сообщения;
- `raw_payload`, `request_payload`, `response_payload`;
- `error_message` или stack trace.

## Стоп-условия

Остановиться и не продолжать запуск, если:

1. доступ не read-only;
2. команда просит пароль от admin/superuser;
3. SQL возвращает per-record строки или персональные данные;
4. возникает ошибка schema mismatch вроде `column does not exist`;
5. запрос упирается в timeout на коротком периоде;
6. терминал показывает connection string или секреты в ошибке;
7. прямое production-подключение не использует проверяемый TLS;
8. политика доступа требует `default_transaction_read_only=on`.

В этих случаях передать обратно только короткое описание проблемы без секретов.

## Если timeout

1. Не поднимать `statement_timeout` на первом production-запуске.
2. Для секций 2, 3, 6, 7, 8 и 10 сначала сократить период до 1-7 дней.
3. Материализация текущего состояния диалогов и секции 4, 5 и 9 не зависят от
   выбранного периода. Если timeout возникает там, сокращение периода не
   поможет: запуск нужно остановить и разобрать конкретный блок локально по
   схеме и плану запроса.

## После запуска

1. Скопировать только агрегированный вывод.
2. Удалить локальный файл вывода, если он содержит production totals и не нужен
   для дальнейшего анализа.
3. Передать агрегаты для интерпретации KPI и уточнения следующих запросов.

Временные views, таблица и индекс создаются внутри одной транзакции
`REPEATABLE READ` и удаляются итоговым `ROLLBACK`; production-схема и данные не
изменяются. При ошибке `ON_ERROR_STOP` завершает psql, а незавершённая транзакция
также откатывается. Текущее состояние очереди диалогов материализуется один раз
и повторно используется секциями 1, 4 и 5.
