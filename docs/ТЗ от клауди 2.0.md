# ТЗ от Клауди 2.0: Движок сценариев — фундамент для собственного SaleBot

## Контекст

В проекте уже есть частично реализованный сценарный движок: модели, таблицы, версионирование, Filament-админка. Но runtime работает только на handler-классах из `config/scenarios.php` (`WarmupScenario`, `NeedsDiscoveryScenario`). Нельзя создать новый сценарий без написания PHP-класса.

Цель: подключить runtime к существующим DB-сценариям так, чтобы можно было создавать произвольные воронки через `schema_payload` в `scenario_versions`. Первая воронка для проверки — VIP Ибица.

## Стратегические решения

| Вопрос | Решение |
|--------|---------|
| Источник истины для сценариев | Существующее версионирование в БД (`scenarios` + `scenario_versions.schema_payload`). YAML не вводим. |
| Кто настраивает | Через Filament-админку, редактируя `schema_payload` |
| Совместимость со старыми сценариями | `WarmupScenario`/`NeedsDiscoveryScenario` остаются как built-in. Новые DB-сценарии — параллельно. Старые не переписываем. |
| Произвольные поля контакта | Не вводим в MVP. Всё в `scenario_runs.state_payload`. Если нужно — промоутировать в существующие поля или теги. |
| Запись на время | Не входит в MVP. Внешняя ссылка на календарь. |
| Напоминания | Не входят в MVP. Менеджер напоминает вручную. |
| Параллельные сценарии | Один активный run на `dialog_id`. Инвариант совпадает с текущей БД. |
| Запрос телефона | Только кнопкой `request_contact`, никогда текстом. |
| Существующая анкета | Не трогаем в MVP. Миграция — отдельный этап позже. |

### Что добавляется

#### Новый runtime-контракт

`ScenarioHandler::code(): string` — статический метод. Не подходит для DB-сценариев, где код определяется записью в БД, а не классом.

Решение: ввести второй runtime-контракт `ResolvedScenarioRuntime` (или аналогичный adapter), где код передаётся при инстанцировании, а не возвращается статически.

```php
interface ResolvedScenarioRuntime
{
    public function code(): string;
    public function shouldStart(Message $message): bool;
    public function start(ScenarioRun $run, Message $message): void;
    public function handleInbound(ScenarioRun $run, Message $message): ScenarioInboundResult;
}
```

`WarmupScenario` и `NeedsDiscoveryScenario` оборачиваются в adapter, который реализует `ResolvedScenarioRuntime` и делегирует на статические методы.

`GenericDbScenarioRuntime` — новый класс, реализующий `ResolvedScenarioRuntime`. Принимает `Scenario` (модель) и опубликованную `ScenarioVersion` через конструктор. После `slice 0` уже подключён в runtime discovery как stub. В `slice 1` начинает исполнять published `schema_payload`, но только для линейного flow с блоками `message`, `question`, `complete`.

#### Единый catalog

`ScenarioRegistry` расширяется:
- `has(string $code): bool` — проверяет и config, и активные `scenarios` в БД
- `makeRuntime(string $code): ?ResolvedScenarioRuntime` — возвращает адаптер для built-in или новый `GenericDbScenarioRuntime` для DB-сценариев
- Кэширование DB-сценариев через `Cache::remember()`
- Инвалидация кэша при `PublishScenarioVersionAction`

#### Контракт результата

`ScenarioInboundResult` остаётся без изменений. Generic engine использует тот же объект:
- `currentStep` — хранит ID блока в `schema_payload`
- `statePayload` — runtime state с пространствами имён

### Пространства имён переменных

Все переменные в сценарии должны явно указывать пространство имён:

| Префикс | Куда сохраняется |
|---------|-------------------|
| `run.*` | `scenario_runs.state_payload` |
| `contact.*` | Поля модели `Contact` (только существующие) |
| `contact.tag.*` | Теги через существующий механизм |

`save_to` без префикса запрещён. Валидация при сохранении сценария в админке.

### Структура `schema_payload`

Ниже приведён расширенный пример полной схемы. Для `slice 1` он шире фактического scope:
- `condition` реализуется только в `slice 2`
- `phone_capture` реализуется только в `slice 3`
- actions уровня `notify_operator` / `set_field` не входят в `slice 1`

```json
{
  "version": 1,
  "start_block_id": "welcome",
  "triggers": [
    {"type": "parameter", "value": "vip_ibiza_apply"},
    {"type": "parameter", "value": "vip_ibiza_tg1"}
  ],
  "blocks": {
    "welcome": {
      "type": "message",
      "text": "...",
      "text_format": "html",
      "buttons": [
        {"label": "Начать отбор", "action": "callback", "next": "ask_name"}
      ]
    },
    "ask_name": {
      "type": "question",
      "text": "Как тебя зовут?",
      "expects": "text",
      "save_to": "contact.first_name",
      "next": "ask_dates"
    },
    "ask_dates": {
      "type": "question",
      "text": "Готова ли ты участвовать в выездной VIP-группе на Ибице 1-5 июня?",
      "expects": "button",
      "save_to": "run.dates_response",
      "buttons": [
        {"label": "Да, готова", "value": "ready", "next": "ask_goal"},
        {"label": "Сейчас даты не подходят", "value": "not_ready", "next": "weak_branch"}
      ]
    },
    "evaluate": {
      "type": "condition",
      "branches": [
        {
          "if": {
            "all": [
              {"var": "run.dates_response", "equals": "ready"},
              {"var": "run.commitment", "equals": "full_commitment"},
              {"var": "run.budget_tier", "in": ["middle", "high"]}
            ]
          },
          "then": "strong_branch"
        },
        {"default": "weak_branch"}
      ]
    },
    "request_phone": {
      "type": "phone_capture",
      "text": "Оставь, пожалуйста, телефон для связи.",
      "button_label": "Поделиться номером телефона",
      "next": "confirmation"
    },
    "confirmation": {
      "type": "message",
      "text": "Спасибо! Менеджер свяжется с тобой.",
      "actions": [
        {"type": "set_tag", "value": "vip_strong"},
        {"type": "notify_operator", "template": "Новая сильная заявка"}
      ],
      "next": "end"
    },
    "end": {"type": "complete"}
  }
}
```

### Типы блоков для MVP

| Тип | Назначение |
|-----|------------|
| `message` | Отправить сообщение, опционально с кнопками. Переход по `next` или нажатию кнопки. |
| `question` | Отправить вопрос, ждать ответ (текст, кнопка или любой). Сохранить в `save_to`. |
| `condition` | Ветвление по правилам (`equals`, `not_equals`, `in`, `not_in`, `all`, `any`, `not`). |
| `phone_capture` | Запросить телефон кнопкой. Использовать существующий phone capture flow. После получения — продолжить сценарий. |
| `action` (внутри блока) | `set_tag`, `remove_tag`, `notify_operator`, `set_field` |
| `complete` | Завершить сценарий. |

### Поддерживаемые входящие события

Сценарий может обрабатывать:
- `text` — обычное текстовое сообщение
- `telegram_callback` — нажатие inline-кнопки
- `contact_share` — клиент поделился телефоном
- `max_bot_started_with_parameter` — старт MAX-бота по ссылке с параметром

### Каноничный формат callback

Новый формат для всех generic-сценариев:
```
scenario:{runId}:{key}
```

Регулярка:
```
^scenario:(\d+):([A-Za-z0-9_-]{1,32})$
```

Старый формат `scenario:warmup:{runId}:{action}` остаётся как legacy для совместимости с `WarmupScenario`. Все новые сценарии используют только canonical format.

### Валидация callback при получении

При парсинге callback нужно проверить:
- `run_id` существует в БД
- `channel_id` совпадает с каналом, где был запущен run
- `external_chat_id` совпадает с chat_id из run-а
- `external_user_id` совпадает с user_id из run-а
- `status === 'active'`
- callback соответствует ожидаемому состоянию текущего блока (есть ли такой `key` в кнопках текущего блока)

## Блокеры (этап 0 — runtime bridge)

Без разблокировки этих мест ни один новый сценарий не запустится.

### Блокер 1: Telegram callback захардкожен под warmup

**Файлы:**
- `app/Services/Bots/BotIncomingMessageNormalizer.php` (строка 127)
- `app/Http/Controllers/BotWebhookController.php` (строка 331)

**Проблема:** парсинг callback ищет только `scenario:warmup:` префикс. Другие сценарные callback нормализуются в `null` и теряются.

**Решение:**
- Заменить regex на canonical format
- Парсить любой callback вида `scenario:{runId}:{key}`
- Передавать в `DispatchStoredInboundScenarioAction` для валидации
- Сохранить legacy путь для warmup на переходный период

### Блокер 2: MAX `bot_started + parameter` идёт в автоответ

**Файл:** `app/Services/Bots/DispatchStoredInboundBotMessageAction.php` (строки 67-71)

**Проблема:** если у MAX-сообщения есть `message_parameter`, оно сразу уходит в автоответ. Сценарии не получают шанса.

**Решение:**
- Убрать ранний return
- Добавить событие `max_bot_started_with_parameter` в список поддерживаемых сценариями
- Проверять триггер сценария **до** автоответа
- Если сценарий не сработал — fallback в автоответ

### Блокер 3: `contact_share` не доходит до сценариев

**Файлы:**
- `app/Services/Bots/DispatchStoredInboundBotMessageAction.php` (строки 55-59)
- `app/Services/Scenarios/DispatchStoredInboundScenarioAction.php` (строка 20)

**Проблема:** `contact_share` сразу уходит в `dispatchContactShareFollowUp`, минуя сценарии. Сценарий не может принять телефон.

**Решение:**
- Если есть активный run для диалога — передать `contact_share` в `ScenarioRunner` до старого phone capture
- Если сценарий обработал — стоп
- Если нет — старый phone capture flow продолжается как раньше

### Новый порядок маршрутизации

В `DispatchStoredInboundBotMessageAction`:

```
1. Дедупликация и системные guard clauses
2. Если есть активный scenario_run для dialog_id → передать в ScenarioRunner
3. Если сценарий не забрал событие и это contact_share → legacy phone follow-up
4. Если сценарий не забрал событие и контакт в data_collection → legacy collector
5. Если активного run нет → ScenarioTriggerResolver пытается стартовать новый сценарий
6. Если сценарий не стартовал → auto-reply fallback
```

## Слайсы

### Slice 0: Runtime bridge (1-1.5 недели)

**Что делается:**
- Новый контракт `ResolvedScenarioRuntime`
- Adapter для `WarmupScenario` и `NeedsDiscoveryScenario`
- `ScenarioRegistry` становится единым catalog (built-in + DB) с кэшированием
- Generic Telegram callback routing (canonical format + legacy для warmup)
- Поддержка `contact_share` и `max_bot_started_with_parameter` в `DispatchStoredInboundScenarioAction`
- Новый порядок маршрутизации в `DispatchStoredInboundBotMessageAction`
- Валидация `scenario_code` через единый catalog в `ScenarioChannelBinding` и `ScenarioRun`

**Критерии приёмки:**
- `WarmupScenario` и `NeedsDiscoveryScenario` продолжают работать без изменений
- Можно зарегистрировать новый scenario code в БД и привязать к каналу
- Generic callback парсится и валидируется
- `contact_share` доходит до сценариев

### Slice 1: DB-backed generic engine (1-1.5 недели)

**Что делается:**
- `GenericDbScenarioRuntime` перестаёт быть stub и начинает исполнять DB-сценарии
- Чтение published `schema_payload` из `ScenarioVersion`
- Trigger типа `parameter`
- Поддержка только линейных блоков: `message`, `question`, `complete`
- Сохранение `current_step` и `state_payload`
- Минимальная валидация `schema_payload` при сохранении сценария в Filament

**Что не входит:**
- `condition`
- `phone_capture`
- actions (`set_tag`, `remove_tag`, `notify_operator`, `set_field`)
- operator visibility / summary UI
- generic continuation через `contact_share` внутри DB engine
- Ibiza-specific special-case логика

**Критерии приёмки:**
- Можно создать и опубликовать DB-сценарий в админке
- Сценарий стартует по `parameter` trigger
- Линейный поток `welcome → question → question → complete` работает
- Ответы сохраняются в `scenario_runs.state_payload`
- `current_step` двигается по блокам
- Built-in сценарии не ломаются

### Slice 2 lite: Условия и tags (1 неделя)

**Что делается:**
- Тип блока `condition` с правилами `equals`, `not_equals`, `in`, `not_in`, `all`, `any`, `not`
- Actions только уровня `set_tag` и `remove_tag`
- Чтение переменных только из `run.*`

**Что не входит:**
- `notify_operator`
- `set_field` / `set_contact_field`
- operator visibility / summary UI
- callback-buttons внутри DB engine
- MAX-specific расширения

**Критерии приёмки:**
- Воронка с тремя ветками работает корректно
- Ветвление читает ответы только из `run.*`
- `set_tag` и `remove_tag` реально меняют теги контакта

### Slice 3: Phone capture в сценариях (1 неделя)

**Что делается:**
- Тип блока `phone_capture`
- Интеграция только с уже существующим `contact_share` / phone capture flow для Telegram и MAX
- Для active DB-run continuation происходит только через входящее событие `contact_share`
- Сначала телефон сохраняется в `Contact` существующим путём, затем сценарий продолжается с `next`
- Запрос телефона только provider-specific кнопкой, никогда не текстом

**Что не входит:**
- Ввод телефона текстом
- Новый transport-layer сверх уже существующего phone capture flow
- `notify_operator`, `set_field` / `set_contact_field`
- callback-buttons внутри DB engine
- Переписывание legacy phone capture flow для не-сценарных диалогов

**Критерии приёмки:**
- Сценарий запрашивает телефон в любой точке
- Active DB-run на блоке `phone_capture` ждёт именно `contact_share`
- После получения телефона — продолжение с `next`
- Никогда не запрашивает текстом
- Legacy phone capture flow для диалогов без active scenario step не ломается

### Slice 4 (отложен): Запись на время и напоминания

- `appointment_slots` таблица
- Тип блока `appointment_pick`
- Тип блока `schedule`
- Job для отложенных сообщений

Не входит в MVP.

### Slice 5 (отложен): Миграция старого collector

Существующая анкета (имя, город, страна, возраст) переписывается как сценарий. Старый код помечается deprecated. Не входит в MVP.

## Ibiza MVP — после Slice 3

После завершения slice 0-3 можно запустить воронку VIP Ибица:

- **Trigger:** `vip_ibiza_apply`, `vip_ibiza_tg1`, `vip_ibiza_inst1`
- **Flow:** welcome → старт отбора → 6 вопросов → `strong / borderline / weak`
- **Реализация:** только на уже готовых блоках `message`, `question`, `condition`, `phone_capture`, `complete`
- **State:** ответы сохраняются только в `run.*`
- **strong:** `phone_capture` → вопрос про Instagram → тег `vip_strong`
- **borderline:** `phone_capture` → тег `vip_borderline`
- **weak:** альтернативный оффер или завершение → тег `vip_weak`

### Границы Ibiza MVP

**Что входит:**
- published DB-сценарий `VIP Ibiza`
- parameter trigger для `vip_ibiza_*`
- ветвление `strong / borderline / weak` через `condition`
- `phone_capture` только в тех ветках, где нужен телефон
- outcome visibility через теги контакта
- привязка сценария к нужным каналам
- staging smoke и короткий ручной happy-path

**Что не входит:**
- `appointment_pick`
- `schedule`
- напоминания
- `notify_operator`
- `set_field` / `set_contact_field`
- callback-buttons внутри DB engine
- новый transport-layer
- отдельный summary UI

### Хранение схемы Ibiza

Source of truth для `Ibiza MVP` остаётся тем же, что и для всего движка:
- runtime-версия живёт в БД (`scenarios` + `scenario_versions.schema_payload`)
- настройка и публикация идут через Filament-админку

В репозитории допускаются только вспомогательные артефакты:
- test helper / fixture для schema в `tests`
- reference JSON в `docs`, если он нужен оператору как шаблон

В `Ibiza MVP` не вводим:
- сидер сценария
- миграцию с runtime-content
- файловый runtime-source вместо published DB-version

Запись на время для этого MVP остаётся внешней ссылкой на календарь. Напоминания — вручную. Operator visibility в этом MVP — только через теги контакта; summary UI и отдельные уведомления — следующий этап.

## Критерии приёмки MVP

- Сценарий стартует из published DB-version, а не из `config/scenarios.php`
- `WarmupScenario` и `NeedsDiscoveryScenario` не ломаются
- Telegram callback generic-сценария проходит без хардкода в normalizer/controller
- MAX `bot_started + parameter` стартует сценарий, а не только автоответ
- После `contact_share` сценарий продолжается с нужного блока
- Воронка VIP Ибица проходит от старта до квалификации
- Менеджер видит outcome ветки через теги контакта
- Старый collector работает для не-сценарных диалогов
- Старые автоответы работают как раньше

## Что не входит

- YAML как источник истины (используем существующее DB-версионирование)
- Визуальный редактор блоков (drag-and-drop)
- Запись на время в боте (внешняя ссылка)
- Напоминания (вручную)
- Платежи
- Миграция старого profile collector
- Параллельные активные сценарии
- A/B тестирование
- Аналитика воронок
- `contacts.custom_fields` (не нужно для MVP)

## Известные компромиссы

- Без визуального редактора админ редактирует JSON в Filament. Это нормально для разработчика, неудобно для оператора. Редактор — отдельный эпик после стабилизации движка.
- Слот-пикер откладывается. Если воронка VIP Ибица потребует встроенную запись — добавляем в slice 4 как следующий шаг.
- Старые сценарии работают через adapter, что добавляет небольшой слой сложности в `ScenarioRegistry`. Это плата за обратную совместимость.
- Все промежуточные ответы хранятся в `state_payload`. Если нужно сделать поиск/фильтрацию по ответам — придётся выносить их в индексированные поля или использовать JSONB-индексы PostgreSQL.

- Существующие миграции

## Тестовая стратегия

- Регрессия: `WarmupScenario` и `NeedsDiscoveryScenario` работают как раньше
- Регрессия: старые автоответы работают как раньше
- Регрессия: phone capture flow для не-сценарных диалогов работает
- Slice 0: новый runtime catalog возвращает built-in и DB-сценарии
- Slice 0: generic callback парсится и валидируется
- Slice 0: новый порядок маршрутизации не ломает существующее поведение
- Slice 1: создание DB-сценария через Filament, запуск по параметру, прохождение
- Slice 1: валидация `schema_payload` при сохранении (плохая структура → ошибка)
- Slice 2: ветвление работает по всем операторам
- Slice 2: `set_tag` и `remove_tag` меняют теги контакта
- Slice 3: phone_capture запрашивает телефон кнопкой и продолжает после
- E2E: воронка VIP Ибица проходит от старта до квалификации с разными ответами
