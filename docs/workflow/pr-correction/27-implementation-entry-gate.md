# Проверка перед реализацией

Загружайте этот модуль только для состояния `G00`.

## `G00` — Проверка ТЗ, Spec и разрешений перед реализацией

Исполнитель: агент.

Перед локальной реализацией проверяются актуальность ТЗ для текущих base/head,
закрытие обязательных внешних review, текущая команда пользователя, предел
исполнения и отсутствие открытого продуктового решения или blocker-а.

До `G00` создаётся неизменяемая
`implementation-spec-classification.json`. Она связывает ТЗ, base/head/tree,
точный diff, класс stream-а, шесть publish/release-факторов, доказательства и
решение `not_required`, `pending` или `fixed`. Неопределённость запрещает
`not_required`; `fixed` требует проверенную `Spec revision`.

Spec обязателен только для миграции, секрета, VPS, deploy, staging или внешней
мутации. Для обычного локального исправления Spec не требуется и `git show` не
вызывается. Если Spec обязателен, фиксируются `Spec repo`, `Spec doc` и
`Spec revision`; commit ревизии должен изменять сам документ, а SHA-256 точных
байтов между единственными маркерами `IMPLEMENTATION-CONTRACT START/END` в
итоговом ТЗ и документе Spec обязан совпасть.

| № | Проверяемый результат | Следующее состояние | Исполнитель перехода |
|---:|---|---|---|
| 1 | Все условия выполнены | `C10` | Агент |
| 2 | Требуется разрешение, ручное действие или разрешение на фиксацию обязательного Spec; сохранить `resume_state=G00` | `D02` | Агент → пользователь |
| 3 | Не хватает доказательств или доступа; сохранить `return_state=G00` | `B01` | Агент |
| 4 | Изменился продукт, риск или объём работ | `D01` | Агент → пользователь |
| 5 | Обязательный Spec отсутствует либо hash блока не совпадает, а фиксация разрешена | `EXIT:main_process_spec_revision` | Основной процесс |

После внешней фиксации Spec разрешён возврат только в `G00`. Это состояние
повторяет все проверки; `D02` не материализует Spec и не ведёт прямо в код.
Любое последующее изменение объёма, риска, внешних мутаций или требований к
Spec аннулирует результат проверки и возвращает работу к новому ТЗ либо
решению пользователя.

Успешный `G00` атомарно создаёт строгий `implementation-gate.json`, выданный
только `G00`. Он связывает cycle/revision, итоговый review manifest, ТЗ,
base/input HEAD и identity классификации и разрешает только `C10`, `C11` и
`G01`. Ожидаемые рабочие изменения `C10` gate не аннулируют; изменение любого
входного доказательства аннулирует.
