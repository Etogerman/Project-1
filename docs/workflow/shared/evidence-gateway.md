# Доказательный шлюз

Этот документ определяет достаточные доказательства для независимого review и
технической квалификации сигнала. Он применяется из состояний `C02`, `C03` и
`P02` цикла исправления PR.

## Термины

- `Review snapshot` — зафиксированный снимок PR: полные `base SHA`, `head SHA`
  и SHA-256 точной строки `title + "\n" + body`; для сверки CI используется
  `head SHA` этого снимка.
- `P0` — доказанный дефект с непосредственным риском необратимой потери или
  порчи данных, уязвимости, полного отказа критичного контура либо необратимого
  или масштабного неконтролируемого внешнего действия.
- `P1` — доказанный дефект без последствий уровня `P0`, который нарушает
  обязательный пользовательский сценарий или инвариант данных, безопасности,
  интеграции либо доставки и блокирует текущий merge или release.

## Правила

1. При review зафиксированного снимка code/runtime PR с применимым CI перед
   публикацией `P0`, `P1` или inline-аннотации, опирающейся на результат CI,
   ревьюер сверяет проверку с точным `head SHA`. Ссылка на падение указывает
   конкретное имя или ID проверки этого SHA.
2. При прямой проверке commit-а, docs-only/process-only PR или снимка без
   применимых проверок отсутствие CI само по себе не запрещает `P0`, `P1` или
   inline-аннотацию. Допустимы доказательства из diff точного SHA,
   воспроизводимого теста или команды, привязанных к снимку логов либо
   проверяемого инварианта с указанным путём исполнения.
3. Если вывод зависит от версии внешней платформы, библиотеки, фреймворка,
   синтаксиса конфигурации или инструмента, обязательна актуальная первичная
   документация производителя. Память модели, совпадение мнений агентов,
   вторичный пересказ и старый комментарий доказательством не являются.
4. Если отсутствуют все применимые доказательства, источники противоречивы или
   не подтверждают критичность, ревьюер не публикует блокирующее замечание либо
   inline-аннотацию. Он фиксирует ограничение и передаёт гипотезу человеку.
   Отсутствие только CI не включает этот запрет, когда дефект подтверждён другим
   допустимым прямым доказательством.
5. Успешная релевантная проверка точного SHA опровергает только утверждение,
   которое она действительно проверяет. Другой воспроизводимый сценарий или не
   охваченный проверкой путь оценивается отдельно.
6. Доказательный шлюз не меняет роли: ревьюер проверяет и сообщает результат,
   а исправление выполняет назначенный исполнитель после применимого ТЗ и
   разрешения.
