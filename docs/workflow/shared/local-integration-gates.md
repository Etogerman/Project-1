# Локальные интеграционные границы

Этот модуль читается при работе с Bitrix24, Open Lines, Telegram, MAX,
webhook/callback и другими внешними интеграциями.

1. Staging не используется как первая среда воспроизведения, если доступен
   рабочий локальный контур с тестовой внешней системой.
2. Сначала фиксируется локальный маршрут: URL, callback/webhook endpoint,
   тестовый портал/бот/линия и требуемые процессы runtime.
3. Локально воспроизводятся исходный дефект и исправленный сценарий. Для
   публикации фиксируются команды, логи, скриншоты или другой проверяемый
   артефакт.
4. Мутирующее действие во внешней тестовой системе требует отдельного описания
   ожидаемых побочных эффектов и способа отката/очистки, а затем отдельного
   разрешения пользователя.
5. Для Bitrix24 Open Lines агент отдельно подтверждает отсутствие методов,
   способных неявно создать новую открытую линию, если создание не является
   целью проверки.
6. Перед операторской приёмкой запускается полный локальный runtime, а не только
   web-server: приложение, scheduler и нужные queue workers. Для каналов связи
   отсутствие scheduler-а является блокировкой, потому что UI получает
   устаревшие статусы.
7. После смены `LINE_ID`, `connector_code`, callback owner или tunnel/callback
   URL заново публикуется OpenLines route registry, Doctor доводится до
   `synced` / `Diffs 0`, и только затем проверяется новый ответ из Bitrix24.
   Старые сообщения до публикации registry не являются доказательством fix-а.
8. Выход в staging допустим после локального доказательства либо после явного
   пользовательского исключения с перечисленным остаточным риском.
