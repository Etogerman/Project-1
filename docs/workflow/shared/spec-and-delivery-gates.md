# ТЗ и границы доставки

Этот модуль читается для нового stream-а, публикации, staging/main, deploy,
smoke, closure и ответа о следующем этапе доставки. Пошаговые этапы, ещё не
вынесенные в отдельные модули, остаются в
[`docs/task-delivery-workflow.md`](../../task-delivery-workflow.md).

## Термины

- `ТЗ` — согласованный контракт текущего stream-а.
- `Spec repo` — внешний репозиторий документации с полным ТЗ.
- `Spec doc` — конкретный документ ТЗ.
- `Spec revision` — commit, изменивший сам `Spec doc`; изменения только
  реестров документации эту ревизию не двигают.
- `Активный slice` — внутренний инженерный подшаг, не являющийся основанием для
  автоматического выхода в staging.
- `Локальный MVP` — минимальный локальный end-to-end результат, который можно
  честно показать оператору.
- `Хвост` — незавершённое обязательство stream-а: diff, commit/push, PR, CI,
  rollout, closure, cleanup или follow-up.

## ТЗ и внешний репозиторий

1. Мелкое локальное исправление может опираться на согласованное ТЗ в чате.
2. Существенный stream до решения о выкладке может хранить временный черновик
   только в чате или явно указанном локальном месте вне основного и внешнего
   репозиториев.
3. До первого внешнего publish/release действия существенного stream-а должны
   быть зафиксированы `Spec repo`, `Spec doc` и `Spec revision`.
4. Стандартный контур: `Etogerman/Project-1-specs`, локально
   `/Users/abrikosov/Documents/Project-1-specs`. Перед записью применяются его
   `README.md`, `active-streams.md`, `streams/README.md` и шаблон stream-а.
   Новый существенный документ по умолчанию сохраняется в `streams/`; после
   изменения обновляется `streams/README.md`, а `active-streams.md` — только
   когда implementation stream реально открыт или меняет статус.
5. Основной репозиторий хранит код, тесты, настройки, process/policy/reference и
   короткие ссылки; полные живые ТЗ и их реестр здесь не хранятся.
6. Расхождение кода, локальных документов и внешнего ТЗ сначала показывается
   пользователю. Правильная версия не выбирается молча.
7. Статусы существенного Spec синхронизируются после материализации результата:
   `Spec doc`, `streams/README.md` и `active-streams.md` не остаются в
   противоречии.
8. Перед новым несвязанным существенным code stream-ом проверяется внешний
   `spec/admin tail` предыдущего stream-а.

## Локальная граница

1. Команда `реализовать` по умолчанию разрешает довести новый code stream до
   согласованного локального MVP, но не разрешает публикацию.
2. После локального MVP агент предлагает конкретную операторскую проверку и
   ждёт явного решения о готовности к выкладке. Зелёные автотесты её не заменяют.
3. Перед handoff оператору обязательна идентичность runtime: URL, процесс или
   контейнер, смонтированный worktree, ветка и commit внутри runtime, видимый
   `rev`/version marker и его совпадение с commit stream-а.
4. Если идентичность не подтверждена, операторская приёмка недоступна до запуска
   правильного контура или отдельного временного URL.

## Обычный путь доставки

Для нового code stream-а без явного исключения действует порядок:

`локальный MVP → операторская приёмка и решение о выкладке → фиксация
существенного ТЗ → draft PR в staging → CI → пользовательский ready →
независимые проверки снимка → сводный вердикт → пользовательский merge в
staging → deploy-check → staging smoke → staging QA → draft PR в main из
validated diff → CI → пользовательский ready → независимые проверки снимка →
сводный вердикт → пользовательский merge в main → production deploy →
production smoke`.

Дополнительные инварианты:

1. Первый внешний PR нового code stream-а по умолчанию направлен в `staging`.
   Прямой main требует отдельного явного решения пользователя.
2. Срочный hotfix может получить ранние push + draft PR в staging со статусом
   `Spec pending`, но ready, merge и deploy блокируются до `Spec revision`.
3. PR в main строится из validated diff активного stream-а, а не из состояния
   ветки staging. Его body содержит точные `Staging PR(s)` и `Staging smoke`.
4. После staging deploy обязателен живой staging QA либо явное принятие
   остаточного риска. Автоматический smoke сам по себе QA не заменяет.
5. После merge в main следующий этап code/release stream-а — ручной production
   deploy, затем Production Post-Deploy Smoke.
6. Docs-only/process-only/reference-only изменение использует отдельный clean
   docs-only stream от `origin/main`: commit → draft PR, если пользователь не
   выбрал отмену или паузу.
7. Текущее состояние runtime используется для диагностики, но не отменяет
   staging-first путь после решения о выкладке.

## Review, closure и cleanup

1. Нетривиальный PR создаётся как draft. После авторской проверки снимка
   пользователь проверяет CI и выполняет ready.
2. Для code/runtime PR после ready обязательны независимые проверки агента и
   стороннего ИИ одного `Review snapshot`; merge выполняет только пользователь
   после сводного вердикта `готово к merge`.
3. Сигнал открытого PR обрабатывается только через
   [цикл исправления](../pr-correction/README.md).
4. После materialized result выполняются Issue Closure и Spec Closure. Cleanup
   доступен только когда оба checkpoint имеют `completed` или `not_required`.
5. Принятая, но оставленная открытой Issue становится неблокирующим
   issue/admin tail. `deferred` с сохранённым branch/worktree остаётся dormant
   tail и не считается завершённым cleanup.
6. Materialized result существует, если изменение полностью или частично
   смёржено в delivery-ветку, активировано в shared runtime либо опубликовано
   вне временного review evidence. Локальный worktree, remote feature branch,
   открытый PR и CI/review сами по себе materialization не создают.
7. No-result closure допустим только после доказательства отсутствия любой
   materialization и решения пользователя `cancelled`, `deferred` или
   `closed_without_merge`. Auto-delete ветки не заменяет cleanup checkpoint.

## Обязательные поля задания существенного stream-а

Задание на реализацию указывает рабочую копию, ветку, `Spec repo`, `Spec doc`,
`Spec revision`, базу первого PR и точку остановки. Расхождение этих полей с
путём доставки является блокировкой до решения пользователя.
