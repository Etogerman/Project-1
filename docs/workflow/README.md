# Маршрутизатор рабочего процесса

Этот каталог реализует пошаговую загрузку правил. Агент сначала определяет
текущее состояние, затем читает только документ этого состояния и явно
указанные общие правила. Полный обзор процесса не загружается без необходимости.

## Порядок загрузки

1. Применить обязательные инварианты из `AGENTS.md`.
2. Для любого изменения файлов, документации или Git прочитать
   [язык и стандарты Git](shared/language-and-git-standards.md).
3. Перед изменяющим действием прочитать
   [полномочия, потоки и передачу шага](shared/work-authority.md).
4. Определить тип потока и текущий уровень доставки через
   `ab-stream-state-resolver`.
5. По таблице ниже открыть только общие модули, относящиеся к задаче.
6. Если есть сигнал об ошибке в открытом PR, определить состояние цикла:

   ```bash
   node .github/scripts/workflow-docs-check.mjs --state C01
   ```

7. Прочитать только документ, указанный командой.
8. При переходе повторить команду с новым ID и открыть следующий документ.
9. `docs/task-delivery-workflow.md` открывать дополнительно только для этапа
   основного delivery-процесса, который не покрыт текущим модулем.

Если ID состояния неизвестен, агент не угадывает этап. Новый сигнал открытого PR
начинается с `C01`; другой процесс возвращается к определению уровня доставки.

## Маршруты по типу задачи

| Задача | Обязательный профильный модуль |
|---|---|
| Любое создание/изменение файла, документации, Git-состояния или ветки | [Язык и стандарты Git](shared/language-and-git-standards.md) |
| Любое изменение файлов, git или среды | [Полномочия, потоки и передача шага](shared/work-authority.md) |
| ТЗ, новый stream, staging/main, deploy, smoke, closure | [ТЗ и границы доставки](shared/spec-and-delivery-gates.md) |
| Laravel-код, данные, тесты, Filament/Livewire или конфигурация | [Инженерные стандарты](shared/project-engineering-standards.md) |
| Bitrix24, Open Lines, Telegram, MAX, webhook/callback | [Локальные интеграционные границы](shared/local-integration-gates.md) и инженерные стандарты |
| Сигнал об ошибке в открытом PR | [Вход цикла исправления](pr-correction/README.md), затем один модуль текущего состояния |
| Только read-only ответ о следующем шаге | `ab-stream-state-resolver`, затем только модуль текущего этапа |

Если задача пересекает несколько строк, загружаются соответствующие модули, но
не остальные. Например, исправление Bitrix24 PR использует полномочия,
инженерные и интеграционные границы и один текущий модуль цикла PR.

## Канонические источники

- [`states.json`](pr-correction/states.json) — ID, исполнитель, файл состояния и
  допустимая топология переходов цикла исправления PR.
- [Вход и общие правила цикла](pr-correction/README.md) — область применения,
  формат передачи состояния и правила выбора модуля.
- [Prompt внешнего ревью ТЗ](pr-correction/external-spec-review-prompt.md) —
  единственный текст задания, который launcher передаёт независимым reviewer-ам.
- [Доказательный шлюз](shared/evidence-gateway.md) — допустимые доказательства
  при технической квалификации и независимом review.
- Общий профильный модуль — неизменяемые правила конкретного риск-контура без
  перечисления всех этапов процесса.
- Модуль состояния — точные условия каждого перехода и результат состояния.

Состояния и переходы не копируются в `AGENTS.md`, skills,
`docs/action-ownership.md` или `docs/task-delivery-workflow.md`. Эти документы
только направляют к каноническому модулю.

## Проверка структуры

```bash
node .github/scripts/workflow-docs-check.mjs --self-test
node .github/scripts/workflow-docs-check.mjs --check
node .github/scripts/workflow-docs-check.mjs --mermaid
node .github/scripts/workflow-state-policy.mjs --self-test
node .github/scripts/workflow-state-policy.mjs --check
node .github/scripts/workflow-cycle-store.mjs --self-test
node .github/scripts/workflow-spec-review-self-test.mjs
node .github/scripts/workflow-spec-review-gates-self-test.mjs
```

Проверка подтверждает существование состояний и документов, допустимость всех
переходов, достижимость состояний, наличие заголовков состояния в нужных
модулях, обязательные шлюзы и отсутствие сломанных локальных Markdown-ссылок.
Отдельные self-test проверяют внешний review, signal/CI/decision ledger,
transaction recovery, классификации, неизменяемые gate, exact-tree проверки и
согласованность `activeRunId`. Mermaid-команда строит
актуальную схему из того же реестра без отдельной ручной копии.

## Граница пилота

Пока модульно вынесен только цикл исправления открытого PR. Остальные этапы
остаются в `docs/task-delivery-workflow.md` и переносятся отдельными небольшими
изменениями после проверки пилота на реальных сценариях.
