# Технология работы над задачами

## Цель документа

Этот документ описывает подробный delivery-playbook для одного implementation stream.

Роли документов разделены так:
- `AGENTS.md` фиксирует верхнеуровневые рамки, инварианты проекта и ограничения по разрешениям
- этот документ описывает пошаговую процедуру внутри этих рамок

Если между документами есть пересечение, `AGENTS.md` задаёт рамки и права,
а `docs/task-delivery-workflow.md` — порядок действий.

## Границы документа

Здесь нет:
- полного проектового описания
- подробной архитектурной карты
- полного domain/config reference
- code style и language rules

Здесь есть только workflow:
- классификация запроса
- read-only анализ
- подготовка и проверка ТЗ
- slices
- preflight
- branch/start rules
- реализация
- локальные проверки
- контрольные точки и разрешения
- `commit/push/PR/CI`
- путь через `staging` и `main`
- `docs-only` path
- blockers
- closure и cleanup

## Термины

- `ТЗ` — согласованный контракт текущего шага
- `Активный slice` — единственный slice, который сейчас реализуется
- `Implementation stream` — полный цикл текущего шага от preflight до закрытия хвоста
- `Хвост` — незавершённый diff, незапушенная работа, открытый PR, незавершённый CI, deploy, smoke, cleanup или другой обязательный follow-up текущего stream
- `Validated PR` — опубликованный PR текущего stream, по которому `CI` зелёный, выполнен финальный author self-review опубликованного diff, helper-review завершён если он доступен, и в рамках текущего scope не осталось blocker-ов
- `Внешняя публикация` — `push`, создание или обновление PR, `merge`, `deploy`, `migrate` и действия во внешних системах
- `Blocker` — всё, что не даёт надёжно продолжать шаг без отдельного решения пользователя
- `Docs-only stream` — stream, меняющий только разрешённые документальные файлы

## Базовая модель работы

1. Сначала смысл и контракт, потом код.
2. Один активный implementation stream за раз.
3. Новый кодовый шаг не начинается, пока не проверен хвост предыдущего stream.
4. По умолчанию реализация идёт только после read-only анализа и согласованного ТЗ.
5. Если пользователь явно ограничил шаг локальной работой или явно запретил публикацию, действует локальный режим.
6. Если ТЗ согласовано, пользователь дал команду на реализацию и явно не запретил публикацию, normal default для code stream — уровень `PR в staging`.
7. Уровень `PR в staging` доводит шаг до validated PR и не считается staging-verification.
8. Если команда двусмысленна, агент выбирает более безопасный вариант и останавливается на нём.

## Этап 1. Классификация запроса

1. Сначала определить, это read-only запрос или implementation запрос.
2. Если запрос на анализ, review, сравнение вариантов, план или ТЗ, работа остаётся read-only.
3. Если запрос на реализацию, сначала всё равно пройти через анализ и согласование ТЗ.

Результат:
- понятен режим работы по текущему запросу.

## Этап 2. Read-only анализ

1. Изучить текущую реализацию в коде.
2. Найти существующие runtime-path и минимальную безопасную точку изменения.
3. Зафиксировать ограничения, риски и возможный scope drift.
4. На этом этапе ничего не менять.

Результат:
- техническая картина текущего состояния.

## Этап 3. Черновик ТЗ

На основе read-only анализа агент готовит черновик ТЗ текущего stream.

Черновик ТЗ фиксирует:
- цель
- границы
- что меняется и что не меняется
- write-set
- критерии приёмки
- предполагаемую основную среду проверки
- риски и двусмысленности

Если задача потенциально шире одного безопасного шага, это отмечается уже в черновике.

Результат:
- первый рабочий черновик ТЗ по текущему stream.

## Этап 4. Критика ТЗ

Агент обязан критически проверить ТЗ на слабые места по реальному коду и runtime:
- соответствие архитектуре и инвариантам
- наличие нужных runtime-path
- риск scope drift и побочных эффектов
- честность локальной проверки
- не является ли `staging` основной средой проверки
- не нужен ли более сильный уровень делегации

Если найдены слабые места, агент обязан сформулировать их явно.

Результат:
- список замечаний, рисков и слабых мест по черновику ТЗ.

## Этап 5. Финальное ТЗ и slices

После критики агент переписывает ТЗ в финальную версию текущего stream.

Если задача шире одного безопасного шага:
- кратко описать все slices
- подробно описать только активный slice
- не активировать следующий slice, пока не закрыт хвост текущего

Результат:
- финальное ТЗ и понятный активный slice.

## Этап 6. Согласование ТЗ

Перед запуском в работу агент согласует с пользователем:
- финальное ТЗ
- активный slice
- уровень делегации
- нужно ли сохранять ТЗ в `docs/`

Уровни делегации:
- локальный режим
- `PR в staging`
- `через staging`
- `до merge в main`
- dangerous ops

ТЗ по умолчанию фиксируется в чате.
Сохранять ТЗ в `docs/` можно только по явной команде пользователя.

Результат:
- утверждённое ТЗ и понятный уровень делегации для текущего stream.

## Этап 7. Preflight

Preflight делается непосредственно перед запуском stream.

Проверить:
- локальный diff и незапушенные изменения
- активную ветку
- открытые PR
- незавершённый CI
- хвост предыдущего stream
- хватает ли текущего уровня делегации

Если preflight не чистый или делегации недостаточно, агент останавливается.

Результат:
- подтверждено, можно ли запускать текущий stream.

## Этап 8. Запуск stream

Если ТЗ согласовано и preflight чистый:
- начать новый stream с clean branch от `origin/main`, если это новый шаг
- при необходимости сохранить утверждённое ТЗ
- запустить implementation stream в рамках активного slice и согласованного уровня делегации

Результат:
- implementation stream корректно запущен.

## Этап 9. Реализация slice

Агент реализует только активный slice.
Если появляется новая смысловая развилка, нужен следующий шаг от пользователя.
Если локальная проверка не даёт честного сигнала, slice может двигаться дальше до уровня, где доступна основная среда проверки.
Если для проверки нужен более сильный уровень делегации, агент останавливается.

Результат:
- локальный diff по текущему активному slice доведён до честной точки передачи дальше по разрешённой цепочке.

## Этап 10. Self-review и проверки

Author self-review обязателен всегда.
Локальные проверки выполняются только там, где они реально дают честный сигнал.
Для UI-only изменений локальная проверка может быть основной.
Для process logic, jobs, webhook, collector flow, routing, sync и интеграций основной средой проверки считается `staging`, но только после `merge` в ветку `staging`.

Результат:
- diff прошёл обязательный author self-review и доведён до честной точки контроля.

## Этап 11. Helper-review

Для code stream diff дополнительно проходит review двумя вспомогательными агентами, если среда и разрешения это поддерживают.
Helper-review не заменяет author self-review.
Если замечания выходят за scope или требуют более сильной делегации, агент останавливается.

Результат:
- diff прошёл дополнительный review-контур или честно остановлен на blocker.

## Этап 12. Контрольные точки

Контрольные точки обязательны:
- перед первым неразрешённым действием
- перед `merge` в `staging`
- перед `merge` в `main`
- перед dangerous ops
- при blocker, конфликте, scope drift или красном `CI`

На контрольной точке агент обязан показать:
- короткий итог
- что осталось открытым
- короткое меню следующих действий
- одну явную рекомендацию
- краткое `Почему`

Варианты нумеруются.
Формат рекомендации: `Рекомендация: 1. ...`

Правило рекомендации:
1. Если действует локальный режим и `commit` не разрешён, рекомендуемый вариант — `1. Остановиться`.
2. Если действует локальный режим и `commit` разрешён, рекомендуемый вариант — `1. Commit`.
3. Если действует уровень `PR в staging`, рекомендуемый вариант после локальной готовности — `1. Commit + push + draft PR в staging`.
4. Если действует уровень `через staging` и validated PR в `staging` всё ещё draft, рекомендуемый вариант — `1. Перевести PR в ready`.
5. Если действует уровень `через staging` и PR в `staging` уже ready, рекомендуемый вариант — `1. Merge в staging`.
6. Если действует уровень `до merge в main` и `staging smoke` уже зелёный, рекомендуемый вариант зависит от стадии: `1. PR в main`, `1. Перевести PR в ready` или `1. Merge в main`.

Результат:
- пользователь видит честную следующую точку выбора без скрытого расширения полномочий агента.

## Этап 13. Уровень `PR в staging`

Это normal default для code stream после согласованного ТЗ и команды на реализацию, если пользователь явно не запретил публикацию.

Разрешает:
- self-review
- helper-review при доступности
- `commit`
- `push`
- draft PR в `staging`
- `CI`
- исправления в рамках того же scope
- финальный author self-review опубликованного PR после зелёного `CI`
- перевод PR в `ready` только после того, как он стал validated PR

Не разрешает:
- `merge` в `staging`
- staging smoke
- PR в `main`
- `merge` в `main`
- `rebase`
- `force-push`
- `migrate`
- `production deploy`

Готовый PR в `staging` — это публикационная и CI-точка, но не staging-verification.

Результат:
- получен validated PR в `staging`, готовый к отдельному решению о переходе через `staging`.

## Этап 14. Уровень `через staging`

Требует отдельной явной делегации.

Разрешает:
- при необходимости перевести validated PR в `staging` из draft в `ready`
- `merge` в ветку `staging`
- staging deploy-check
- staging smoke
- исправления в том же scope, если staging выявил проблемы

Основная проверка логики процессов и интеграций происходит именно здесь.

Результат:
- текущий validated diff либо успешно прошёл `staging`, либо честно остановлен на blocker.

## Этап 15. Уровень `до merge в main`

Требует отдельной явной делегации и начинается только после успешного прохождения через `staging`.

Разрешает:
- PR в `main` только из validated diff текущего шага, а не из накопленного состояния `staging`
- `CI`
- self-review и helper-review
- исправления в том же scope
- финальный author self-review опубликованного PR после зелёного `CI`
- перевод PR в `main` из draft в `ready` только после того, как он стал validated PR
- `merge` в `main`

`merge` в `main` не включает автоматически `production deploy`.

Результат:
- validated diff доведён до `merge` в `main` в рамках отдельной явной делегации.

## Этап 16. Dangerous ops

К dangerous ops относятся:
- `rebase`
- `force-push`
- любые `migrate`
- `production deploy`

Они всегда требуют отдельного явного разрешения.

Результат:
- операции повышенного риска не смешиваются с обычной delivery-цепочкой.

## Этап 17. Docs-only path

`Docs-only` stream — отдельное исключение и не подчиняется цепочке `staging -> main`.

Допустим только если diff меняет исключительно:
- `AGENTS.md`
- `docs/**`
- `README*.md`
- ТЗ
- другие markdown/текстовые регламенты

И только если stream стартует из clean branch/worktree от `origin/main` без недокументального хвоста в рабочем контексте.

По команде пользователя на документальный путь агент может пройти:
- clean branch/worktree от `origin/main`
- правка документов
- self-review
- `commit`
- `push`
- PR в `main`
- `CI`, если он есть
- финальный self-review
- `ready`
- `merge`
- cleanup

Отсутствие `CI` не блокирует `docs-only` path.

Если в diff появляется недокументальный файл, stream возвращается к обычному workflow.

Результат:
- документальные изменения идут по отдельному честному пути без смешения с code stream.

## Этап 18. Закрытие stream

Stream может быть доведён до разных handoff-точек:
- validated PR в `staging`
- успешное прохождение через `staging`
- `merge` в `main`
- полностью закрытый stream со всеми делегированными follow-up

Handoff-точка — это допустимая точка остановки и следующего решения пользователя, но не автоматически закрытый хвост.

Открытый PR, незавершённый `CI`, незавершённый `staging`/`main` path, deploy, smoke и cleanup остаются хвостом до их фактического завершения.

Новый code stream по умолчанию не начинается, пока этот хвост не закрыт или пользователь явно не разрешил исключение после перечисления хвоста и связанных рисков.

Stream считается полностью закрытым только когда выполнены все follow-up для того уровня, до которого он был делегирован.

Если для текущего release-flow после `merge` в `main` ещё обязателен ручной production deploy и post-deploy smoke, `merge` в `main` остаётся только handoff-точкой, а хвост не считается закрытым до завершения этого post-deploy контура по правилам `docs/post-deploy-smoke.md`.

Результат:
- у stream есть честная точка завершения без путаницы между локальной готовностью, `staging` и `main`.

## Этап 19. Cleanup

После полного закрытия stream агент отдельно предлагает cleanup временных артефактов.

По умолчанию cleanup включает только:
- временные `git worktree`
- временные локальные ветки
- remote-ветки после merge
- временные файлы в `/tmp`
- фоновые процессы этого шага

Cleanup не должен затрагивать:
- пользовательские `untracked` файлы
- незавершённые ветки и worktree
- окружения, доступы и deploy-настройки
- любые артефакты без явного безопасного основания

Потенциально опасный cleanup требует отдельного подтверждения пользователя.

Результат:
- временные артефакты шага убраны без затрагивания пользовательских хвостов.

## Короткая формула workflow

`Запрос -> Классификация -> Read-only анализ -> Черновик ТЗ -> Критика ТЗ -> Финальное ТЗ и slices -> Согласование -> Preflight -> Запуск -> Реализация -> Self-review -> Helper-review -> Контрольная точка -> PR в staging -> Через staging -> До merge в main -> Docs-only path при необходимости -> Closure -> Cleanup`
