# Технология работы над задачами

## Цель документа

Этот документ описывает подробный delivery-playbook для одного implementation stream.

Роли документов разделены так:
- `AGENTS.md` фиксирует верхнеуровневые рамки, инварианты проекта и ограничения по разрешениям
- этот документ описывает пошаговую процедуру внутри этих рамок

Если между документами есть пересечение, `AGENTS.md` задаёт рамки и права,
а `docs/task-delivery-workflow.md` — порядок действий.

## Границы документа

Здесь нет:
- полного проектового описания
- подробной архитектурной карты
- полного domain/config reference
- code style и language rules

Здесь есть только workflow:
- классификация запроса
- read-only анализ
- подготовка и проверка ТЗ
- slices
- preflight
- branch/start rules
- реализация
- локальные проверки
- контрольные точки и разрешения
- `commit/push/PR/CI`
- путь через `staging` и `main`
- `docs-only` path
- blockers
- closure и cleanup

## Термины

- `ТЗ` — согласованный контракт текущего шага
- `Внешнее ТЗ` — versioned ТЗ, которое хранится вне основного репозитория проекта во внешнем репозитории документации
- `Локальный черновик ТЗ` — временное ТЗ для локального режима, которое может жить в чате или в явно указанном локальном месте вне основного репозитория и вне внешнего репозитория документации до операторского решения о выкладке
- `Spec repo` — конкретный внешний репозиторий документации, в котором лежит зафиксированное ТЗ
- `Spec revision` — конкретный commit/hash внешнего ТЗ, на который опирается implementation stream
- `Активный slice` — внутренний инженерный подшаг текущего stream-а; slice может быть меньше пользовательски видимого результата и сам по себе не является trigger-ом выхода в `staging`
- `Локальный MVP` — минимальный локально тестируемый feature increment текущего stream-а; default trigger операторской приёмки, а не автоматического выхода в первый внешний publish-level
- `Implementation stream` — полный цикл текущего шага от preflight до закрытия хвоста
- `Хвост` — незавершённый diff, незапушенная работа, открытый PR, незавершённый CI, deploy, smoke, cleanup или другой обязательный follow-up текущего stream
- `Хвост очистки веток` — незавершённая уборка веток: слитая удалённая ветка, слитая локальная ветка, локальная ветка без отслеживаемой удалённой ветки или устаревший рабочий каталог (`worktree`), оставшиеся после фактического закрытия потока
- `Проверка чистоты веток` — предварительная проверка `Хвоста очистки веток` перед новым потоком разработки кода; проверка требует устранить такой хвост либо явно принять его как временное исключение с перечислением оставшихся веток, рабочих каталогов и рисков
- `Validated PR` — опубликованный PR текущего stream, по которому пользователь подтвердил, что `CI` зелёный и в рамках текущего scope не осталось blocker-ов. Если `CI` красный или неоднозначный, пользователь возвращает задачу агенту для разбора ошибки и исправления.
- `Сторонний ИИ-ревьюер` — Copilot или другой выбранный пользователем ИИ-ревьюер, который не получает выводы самостоятельной проверки агента до завершения собственной проверки.
- `Зафиксированный снимок PR` — точная тройка доказательств: полные `base SHA`, `head SHA` и SHA-256 от UTF-8-байтов строки `title + "\n" + body`, полученной из текущих значений GitHub API без дополнительной нормализации; отсутствующее body считается пустой строкой. Снимок записывается строкой `Review snapshot: base=<sha> head=<sha> metadata=<sha256>`. Изменение base, head, title или body создаёт новый снимок и обнуляет пакет предыдущего.
- `Загрязнённая независимая проверка` — проверка, перед которой проверяющая сторона уже получила выводы другой стороны. Такая проверка не считается независимой и не закрывает пакет.
- `Пакет независимых проверок` — обязательные для code/runtime PR в `staging` и `main` две параллельные незагрязнённые проверки одного зафиксированного снимка PR: самостоятельная проверка агента без предварительного чтения выводов стороннего ИИ-ревьюера и проверка того же снимка сторонним ИИ-ревьюером.
- `Технический вердикт агента по review` — read-only сводное заключение после завершения пакета независимых проверок и чтения всех актуальных review comments/threads: `готово к merge`, `нужны правки` или `нужен выбор пользователя`. Вердикт не является GitHub approve, request changes, dismiss review, переводом статуса или merge.
- `Внешняя публикация` — `push`, создание или обновление PR, `merge`, `deploy`, `migrate`, `staging`, VPS, секреты, smoke внешней среды и действия во внешних системах
- `Publish/release действие` — действие, после которого diff может попасть в shared runtime или внешнюю среду: пользовательский перевод PR в `ready`, `merge`, `deploy`, `migrate`, `staging`, VPS, секреты, smoke внешней среды и действия во внешних системах
- `Spec pending draft PR` — ранний `draft PR` в `staging` для срочного hotfix-а, открытый по согласованному в чате ТЗ до внешней `Spec revision`; он разрешает CI/review, но не разрешает `ready`, `merge`, deploy или smoke
- `Blocker` — всё, что не даёт надёжно продолжать шаг без отдельного решения пользователя
- `Docs-only stream` — stream, меняющий только разрешённые документальные файлы

## Базовая модель работы

1. Сначала смысл и контракт, потом код.
2. Один активный implementation stream за раз.
3. Новый кодовый шаг не начинается, пока не проверен хвост предыдущего stream.
4. `Проверка чистоты веток` является частью проверки хвоста перед новым потоком разработки кода: слитые удалённые и локальные ветки, устаревшие рабочие каталоги (`worktree`) и локальные ветки без отслеживаемой удалённой ветки должны быть либо удалены, либо явно классифицированы как допустимый остаток.
5. По умолчанию реализация идёт только после read-only анализа и согласованного ТЗ.
6. Если пользователь явно ограничил шаг локальной работой или явно запретил публикацию, действует локальный режим.
7. Если ТЗ согласовано, пользователь дал команду на реализацию и явно не запретил публикацию, для нового code stream normal default rollout path: `локальная реализация до локального MVP -> операторская приёмка и решение о выкладке -> фиксация существенного ТЗ во внешнем репозитории документации -> draft PR в staging -> зелёный CI -> пользовательский ready и делегация двух проверок одного снимка PR -> параллельные независимые проверки агента и стороннего ИИ-ревьюера в staging -> сводный вердикт агента -> пользовательский merge в staging -> staging deploy-check -> staging smoke -> staging QA либо явное принятие остаточного риска -> draft PR в main -> зелёный CI -> пользовательский ready и делегация двух проверок одного снимка PR -> параллельные независимые проверки агента и стороннего ИИ-ревьюера в main -> сводный вердикт агента -> пользовательский merge в main -> production deploy -> production smoke`. Для срочного hotfix-а пользователь может отдельно разрешить `Spec pending draft PR` до внешней `Spec revision`.
8. Default trigger после достижения согласованного `Локального MVP` — операторская приёмка локального контура.
9. Команда `реализовать` по умолчанию разрешает агенту вести stream локально до `Локального MVP` и подготовки к операторской приёмке; ближайший внешний publish-level открывается только после явного решения о выкладке.
10. Если пользователь явно решил идти в `staging` раньше или позже операторской приёмки, это фиксируется как override относительно default-правила.
11. Полная локальная реализация всего ТЗ считается допустимым trigger-ом publish-boundary только если оператор или пользователь явно подтвердил готовность к выкладке.
12. Прямой `PR` в `main` для нового code stream запрещён без отдельной явной команды пользователя.
13. Если команда двусмысленна, агент выбирает более безопасный вариант и останавливается на нём.
14. Для существенных stream-ов versioned ТЗ требуется перед первым publish/release действием; до этого локальный режим может идти по согласованному локальному черновику ТЗ. Для срочного hotfix-а допускается ранний `push` ветки и `draft PR` в `staging` как `Spec pending` CI/review-точка, если пользователь явно выбрал этот путь.

## Solo-dev шкала документации

Процесс оптимизирован под одного разработчика и ИИ-агентов. Документ нужен, если
он будет полезен после текущей сессии. Намерение фиксируется в PR, поведение — в
тестах, устройство и повторяемые операции — в `docs/` рядом с кодом.

Уровни работ:

| Уровень | Критерий | Контракт |
| --- | --- | --- |
| `L0` мелочь | не `L2` и не меняет публичный поведенческий контракт | commit message |
| `L1` обычная | меняет код или поведение, но не попадает в `L2` | краткое PR-описание: цель, что меняется, как проверить, риск, стоп-точка |
| `L2` рискованная | миграция БД, deploy/infra, внешняя интеграция, массовые данные/backfill, права/безопасность | decision note в чате/PR body или versioned ТЗ во внешнем spec repo |

Эта шкала определяет размер контракта и доказательств. Она не отменяет delivery
path, `Spec revision`, PR, CI, пользовательский `ready`, пользовательский
`merge`, deploy или smoke gates.

Правило актуальности:

1. любое изменение поведения обновляет или добавляет тест;
2. prose-документация обновляется только если меняется публичный контракт,
   интеграция, runbook, операторский сценарий или правило работы агента;
3. внешняя wiki допустима только как справка для оператора или пользователя, но
   не как инженерный источник истины.

## Локальное воспроизведение интеграций перед staging

Для Bitrix24, Open Lines, Telegram, MAX и других внешних интеграций локальный контур
с подключённой тестовой внешней системой является первым runtime-gate.

Обязательный порядок:

1. Локально воспроизвести проблему на реальном интеграционном path-е или явно зафиксировать, почему это невозможно.
2. Локально написать/обновить автотест, который ловит ошибочный decision path без обращения к внешней системе.
3. Локально исправить код.
4. Локально доказать, что:
   - автотест падает на старом поведении или явно проверяет опасный вызов;
   - автотест проходит на новом поведении;
   - интеграционный сценарий на локальном контуре больше не воспроизводит проблему.
5. Только после этого переходить к PR, CI и `staging` smoke.

`staging` не используется как первая среда воспроизведения, если локальный Bitrix24/dev-контур
доступен и способен проверить сценарий. Если локальный контур не готов или не покрывает нужный
тип побочного эффекта, это считается blocker-ом или явным risk override-ом, который нужно
назвать пользователю до выхода в `staging`.

Для мутирующих интеграционных проверок агент обязан заранее назвать:

1. какие внешние сущности будут затронуты;
2. какой метод или пользовательское действие может создать/изменить данные;
3. как проверить отсутствие лишних побочных эффектов;
4. как очистить тестовые артефакты, если они появятся.

## Приоритет rollout discipline

1. Для нового code stream приоритет у rollout discipline, а не у того, какая ветка ближе к текущему production runtime.
2. Truth текущего runtime нужен для анализа, диагностики и проверки текущего поведения.
3. Truth текущего runtime не даёт агенту права самовольно менять normal default rollout с `staging-first` на `main-first`.
4. Если `main` содержит более свежий runtime-контур, но новый stream ещё не проходил через `staging`, агент обязан:
   - остановиться
   - назвать это process-risk или process-ошибкой
   - запросить явное решение пользователя
5. Staging-first rollout после операторского решения о выкладке сам по себе не делает любой новый code stream существенным stream-ом с обязательным внешним versioned ТЗ.

## Где хранится ТЗ

Для существенного stream-а ТЗ должно стать versioned и жить во внешнем репозитории документации до первого publish/release действия.

До операторского решения о выкладке локальный режим может использовать локальный черновик ТЗ:

1. в чате
2. в явно указанном пользователем локальном месте вне основного репозитория и вне внешнего репозитория документации
3. без записи полного ТЗ в основной репозиторий

Локальный черновик ТЗ не считается достаточным для `ready`, `merge`, `staging`, VPS, секретов, миграций, deploy, smoke внешней среды или действий во внешних системах. Для срочного hotfix-а локальный черновик ТЗ может быть достаточным только для явно разрешённого `Spec pending draft PR` в `staging`.

Основной репозиторий не хранит:

1. полные stream-ТЗ
2. живые указатели на версии ТЗ
3. реестр активных работ
4. историю статусов ТЗ

### Внешнее ТЗ

Перед первым publish/release действием существенного stream-а агент проверяет зафиксированный внешний репозиторий документации:

1. конкретный `Spec repo`
2. `active-streams.md`
3. `streams/README.md`
4. конкретный `Spec doc`
5. конкретный `Spec revision`

Если внешний репозиторий документации недоступен, substantial stream paused перед первым publish/release действием до восстановления доступа. Ранний `Spec pending draft PR` не снимает эту паузу для `ready`, `merge` и deploy-уровней.

### Чего недостаточно

Недостаточно как единственного source of truth:

1. только чата
2. только устной договорённости
3. только ссылки на «последнюю версию документа» без фиксированной revision

## Этап 1. Классификация запроса

1. Сначала определить, это read-only запрос или implementation запрос.
2. Если запрос на анализ, review, сравнение вариантов, план или ТЗ, работа остаётся read-only.
3. Если запрос на реализацию, сначала всё равно пройти через анализ и согласование ТЗ.

Результат:
- понятен режим работы по текущему запросу.

## Этап 2. Read-only анализ

1. Изучить текущую реализацию в коде.
2. Найти существующие runtime-path и минимальную безопасную точку изменения.
3. Зафиксировать ограничения, риски и возможный scope drift.
4. На этом этапе ничего не менять.

Результат:
- техническая картина текущего состояния.

## Этап 3. Черновик ТЗ

На основе read-only анализа агент готовит черновик ТЗ текущего stream.

Черновик ТЗ фиксирует:
- цель
- границы
- что меняется и что не меняется
- затронутую область изменений
- критерии приёмки
- предполагаемую основную среду проверки
- риски и двусмысленности

Если задача потенциально шире одного безопасного шага, это отмечается уже в черновике.

Результат:
- первый рабочий черновик ТЗ по текущему stream.

## Этап 4. Критика ТЗ

Агент обязан критически проверить ТЗ на слабые места по реальному коду и runtime:
- соответствие архитектуре и инвариантам
- наличие нужных runtime-path
- риск scope drift и побочных эффектов
- честность локальной проверки и достаточность локального контура для достижения `Локального MVP` и операторской приёмки
- что именно должно проверяться на `staging` как на confirmatory integration / environment gate, а не как на первой среде, где фича вообще становится тестируемой
- не нужен ли более сильный уровень делегации

Если найдены слабые места, агент обязан сформулировать их явно.

Результат:
- список замечаний, рисков и слабых мест по черновику ТЗ.

## Этап 5. Финальное ТЗ и slices

После критики агент переписывает ТЗ в финальную версию текущего stream.

Если задача шире одного безопасного шага:
- кратко описать все крупные feature-increments или фазы
- подробно описать только активный slice как внутренний инженерный подшаг
- отдельно явно зафиксировать, что считается `Локальным MVP` текущего stream-а
- не активировать следующий крупный increment, пока не закрыт хвост текущего

Результат:
- финальное ТЗ, понятный активный slice и согласованный `Локальный MVP`.

## Этап 6. Согласование ТЗ

Перед запуском в работу агент согласует с пользователем:
- финальное ТЗ
- активный slice
- критерий `Локального MVP`
- уровень делегации
- где зафиксировано текущее ТЗ: чат, локальный черновик вне основного репозитория и вне внешнего репозитория документации или внешнее versioned ТЗ
- если текущий уровень уже включает первое publish/release действие — какие `Spec repo`, `Spec doc` и `Spec revision` являются согласованными

Уровни делегации:
- локальный режим
- `PR в staging`
- `через staging`
- `до merge в main`
- dangerous ops

Для мелких исправлений и коротких локальных действий ТЗ может оставаться в чате.
Для существенных stream-ов в локальном режиме допустим локальный черновик ТЗ до согласованного `Локального MVP` и операторского решения о выкладке, если нет внешней публикации и изменений внешних сред.
Перед первым publish/release действием должно существовать versioned ТЗ в конкретном `Spec repo` на конкретной `Spec revision`.
Для срочного hotfix-а отдельная явная команда пользователя может разрешить ранний `push` ветки и `draft PR` в `staging` как `Spec pending` CI/review-точку до внешней `Spec revision`.
Когда существенный stream впервые выходит на publish/release уровень, его нужно явно зафиксировать во внешнем `active-streams.md`.
По умолчанию согласование нового code stream означает локальную разработку до операторской приёмки, а затем staging-first rollout только после явного решения о выкладке.
Если пользователь хочет идти в `staging` раньше или позже операторской приёмки, это должно быть оговорено отдельно и явно. Для раннего выхода в `staging` агент фиксирует, что именно не принято оператором, почему риск считается допустимым, кто принял риск и какая проверка временно заменяет операторскую приёмку.
По умолчанию это не поднимает execution ceiling выше локального режима до `Локального MVP` и подготовки к операторской приёмке. Фиксация существенного ТЗ во внешнем репозитории документации, `draft PR в staging`, пользовательский `ready`, `staging smoke`, `PR в main`, `production deploy` и `production smoke` требуют отдельного решения пользователя, если иное заранее не согласовано. GitHub-контрольные действия не делегируются агенту: пользователь выполняет их во внешнем UI, агент проверяет результат и следующий checkpoint.
Мелкий публикуемый fix может оставаться на chat-only ТЗ, если stream не признан существенным.
К существенным stream-ам относятся как минимум:
- rollout, заранее делегированный выше уровня `draft PR в staging`
- multi-step implementation
- изменения с runtime/data-flow/delivery риском
- новая интеграционная модель или новый сложный slice внутри интеграции

Результат:
- утверждённое ТЗ и понятный уровень делегации для текущего stream.

## Этап 7. Preflight

Preflight делается непосредственно перед запуском stream.

Проверить:
- локальный diff и незапушенные изменения
- активную ветку
- открытые PR
- незавершённый CI
- хвост предыдущего stream
- хвост очистки веток: слитые удалённые и локальные ветки, устаревшие рабочие каталоги (`worktree`), локальные ветки без отслеживаемой удалённой ветки
- хватает ли текущего уровня делегации

Если preflight не чистый или делегации недостаточно, агент останавливается.

`Хвост очистки веток` не блокирует анализ в режиме только чтения и не блокирует документальное или административное продолжение работы.
Для нового code stream он должен быть закрыт или явно принят пользователем как исключение
после списка конкретных оставшихся веток/worktree и связанных рисков.

Результат:
- подтверждено, можно ли запускать текущий stream.

## Этап 8. Запуск stream

Если ТЗ согласовано и preflight чистый:
- если это новый code stream, первый publish-level branch/worktree создаётся от `origin/staging`
- `origin/main` используется только:
  - для clean PR в `main` после успешного прохождения через `staging`
  - для `docs-only` stream
  - для direct-to-main path, отдельно и явно разрешённого пользователем
- для существенного stream-а в локальном режиме можно стартовать по согласованному локальному черновику ТЗ
- перед первым publish/release действием существенного stream-а зафиксировать `Spec repo`, ссылку на внешнее ТЗ и конкретную `Spec revision`
- для срочного hotfix-а, если пользователь явно выбрал early-draft exception, разрешается ранний `push` ветки и `draft PR` в `staging` со статусом `Spec pending` до внешней `Spec revision`
- для мелкого шага сохранять ТЗ только в чате или как короткий локальный reference-документ при явной договорённости, но не как полный stream-ТЗ в основном репозитории
- запустить implementation stream в рамках активного slice и согласованного уровня делегации

Результат:
- implementation stream корректно запущен.

## Этап 9. Локальная реализация до MVP

Агент реализует активный slice как внутренний инженерный подшаг текущего stream-а.
Отдельный slice может быть слишком мал, чтобы его мог честно проверить пользователь; сам по себе он не считается trigger-ом перехода в `staging`.

По умолчанию stream продолжается локально, пока не выполнено одно из условий:
- достигнут согласованный `Локальный MVP` и фича готова к операторской приёмке
- пользователь или оператор явно решил выйти в `staging` раньше
- обнаружен blocker
- для честной локальной проверки не хватает среды, данных или доступов

Если `Локальный MVP` достигнут и локальный контур закрыт, следующим шагом по умолчанию становится операторская приёмка. Если оператор или пользователь подтвердил готовность к выкладке, следующим внешним publish-level становится фиксация существенного ТЗ во внешнем репозитории документации и `draft PR в staging`.

Перед handoff на операторскую приёмку агент обязан выполнить `runtime identity check` для пользовательского URL, на котором оператор будет проверять MVP:

1. зафиксировать URL проверки;
2. определить обслуживающий процесс, контейнер или dev-server;
3. определить смонтированный каталог или `worktree`, из которого runtime читает код;
4. определить активную ветку и commit внутри runtime;
5. сверить видимый в UI `rev` / version marker с commit текущего stream-а;
6. явно сообщить пользователю URL, ветку, commit, видимый `rev` и результат сверки.

Если runtime marker не совпадает с commit текущего stream-а или runtime identity не удалось доказать, операторская приёмка не считается доступной. Агент останавливается как на blocker-е и предлагает одно из действий: переподнять официальный локальный контур из нужного worktree, поднять отдельный временный URL или зафиксировать, что локальная приёмка невозможна в текущей среде.

Если текущее ТЗ мало и полностью совпадает с одним локально тестируемым feature increment-ом, полная реализация ТЗ допустима как тот же trigger.

Результат:
- локальный diff доведён либо до согласованного `Локального MVP`, либо до честной точки blocker-а или явного handoff к пользователю.

## Этап 10. Review policy по slice-ам

Каждый slice заканчивается обязательным `author self-check`.

`Author self-check` означает:
- проверить, что slice действительно закрывает свой acceptance
- проверить, что diff соответствует активному slice
- проверить, что не появилось scope drift
- проверить, что следующий шаг понятен и честно определён

Перед созданием или обновлением PR author self-check дополнительно включает publish-language check:
- `title`, `body` и человекочитаемые GitHub-комментарии написаны на русском языке
- технические исключения ограничены командами, именами веток, путями файлов, названиями workflow, дословными логами и внешними шаблонами, которые явно требуют английский
- если PR уже создан с нарушением языкового правила, агент исправляет GitHub-описание до следующего delivery checkpoint и не считает checkpoint закрытым, пока описание не приведено к правилам проекта

Полный `formal self-review` выполняется на boundary points, а не после каждого micro-slice.

Boundary point считается наступившим, если slice:
- завершает смысловую единицу
- выводит diff на внешний publish-уровень
- меняет delivery-уровень
- затрагивает рискованный runtime/data-flow/integration контур

Для code stream `formal self-review` обязателен:
- перед внешней публикацией
- для окончательного опубликованного снимка PR до передачи пользователю на
  проверку `CI`

Финальная авторская самопроверка опубликованного `draft` PR проверяет изменения,
заголовок, описание и контрольные поля, а затем фиксирует `Review snapshot`. Она выполняется до или во время
ожидания `CI`, а не отдельным вызовом после зелёного результата. Если `CI`
текущего неизменного снимка зелёный, самопроверка завершена и blocker-ов нет,
пользователь сразу переводит PR в `ready`. Повторная авторская самопроверка
нужна только после изменения `base`, `head`, заголовка или описания либо если проверка
текущего снимка не доказана. Эта авторская проверка не заменяет пакет
независимых проверок после `ready`.

После пользовательского `ready` для code/runtime PR в `staging` и `main`
обязателен пакет независимых проверок зафиксированного снимка PR. По явной команде
пользователя агент сначала самостоятельно проверяет diff и тесты, не читая
выводы стороннего ИИ-ревьюера. Сторонний ИИ-ревьюер параллельно проверяет тот же
снимок. Только после завершения обеих проверок агент читает внешний review и все
актуальные comments/threads и даёт сводный технический вердикт.

Вердикт `готово к merge` допустим только если обе проверки завершены для одного
текущего снимка PR, агенту доступны review status, comments/threads и зелёный
`CI`, актуальный для тех же base/head. Если данные недоступны, неполны или
противоречат друг другу,
агент не использует `готово к merge` и запрашивает недостающие данные или решение
пользователя.

Для docs-only и локальных micro-slice обычно достаточно `author self-check`, если slice не дошёл до boundary point.

Результат:
- каждый slice проходит минимальный контроль
- полный review выполняется в точках, где он реально нужен

## Лестница доказательств

Агент не должен смешивать разные уровни доказательств:

1. чтение кода или документации;
2. статическая проверка или анализ diff;
3. автотест;
4. локальный живой runtime;
5. runtime identity check с URL, worktree, веткой, commit и видимым `rev`;
6. staging/production smoke;
7. операторская или staging QA на затронутом сценарии.

Для provider-матриц и интеграционных claim-ов статус `full` допустим только по
живому payload или подтверждённому provider-событию. Код и тесты доказывают
реализованный decision path, но не заменяют факт живого provider payload.

## Этап 11. Helper-review

Helper-review применяется не после каждого slice, а на boundary points code stream.

Helper-review подключается, если:
- diff уже прошёл `formal self-review`
- slice находится на boundary point
- среда и разрешения позволяют такой review-контур

Helper-review не заменяет `author self-check` и не заменяет `formal self-review`.
Helper-review до `ready` также не заменяет пакет независимых проверок
зафиксированного снимка PR после `ready`.

Результат:
- дополнительный review выполняется в точках повышенного риска и публикации, без лишней бюрократии на micro-slice.

## Этап 11A. Пакет независимых проверок зафиксированного снимка PR

Для каждого code/runtime PR в `staging` и `main` после пользовательского
перевода в `ready` применяется один и тот же порядок:

1. Пользователь передаёт агенту явную команду `готово, проведи независимое
   ревью` или равнозначную по смыслу.
2. Пользователь передаёт PR стороннему ИИ-ревьюеру с требованием до проверки
   самостоятельно зафиксировать и включить в результат строку
   `Review snapshot: base=<sha> head=<sha> metadata=<sha256>`.
3. Агент до начала проверки читает полные `base SHA`, `head SHA`, title и body
   текущего PR, вычисляет SHA-256 по правилу `Зафиксированного снимка PR`, фиксирует в задаче
   `Review snapshot: base=<sha> head=<sha> metadata=<sha256>`, затем
   самостоятельно проверяет diff, тесты, ТЗ и продуктовые инварианты, не
   открывая предварительно выводы, summary и comments стороннего ИИ-ревьюера, и
   фиксирует собственные findings.
4. Сторонний ИИ-ревьюер параллельно проверяет тот же снимок PR, не опираясь на
   выводы агента.
5. После завершения обеих проверок агент читает внешний review, все актуальные
   comments/threads и текущий `CI`, сопоставляет замечания и даёт один сводный
   технический вердикт.

Если внешний review ещё выполняется, агент завершает текущий шаг отчётом о своей
проверке и статусом `внешний review ожидается`, но не даёт сводный вердикт.
После завершения внешней проверки пользователь отдельной командой возвращает
задачу агенту для сопоставления результатов.

Пакет считается закрытым только если:

- обе проверки содержат одинаковую строку `Review snapshot` и относятся к
  одному текущему снимку PR;
- самостоятельная проверка агента завершена до чтения внешних выводов;
- ни одна сторона не получила выводы другой стороны до фиксации собственных
  findings;
- внешний review запущен после пользовательского `ready`; review draft PR
  считается предварительным и не закрывает пакет;
- внешний review завершён и не находится в pending/in-progress состоянии;
- все актуальные review threads доступны агенту;
- `CI`, актуальный для base/head снимка, зелёный.

Изменение `base SHA`, `head SHA`, title или body, включая исправление замечания
или сдвиг целевой ветки, обнуляет пакет. Поток повторяет применимый `CI`; если
base/head изменились, зелёный результат должен быть получен или повторно
запущен для нового снимка. После пользовательского подтверждения результата
пользователь повторно делегирует агенту самостоятельную проверку и передаёт
новый снимок стороннему ИИ-ревьюеру. Затем обе проверки выполняются заново.
Существующий GitHub-статус `ready` сам по себе не сохраняет доказательства
предыдущего снимка.

Если агент уже увидел внешний summary, findings, comments или threads до
фиксации собственных findings, его проверка получает статус `загрязнена` и не
засчитывается. Пользователь делегирует агентскую проверку новой изолированной
задаче/контексту, передавая только URL PR и строку `Review snapshot`, без внешних
выводов. Симметричное правило действует, если сторонний ИИ-ревьюер получил
findings агента: требуется новая внешняя проверка того же снимка.

Если сторонний ИИ-ревьюер недоступен или нельзя доказать совпадение снимка PR, это
blocker технического вердикта, а не основание молча пропустить одну проверку.

Для docs-only/process-only PR пакет не является обязательным, если пользователь
явно не запросил его.

Первый цикл этого правила выполняется вручную. После одного полного ручного
цикла в `staging` и `main` отдельным change оценивается и внедряется исполняемый
guard. Отсутствие guard в первом цикле не делает пакет необязательным.
Существующий `Copilot Merge Readiness Shadow` остаётся advisory-проверкой и сам
по себе не доказывает, что самостоятельная проверка агента выполнена раньше
чтения внешних выводов или что обе проверки относятся к одному снимку PR.

Результат:
- два независимых взгляда относятся к одному неизменному diff;
- сводный вердикт не опирается на устаревший CI или review другого commit.

## Этап 12. Контрольные точки

Контрольные точки обязательны:
- перед первым неразрешённым действием
- после пользовательского подтверждения зелёного `CI` на `draft` PR
- после перевода PR в `ready`
- после завершения обеих независимых проверок зафиксированного снимка PR
- перед `merge` в `staging`
- перед `merge` в `main`
- перед dangerous ops
- при blocker, конфликте, scope drift или красном `CI`

На контрольной точке агент обязан показать:
- короткий итог
- что осталось открытым
- короткое меню следующих действий
- одну явную рекомендацию
- краткое `Почему`

Варианты нумеруются.
Формат рекомендации: `Рекомендация: 1. ...`

Меню обязательно именно здесь, на точке handoff к пользователю.
Вне точки handoff обычные progress updates и commentary идут без меню.
Если нужен один точный ответ без реальных вариантов выбора, агент задаёт один прямой вопрос без меню.

## Этап 12A. Выбор workflow

Перед рекомендацией следующего шага агент сначала определяет, какой workflow
применим к текущему active stream.

Порядок:
1. определить фактически затронутую область изменений текущего stream-а
2. определить тип stream-а: `code stream` или `docs-only`
3. определить, достигнут ли согласованный `Локальный MVP`
4. определить целевой delivery-path текущего stream-а
5. определить, есть ли branch/worktree contamination от более раннего stream-а
6. только после этого выбирать следующий шаг процесса

Правило приоритета:
- текущий active stream важнее истории ветки
- текущая затронутая область изменений важнее прошлого delivery-контура
- `docs-only path` имеет приоритет над обычной цепочкой `staging -> main`,
  если текущий stream удовлетворяет условиям `docs-only`

Если текущий stream является `docs-only`, но рабочая ветка или worktree
содержит историю более раннего stream-а, следующим правильным шагом считается:
1. clean branch/worktree от `origin/main`
2. перенос только текущего `docs-only` diff
3. `draft PR` сразу в `main`

## Выбор базовой ветки и publish-level

1. Новый code stream с runtime/data-flow/integration изменением:
   - локальная реализация от clean worktree/branch на базе `origin/staging`
   - после операторского решения о выкладке и фиксации versioned ТЗ при необходимости первый code publish-level — `draft PR` в `staging`
2. Code stream после успешного `staging` path:
   - clean worktree/branch от `origin/main`
   - отдельный clean PR в `main`
3. `Docs-only` stream:
   - может идти сразу в `main`
4. Direct-to-main code path:
   - допустим только по отдельной явной команде пользователя

## Этап 12B. AB Readiness Check

Перед пользовательским переводом PR из `draft` в `ready` используется `ab-readiness-check`.

Назначение проверки:
- показать, заполнены ли обязательные readiness-поля PR
- подсветить незакрытые условия `Локального MVP`, операторской приёмки, self-check, блокеров и принятого риска
- отделить pre-ready gate от `release-process-guard`, который защищает язык PR, staging-first и validated diff

На `draft` PR незакрытые readiness-поля отображаются как warnings и не означают готовность к `ready`.
После события `ready_for_review` те же незакрытые readiness-поля становятся blocker-ами.
Проверка не переводит PR в `ready`, не запускает `merge` и не заменяет явную команду пользователя.

## Этап 12C. Машинно-читаемое описание PR

Описание PR должно быть одновременно понятным человеку и машинно-читаемым
для `ab-readiness-check` / `release-process-guard`.

Агент не должен заменять обязательные guard-поля свободной прозой. Если guard
ожидает конкретную строку или конкретное значение поля, это значение нужно
вставлять буквально.

Перед созданием PR и перед handoff пользователю агент обязан проверить:

- русские заголовки разделов PR body, например `## Что изменено` и `## Проверки`
- отсутствие англоязычной prose вне технических токенов
- наличие всех readiness-полей
- допустимые значения readiness-полей
- для runtime/code PR в `main` после `staging` — точные строки `Staging PR:` /
  `Staging PRs:` и `Staging smoke:`

Допустимые readiness-значения перед `ready`:

- `Тип изменения: кодовое | документационное | процессное | hotfix`
- `Существенный stream: да | нет`
- `Уровень доставки: PR в staging | через staging | до merge в main | документационный путь`
- `Локальный MVP: принят | не требуется`
- `Операторская приёмка: принята | не требуется`
- `Авторская самопроверка: выполнена`
- `Связанные задачи: не требуется | #NNN | #NNN, #MMM` — positive unique IDs, separator `, `.
- `Основание связи: <профильная причина>` — для Issue обязательно; иначе пусто/`не требуется`.
- `Блокеры: отсутствуют`
- `Принятый риск: отсутствует | принят: <краткая причина>`

Недопустимо:

- `Локальный MVP: выполнен локально`
- `Операторская приёмка: принята для test-only PR после зелёного staging smoke`
- `Staging PR #639 смёржен в staging`
- `Staging smoke #583 прошёл зелёным`

Правильно:

```text
Staging PR: #639
Staging smoke: https://github.com/Etogerman/Project-1/actions/runs/28181486011

Локальный MVP: принят
Операторская приёмка: принята
```

Для нескольких staging PR:

```text
Staging PRs: #614, #615
Staging smoke: https://github.com/Etogerman/Project-1/actions/runs/123
```

Если PR уже создан, агент не должен отдавать его как готовый checkpoint, пока
быстрые process-guards (`ab-readiness-check`, `release-process-guard`) не
подтвердили, что PR body распознан. Красный process-guard из-за title/body
чинится правкой PR-описания без изменения code diff.

Правило рекомендации:

Правила читаются сверху вниз; закрытые checkpoints пропускаются, publish-шаги
ждут зафиксированного операторского решения о выкладке.

Для docs-only/process-only PR до merge применяется только `Этап 17. Docs-only
path`; правила 1–23 ниже не переносят на него code/runtime-цепочку. После merge
или закрытия без merge применяются правила 24–28.

1. Пока согласованный `Локальный MVP` не достигнут и blocker-ов нет, рекомендуемый вариант — `1. Продолжить локальную реализацию`.
2. Если `Локальный MVP` достигнут, локальный контур закрыт, но операторское решение о выкладке ещё не зафиксировано, рекомендуемый вариант — `1. Провести операторскую приёмку`.
3. Если оператор подтвердил готовность к выкладке, а существенное ТЗ ещё не опубликовано во внешнем репозитории документации, рекомендуемый вариант — `1. Зафиксировать Spec repo / Spec doc / Spec revision`. Для срочного hotfix-а по отдельной явной команде пользователя допустимый вариант — `1. Commit + push + draft PR в staging со статусом Spec pending`.
4. Если оператор подтвердил готовность к выкладке, versioned ТЗ уже зафиксировано при необходимости, но текущая делегация не разрешает `commit`/`push`/PR, рекомендуемый вариант — `1. Остановиться на publish-boundary`.
5. Если действует уровень `PR в staging`, оператор подтвердил готовность к выкладке и versioned ТЗ зафиксировано при необходимости, рекомендуемый вариант после локальной готовности — `1. Commit + push + draft PR в staging`.
6. Если для code/runtime PR действует уровень `PR в staging` и `draft` PR ждёт CI, рекомендуемый вариант — `1. Пользователь проверяет CI; при зелёном результате того же самопроверенного снимка переходит сразу к Ready, при ошибке возвращает задачу агенту для исправления`.
7. Если для code/runtime PR действует уровень `PR в staging`, CI зелёный, но авторская самопроверка текущего снимка отсутствует или снимок после неё изменился, рекомендуемый вариант — `1. Агент выполняет авторскую самопроверку текущего снимка PR`; зелёный CI сам по себе повторной проверки не требует.
8. Если для code/runtime PR действует уровень `через staging`, CI зелёный и авторская самопроверка завершена, но PR всё ещё `draft`, рекомендуемый вариант — `1. Пользователь переводит PR в ready, пишет агенту "готово, проведи независимое ревью" и передаёт PR стороннему ИИ-ревьюеру с требованием самостоятельно зафиксировать строку Review snapshot`.
9. Если для code/runtime PR действует уровень `через staging`, PR уже `ready`, но текущий снимок PR изменился после предыдущей делегации либо его CI ещё не подтверждён пользователем, рекомендуемый вариант — `1. Пользователь проверяет CI текущего снимка, повторно пишет "готово, проведи независимое ревью" и передаёт тот же снимок стороннему ИИ-ревьюеру`.
10. Если для code/runtime PR действует уровень `через staging`, текущий снимок PR явно делегирован обеим сторонам, но пакет независимых проверок ещё не закрыт, рекомендуемый вариант — `1. Агент и сторонний ИИ-ревьюер параллельно и независимо проверяют один снимок PR`.
11. Если для code/runtime PR действует уровень `через staging`, обе незагрязнённые независимые проверки одного текущего снимка PR завершены, агенту доступны внешний review, comments/threads и актуальный зелёный CI, но сводный вердикт ещё не дан, рекомендуемый вариант — `1. Агент сопоставляет обе проверки и даёт сводный технический вердикт`.
12. Если для code/runtime PR действует уровень `через staging`, сводный вердикт агента — `готово к merge`, рекомендуемый вариант — `1. Пользователь выполняет merge в staging, агент затем проверяет результат`.
13. Если для code/runtime PR действует уровень `до merge в main`, `staging deploy-check` и `staging smoke` закрыты, а `staging QA` подтверждён либо пользователь явно принял остаточный риск, рекомендуемый вариант до публикации — `1. Commit + push + draft PR в main`.
14. Если для code/runtime PR действует уровень `до merge в main` и `draft` PR в `main` ждёт CI, рекомендуемый вариант — `1. Пользователь проверяет CI; при зелёном результате того же самопроверенного снимка переходит сразу к Ready, при ошибке возвращает задачу агенту для исправления`.
15. Если для code/runtime PR действует уровень `до merge в main`, CI зелёный, но авторская самопроверка текущего снимка отсутствует или снимок после неё изменился, рекомендуемый вариант — `1. Агент выполняет авторскую самопроверку текущего снимка PR`; зелёный CI сам по себе повторной проверки не требует.
16. Если для code/runtime PR действует уровень `до merge в main`, CI зелёный и авторская самопроверка завершена, но PR всё ещё `draft`, рекомендуемый вариант — `1. Пользователь переводит PR в ready, пишет агенту "готово, проведи независимое ревью" и передаёт PR стороннему ИИ-ревьюеру с требованием самостоятельно зафиксировать строку Review snapshot`.
17. Если для code/runtime PR действует уровень `до merge в main`, PR уже `ready`, но текущий снимок PR изменился после предыдущей делегации либо его CI ещё не подтверждён пользователем, рекомендуемый вариант — `1. Пользователь проверяет CI текущего снимка, повторно пишет "готово, проведи независимое ревью" и передаёт тот же снимок стороннему ИИ-ревьюеру`.
18. Если для code/runtime PR действует уровень `до merge в main`, текущий снимок PR явно делегирован обеим сторонам, но пакет независимых проверок ещё не закрыт, рекомендуемый вариант — `1. Агент и сторонний ИИ-ревьюер параллельно и независимо проверяют один снимок PR`.
19. Если для code/runtime PR действует уровень `до merge в main`, обе незагрязнённые независимые проверки одного текущего снимка PR завершены, агенту доступны внешний review, comments/threads и актуальный зелёный CI, но сводный вердикт ещё не дан, рекомендуемый вариант — `1. Агент сопоставляет обе проверки и даёт сводный технический вердикт`.
20. Если для code/runtime PR действует уровень `до merge в main`, сводный вердикт агента — `готово к merge`, рекомендуемый вариант — `1. Пользователь выполняет merge в main, агент затем проверяет результат`.
21. Если `merge` в `main` уже выполнен для code/release stream, рекомендуемый вариант — `1. Ручной production deploy`.
22. Если ручной production deploy уже выполнен для code/release stream, рекомендуемый вариант — `1. Production Post-Deploy Smoke`.
23. Success production smoke без принятия результата/риска -> `1. Пользователь или оператор принимает результат/риск`.
24. Merged docs/process PR без проверки результата -> `1. Агент проверяет merged result`.
25. Нет materialized result, terminal outcome не выбран -> `1. Пользователь выбирает cancelled | deferred | closed_without_merge`.
26. На выбранном route `Issue Closure` pending -> `1. Пройти Issue Closure`.
27. Issue закрыт, `Spec Closure` pending -> `1. Пройти Spec Closure`.
28. Оба checkpoint закрыты, cleanup pending -> `1. Cleanup`; до него только docs/spec/admin follow-up.

Если сводный вердикт агента — `нужны правки`, следующим шагом считается
исправление в текущем scope. Агент не переводит PR обратно в draft и не меняет
GitHub-статус; после fix commit/push формируется новый снимок PR и проходит
применимый CI, затем пользователь подтверждает результат и явно делегирует обе
проверки. После этого
повторяются самостоятельная проверка агента, проверка стороннего ИИ-ревьюера и
сводный технический вердикт перед пользовательским merge. Если вердикт —
`нужен выбор пользователя`, агент показывает риск и запрашивает решение
пользователя.

Если одна из независимых проверок отсутствует, относится к другому снимку PR,
загрязнена либо review status, comments/threads или CI status недоступны или неоднозначны,
следующий шаг — получить недостающие данные или решение пользователя, а не
рекомендовать merge.

Правило следующего шага процесса:
1. Правило следующего шага процесса имеет приоритет над локальной паузой на контрольной точке.
2. Если пользователь спрашивает о следующем логичном и правильном шаге, агент обязан назвать следующий delivery-уровень или следующий process-step.
3. Если текущая контрольная точка закрыта, acceptance выполнен и blocker-ов нет, агент рекомендует именно следующий шаг процесса, а не паузу.
4. Если следующий шаг требует отдельной делегации, это указывается отдельно и не заменяет собой рекомендацию следующего шага.
5. Если следующий шаг является GitHub-контрольным или внешним статусным действием, например пользовательский перевод PR в `Ready for review`, пользовательский approve/request changes, пользовательский merge, manual deploy button или подтверждение environment, основной рекомендуемый вариант — пользователь выполняет ручное действие. Если после этого нужен технический check, агент выполняет его только как отдельный проверочный шаг, а не как замену следующего GitHub-контрольного действия.
6. Агент не предлагает себя исполнителем GitHub-контрольных действий. В меню такие пункты помечаются как `[вы]` или `[вы -> я]`, где агент выполняет только последующую проверку.
7. Формулировка `Остановиться на контрольной точке` используется как рекомендация только если:
   - есть blocker
   - acceptance текущей точки не закрыт
   - следующий шаг выходит за согласованный execution ceiling
   - пользователь сам хочет паузу
8. Для AB Connector после `merge` в `main` следующим шагом процесса считается `Ручной production deploy`, если текущий stream является code/release stream.
9. После production deploy следующим шагом процесса считается `Production Post-Deploy Smoke`, если текущий stream является code/release stream.
10. Статус dangerous op ограничивает исполнение, но не подменяет собой рекомендацию следующего шага процесса.

Результат:
- пользователь видит честную следующую точку выбора без скрытого расширения полномочий агента.

## Этап 13. Уровень `PR в staging`

Это normal default code publish-level для code stream после достижения согласованного `Локального MVP`, операторского решения о выкладке и фиксации versioned ТЗ при необходимости, если пользователь явно не запретил публикацию.

Разрешает:
- self-review до создания PR; после создания PR — только по отдельной команде пользователя
- helper-review при доступности; после создания PR — только по отдельной команде пользователя
- `commit`
- `push`
- draft PR в `staging`
- `CI`
- исправления в рамках того же scope

Не разрешает:
- автоматическое ожидание `CI` после создания PR без отдельной команды пользователя
- самостоятельное ревью PR агентом после создания PR без отдельной команды пользователя
- пользовательский перевод PR в `ready`
- `merge` в `staging`
- staging smoke
- PR в `main`
- `merge` в `main`
- `rebase`
- `force-push`
- `migrate`
- `production deploy`

Готовый PR в `staging` — это публикационная и CI-точка, но не staging-verification.

Результат:
- создан `draft` PR в `staging`
- агент выполнил авторскую самопроверку окончательного опубликованного снимка и
  сообщил ссылку на PR, целевую ветку, статус `draft/ready` и `Review snapshot`
- далее пользователь проверяет `CI`: зелёный результат неизменного снимка ведёт
  сразу к пользовательскому `ready`, красный или неоднозначный результат
  возвращает задачу агенту; проверка стороннего ИИ-ревьюера на `draft` считается
  только предварительной и не закрывает пакет после `ready`.

## Этап 14. Уровень `через staging`

Требует отдельной явной делегации.

`Staging` используется как confirmatory integration / environment gate.
Он не должен быть местом, где фича впервые становится тестируемой; к моменту выхода на `staging` основной пользовательский сценарий уже должен быть честно проверяем локально хотя бы на уровне согласованного `Локального MVP` и принят оператором к выкладке.

Разрешает:
- при необходимости пользователь переводит validated PR в `staging` из draft в `ready`
- отдельную контрольную точку после перевода PR в `ready`
- самостоятельную проверку агента и проверку стороннего ИИ-ревьюера одного
  зафиксированного снимка PR параллельно после пользовательского `ready`
- сводный технический вердикт агента после завершения обеих незагрязнённых
  проверок и чтения всех актуальных comments/threads и `CI` того же снимка PR
- handoff на пользовательский `merge` в ветку `staging`
- staging deploy-check
- staging smoke
- staging QA на живом staging-контуре для затронутых пользовательских и интеграционных сценариев
- исправления в том же scope, если staging выявил проблемы

Основная confirmatory-проверка логики процессов и интеграций на средовом контуре происходит именно здесь. Автоматический staging smoke подтверждает базовую работоспособность окружения и rev, но не заменяет staging QA для затронутых runtime-сценариев.

Результат:
- текущий validated diff либо успешно прошёл `staging` через deploy-check, staging smoke и staging QA, либо честно остановлен на blocker.

## Этап 15. Уровень `до merge в main`

Требует отдельной явной делегации и начинается только после успешного прохождения через `staging`: deploy-check, staging smoke и staging QA должны быть закрыты, если пользователь явно не принял остаточный риск.

Это не `merge staging -> main`.
`PR` в `main` не открывается из накопленного состояния `staging`; источник этого шага — только `validated diff` текущего active stream.

Разрешает:
- draft PR в `main` только из validated diff текущего шага, а не из накопленного состояния `staging`
- `CI`
- авторская и вспомогательная проверки до создания PR
- исправления в том же scope
- финальную авторскую самопроверку окончательного опубликованного снимка до передачи
  пользователю на проверку `CI`
- прямой пользовательский переход к `ready`, если `CI` того же снимка зелёный;
  отдельный повторный вызов агента не требуется
- пользовательский перевод PR в `main` из draft в `ready` только после того, как он стал validated PR
- отдельную контрольную точку после перевода PR в `ready`
- самостоятельную проверку агента и проверку стороннего ИИ-ревьюера одного
  зафиксированного снимка PR параллельно после пользовательского `ready`
- сводный технический вердикт агента после завершения обеих незагрязнённых
  проверок и чтения всех актуальных comments/threads и `CI` того же снимка PR
- handoff на пользовательский `merge` в `main`

### Частая ошибка

Неправильно:
- после успешного прохождения через `staging` описывать следующий шаг как `staging -> main`
- открывать `PR` в `main` из накопленного состояния ветки `staging`

Правильно:
- после успешного этапа `через staging` открывать отдельный `draft PR` в `main`
- строить этот `PR` только из `validated diff` текущего active stream
- в body `main` PR вставлять staging-доказательства в точном формате:

```text
Staging PR: #NNN
Staging smoke: https://github.com/<owner>/<repo>/actions/runs/<run-id>
```

- если staging-доказательств несколько, использовать `Staging PRs: #NNN, #MMM`

Для AB Connector после `merge` в `main` следующим шагом release-flow считается `Ручной production deploy` только для code/release stream.

Результат:
- validated diff доведён пользователем до `merge` в `main` и передан в production handoff.

### Короткая таблица переходов

| Текущий уровень | Следующий правильный уровень |
| --- | --- |
| `PR в staging` | `через staging` |
| `через staging` | `до merge в main` |
| `до merge в main` | `Ручной production deploy` |
| `Ручной production deploy` | `Production Post-Deploy Smoke` |
| `Production Post-Deploy Smoke` | `Принятие результата -> Issue Closure -> применимый Spec Closure -> Cleanup` |

## Этап 16. Dangerous ops

К dangerous ops относятся:
- `rebase`
- `force-push`
- любые `migrate`
- `production deploy`

Они всегда требуют отдельного явного разрешения.

Результат:
- операции повышенного риска не смешиваются с обычной delivery-цепочкой.

## Этап 17. Docs-only path

`Docs-only` stream — отдельное исключение и не подчиняется цепочке `staging -> main`.

Допустим только если diff меняет исключительно:
- `AGENTS.md`
- `docs/**`
- `README*.md`
- другие markdown/текстовые регламенты

И только если stream стартует из clean branch/worktree от `origin/main` без недокументального хвоста в рабочем контексте.

Для `docs-only` slice рекомендация следующего шага строится по `docs-only path`,
а не по предыдущему code stream.

Если текущая ветка или worktree содержит историю более раннего stream-а,
агент рекомендует не публикацию этой истории как есть, а clean branch/worktree
от `origin/main` с переносом только текущего `docs-only` slice.

По команде пользователя на документальный путь агент может пройти:
- clean branch/worktree от `origin/main`
- правка документов
- self-review
- `commit`
- `push`
- PR в `main`
- финальную авторскую самопроверку окончательного опубликованного снимка агент выполняет
  до передачи пользователю на проверку PR и `CI`
- дальше пользователь проверяет PR самостоятельно или с помощью Copilot / другого ревьюера
- `CI` проверяет пользователь; если есть ошибки, он возвращает задачу агенту
- если `CI` зелёный и снимок не изменился, пользователь сразу переводит PR в
  `ready`; промежуточный вызов агента до `ready` не требуется
- после `ready` применимые проверки GitHub и выбранная проверка выполняются без
  автоматического возврата текущей задачи Codex агенту
- когда проверки завершились, пользователь передаёт задачу агенту короткой
  командой `готово, проверь PR`; если применимых проверок нет, команда
  отправляется сразу после `ready`
- до этой команды ответственность за следующий переход остаётся у пользователя;
  после команды — у агента
- агент проверяет актуальное состояние текущего снимка PR, `CI`, выбранной
  проверки и всех комментариев и обсуждений, затем даёт технический вердикт
- `ready` и `merge` выполняет только пользователь; после вердикта
  `готово к merge` пользователь выполняет `merge`
- после merge/closed-without-merge пройти применимый route Этапа 18, затем cleanup

Отсутствие `CI` не блокирует `docs-only` path.

Если в diff появляется недокументальный файл, stream возвращается к обычному workflow.

Результат:
- документальные изменения идут по отдельному честному пути без смешения с code stream.

## Ссылки на ТЗ в implementation stream

Для любого существенного implementation stream агент должен уметь ответить на три вопроса по текущей стадии:

1. Где зафиксировано текущее ТЗ: чат, локальный черновик вне основного репозитория и вне внешнего репозитория документации или внешний `Spec doc`?
2. Текущая стадия ещё локальная, находится на `Spec pending draft PR` или уже дошла до первого publish/release действия?
3. Если стадия дошла до первого publish/release действия, какая именно `Spec revision` является согласованной и где это зафиксировано?

Минимально допустимые места фиксации для локального режима:

1. текущий чат
2. явно указанное пользователем локальное место вне основного репозитория и вне внешнего репозитория документации

Минимально обязательная фиксация для первого publish/release действия существенного stream-а:

1. внешний `Spec doc` в согласованном `Spec repo`
2. конкретная `Spec revision`
3. запись во внешнем `active-streams.md`, если stream реально открыт как существенный

Описание PR, рабочий implementation summary и task tracker могут дублировать ссылки на `Spec repo`, `Spec doc` и `Spec revision`, но не заменяют внешний versioned `Spec doc`.

Если PR делается по внешнему ТЗ, в описании PR должен быть блок вида:

- `Spec repo:` `<repo-or-location>`
- `Spec doc:` `<path-or-doc-name>`
- `Spec revision:` `<commit-hash>`

`Spec repo` в PR-описании указывает только внешний репозиторий документации и не создаёт живой реестр в основном проекте.

## Этап 18. Закрытие stream

Stream может быть доведён до разных handoff-точек:
- validated PR в `staging`
- успешное прохождение через `staging`
- `merge` в `main`
- полностью закрытый stream со всеми делегированными follow-up

Handoff-точка — это допустимая точка остановки и следующего решения пользователя, но не автоматически закрытый хвост.

Открытый PR, незавершённый `CI`, незавершённый `staging`/`main` path, deploy, smoke и cleanup остаются хвостом до их фактического завершения.

Новый code stream по умолчанию не начинается, пока этот хвост не закрыт или пользователь явно не разрешил исключение после перечисления хвоста и связанных рисков.

Stream считается полностью закрытым только когда выполнены все follow-up для того уровня, до которого он был делегирован.

Полное закрытие включает `Issue Closure` и применимый `Spec Closure` как для
result-route, так и для no-result terminal-route.

Нужно различать четыре типа хвоста:

1. runtime/release tail: открытый PR, незавершённый `CI`, незавершённый `staging`/`main` path, deploy и smoke; это жёсткие blockers
2. хвост очистки веток: слитые удалённые и локальные ветки, устаревшие рабочие каталоги (`worktree`) и локальные ветки без отслеживаемой удалённой ветки; это обязательная проверка перед новым потоком разработки кода
3. issue/admin tail: Issue, оставленная открытой после основания закрытия; видимый, но неблокирующий после cleanup follow-up
4. spec/admin tail: `Spec doc` status, `streams/README.md`, запись в `active-streams.md`, `archive pending`; это обязательные follow-up, но не отдельный rollout gate сами по себе

### Issue Closure Checklist

Основание закрытия: принятый production-результат/риск для code/release либо
проверенный merged result для docs/process.

1. `Связанные задачи: не требуется` даёт `Issue Closure: not_required`.
   Closing reference/keyword в PR или commit блокирует pre-merge verdict.
2. Для `#NNN` агент сверяет live state; пользователь выполняет close/reopen и
   пишет на merged PR `Issue Closure: completed` и по строке
   `Issue #NNN: closed | left_open`.
3. Несовпадение record/live state означает pending; `left_open` создаёт
   неблокирующий после cleanup `issue/admin tail`.

### Spec Closure Checklist

На result-route для неприменимого Spec на merged PR нужны
`Spec Closure: not_required` и `Spec Closure reason: <причина>`; иначе pending.
Для применимого Spec:

1. сверить фактический runtime / validated diff / acceptance с внешним `Spec doc`
2. обновить статус в самом `Spec doc`, если документ всё ещё содержит собственный статусный блок
3. обновить каноническую запись во внешнем `streams/README.md`
4. синхронизировать внешний `active-streams.md`: оставить там только реально открытые существенные stream-ы, а закрытую запись удалить или заменить актуальной
5. если перенос документа в `archive/` не делается в том же шаге, явно оставить документ в состоянии `implemented` с отдельным follow-up `archive pending`

Spec write, commit и push — отдельные разрешения по `ab-spec-workflow`.

### No-result terminal-route

`Materialized result` существует, если текущий diff/эквивалент полностью либо
частично смёржен в целевую, интеграционную или иную delivery-ветку, активирован в
shared runtime либо опубликован для использования вне временного review evidence.
Unmerged PR, remote head/feature branch, CI/review artifacts и локальный worktree
сами по себе являются evidence попытки, а не materialized result. Если такая
ветка фактически обслуживает shared runtime или используется как опубликованный
результат, no-result запрещён.

Маршрут требует read-only доказательства отсутствия materialized result и
пользовательского `cancelled | deferred | closed_without_merge`. Любая
materialization переводит в result-route, rollback или forward-fix. До cleanup
фиксируются:

```text
Terminal outcome: cancelled | deferred | closed_without_merge
Terminal reason: <краткая причина>
```

- Каждый `#NNN`: пользователь фиксирует `Issue Closure: completed`,
  `Issue Closure reason: terminal_without_materialized_result` и
  `Issue #NNN: closed | left_open`; `не требуется`:
  `Issue Closure: not_required` плюс непустая `Issue Closure reason`.
- Применимый Spec -> фактический `planned | partial | archived`, после commit
  `Spec Closure: completed` + revision; неприменимый -> `not_required` + reason.
- Record: closed PR; без PR — применимый Spec audit или локальный handoff. Новый
  Spec ради отмены не создаётся; Spec write/commit/push разрешаются отдельно.
- Cleanup ждёт оба checkpoint; `completed` закрывает attempt, не acceptance.
  `Deferred` branch/worktree — dormant tail с owner/checkpoint, не cleanup;
  новый substantial stream требует exception.
- Outcome, close/reopen и Issue-решения выполняет пользователь.

Статус `planned` для уже материализованного acceptance считается process-error и не является допустимым состоянием закрытия stream-а.
Незакрытый `spec/admin tail` нужно явно перечислять перед стартом нового substantial code stream-а, но он сам по себе не запрещает unrelated `docs-only` шаг или малый локальный maintenance step.

Result-route: production acceptance либо проверенный merged docs/process result
-> `Issue Closure` -> `Spec Closure` -> cleanup. Без materialized result —
terminal-route выше. Оба checkpoint должны быть `completed | not_required`.

Результат:
- у stream есть честная точка завершения без путаницы между локальной готовностью, `staging` и `main`.

## Этап 19. Cleanup

После обоих checkpoint агент предлагает cleanup; только он закрывает stream.
Ручные действия требуют checkpoint, GitHub auto-delete их не заменяет.
Если stream дошёл до `merge`, branch cleanup является обязательным closure-подшагом:
агент должен показать конкретный dry-run список и выполнить удаление только после
явного подтверждения пользователя, если удаление затрагивает remote branch,
локальную ветку без upstream или любой неоднозначный артефакт.

По умолчанию cleanup включает только:
- временные `git worktree`
- временные локальные ветки
- remote-ветки после merge
- временные файлы в `/tmp`
- фоновые процессы этого шага

Branch cleanup checklist:

1. проверить, что по ветке нет открытого PR
2. проверить merge либо terminal record и оба checkpoint для closed-without-merge PR
3. проверить, что branch не является `main`, `staging`, активным stream-ом или явно сохранённым backup
4. после merge удалить remote branch по команде/подтвердить auto-delete; после closed-without-merge пользователь удаляет branch либо сохраняет dormant tail
5. удалить соответствующую локальную ветку после сохранения нужного upstream/history
6. выполнить prune локальных remote-tracking ссылок
7. повторно показать короткий статус: что удалено, что оставлено и почему

Агент может удалять remote head branch только как cleanup уже закрытого PR после
явной команды пользователя. Перед удалением агент проверяет, что PR имеет статус
`MERGED`, remote branch соответствует head branch этого PR, branch не является
`main`, `staging`, защищённой веткой, активным stream-ом или backup-веткой, и по
branch нет другого открытого PR. Если любой из этих признаков нельзя подтвердить
read-only проверкой, агент не удаляет remote branch и показывает blocker.
PR, закрытый без merge и без terminal-route, считается blocker-ом branch cleanup для агента: агент
показывает blocker и ждёт действия пользователя, а remote branch удаляет только
пользователь.

Для репозитория GitHub настройка автоматического удаления head branches после merge
должна быть включена, если это не конфликтует с текущей политикой проекта. Даже при
включённой настройке `Проверка чистоты веток` остаётся обязательной: она выявляет
локальные ветки, устаревшие рабочие каталоги (`worktree`), резервные исключения
и оставшиеся удалённые ветки.

Cleanup не должен затрагивать:
- пользовательские `untracked` файлы
- незавершённые ветки и worktree
- окружения, доступы и deploy-настройки
- любые артефакты без явного безопасного основания

Потенциально опасный cleanup требует отдельного подтверждения пользователя.

Результат:
- временные артефакты шага убраны без затрагивания пользовательских хвостов.

## Короткая формула workflow

`Запрос -> Классификация -> Read-only анализ -> Черновик ТЗ -> Критика ТЗ -> Финальное ТЗ и slices -> Согласование -> Preflight -> Запуск -> Реализация -> Self-review -> Helper-review -> Локальный MVP -> Операторская приёмка -> Фиксация внешнего ТЗ при необходимости -> PR в staging -> Пакет независимых проверок снимка PR -> Через staging -> PR в main -> Пакет независимых проверок снимка PR -> До merge в main -> Docs-only path при необходимости -> Closure -> Cleanup`
