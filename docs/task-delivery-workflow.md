# Технология работы над задачами

## Цель документа

Этот документ описывает подробный delivery-playbook для одного implementation stream.

Роли документов разделены так:
- `AGENTS.md` фиксирует верхнеуровневые рамки, инварианты проекта и ограничения по разрешениям
- этот документ описывает пошаговую процедуру внутри этих рамок

Если между документами есть пересечение, `AGENTS.md` задаёт рамки и права,
а `docs/task-delivery-workflow.md` — порядок действий.

## Границы документа

Здесь нет:
- полного проектового описания
- подробной архитектурной карты
- полного domain/config reference
- code style и language rules

Здесь есть только workflow:
- классификация запроса
- read-only анализ
- подготовка и проверка ТЗ
- slices
- preflight
- branch/start rules
- реализация
- локальные проверки
- контрольные точки и разрешения
- `commit/push/PR/CI`
- путь через `staging` и `main`
- `docs-only` path
- blockers
- closure и cleanup

## Термины

- `ТЗ` — согласованный контракт текущего шага
- `Внешнее ТЗ` — versioned ТЗ, которое хранится вне основного репозитория проекта во внешнем репозитории документации
- `Spec repo` — конкретный внешний репозиторий документации, в котором лежит зафиксированное ТЗ
- `Spec revision` — конкретный commit/hash внешнего ТЗ, на который опирается implementation stream
- `Активный slice` — внутренний инженерный подшаг текущего stream-а; slice может быть меньше пользовательски видимого результата и сам по себе не является trigger-ом выхода в `staging`
- `Локальный MVP` — минимальный локально тестируемый feature increment текущего stream-а; default trigger перехода из локалки в первый внешний publish-level
- `Implementation stream` — полный цикл текущего шага от preflight до закрытия хвоста
- `Хвост` — незавершённый diff, незапушенная работа, открытый PR, незавершённый CI, deploy, smoke, cleanup или другой обязательный follow-up текущего stream
- `Validated PR` — опубликованный PR текущего stream, по которому `CI` зелёный, выполнен финальный author self-review опубликованного diff, helper-review завершён если он доступен, и в рамках текущего scope не осталось blocker-ов
- `Внешняя публикация` — `push`, создание или обновление PR, `merge`, `deploy`, `migrate` и действия во внешних системах
- `Blocker` — всё, что не даёт надёжно продолжать шаг без отдельного решения пользователя
- `Docs-only stream` — stream, меняющий только разрешённые документальные файлы

## Базовая модель работы

1. Сначала смысл и контракт, потом код.
2. Один активный implementation stream за раз.
3. Новый кодовый шаг не начинается, пока не проверен хвост предыдущего stream.
4. По умолчанию реализация идёт только после read-only анализа и согласованного ТЗ.
5. Если пользователь явно ограничил шаг локальной работой или явно запретил публикацию, действует локальный режим.
6. Если ТЗ согласовано, пользователь дал команду на реализацию и явно не запретил публикацию, для нового code stream normal default rollout path: `локальная реализация до локального MVP -> draft PR в staging -> ready/merge в staging -> staging smoke -> draft PR в main -> ready/merge в main -> production deploy -> production smoke`.
7. Default trigger выхода из локалки в первый внешний publish-level — достижение согласованного `Локального MVP`.
8. Команда `реализовать` по умолчанию разрешает агенту вести stream локально до `Локального MVP`; ближайший внешний publish-level после этого — `draft PR в staging`, если не оговорено иное.
9. Если пользователь явно решил идти в `staging` раньше или позже, это фиксируется как override относительно default-правила.
10. Полная локальная реализация всего ТЗ считается допустимым trigger-ом перехода в `staging` только если текущее ТЗ мало и совпадает с одним локально тестируемым feature increment-ом.
11. Прямой `PR` в `main` для нового code stream запрещён без отдельной явной команды пользователя.
12. Если команда двусмысленна, агент выбирает более безопасный вариант и останавливается на нём.
13. Для существенных stream-ов требуется versioned ТЗ; chat-only ТЗ остаётся допустимым для мелких исправлений и маленьких публикуемых фиксов, пока stream не признан существенным.

## Приоритет rollout discipline

1. Для нового code stream приоритет у rollout discipline, а не у того, какая ветка ближе к текущему production runtime.
2. Truth текущего runtime нужен для анализа, диагностики и проверки текущего поведения.
3. Truth текущего runtime не даёт агенту права самовольно менять normal default rollout с `staging-first` на `main-first`.
4. Если `main` содержит более свежий runtime-контур, но новый stream ещё не проходил через `staging`, агент обязан:
   - остановиться
   - назвать это process-risk или process-ошибкой
   - запросить явное решение пользователя
5. Staging-first rollout после `Локального MVP` сам по себе не делает любой новый code stream существенным stream-ом с обязательным внешним versioned ТЗ.

## Где хранится ТЗ

Для существенного stream-а ТЗ должно быть versioned и жить во внешнем репозитории документации.

Основной репозиторий не хранит:

1. полные stream-ТЗ
2. живые указатели на версии ТЗ
3. реестр активных работ
4. историю статусов ТЗ

### Внешнее ТЗ

Перед существенной реализацией агент проверяет зафиксированный внешний репозиторий документации:

1. конкретный `Spec repo`
2. `active-streams.md`
3. `streams/README.md`
4. конкретный `Spec doc`
5. конкретный `Spec revision`

Если внешний репозиторий документации недоступен, substantial stream paused до восстановления доступа.

### Чего недостаточно

Недостаточно как единственного source of truth:

1. только чата
2. только устной договорённости
3. только ссылки на «последнюю версию документа» без фиксированной revision

## Этап 1. Классификация запроса

1. Сначала определить, это read-only запрос или implementation запрос.
2. Если запрос на анализ, review, сравнение вариантов, план или ТЗ, работа остаётся read-only.
3. Если запрос на реализацию, сначала всё равно пройти через анализ и согласование ТЗ.

Результат:
- понятен режим работы по текущему запросу.

## Этап 2. Read-only анализ

1. Изучить текущую реализацию в коде.
2. Найти существующие runtime-path и минимальную безопасную точку изменения.
3. Зафиксировать ограничения, риски и возможный scope drift.
4. На этом этапе ничего не менять.

Результат:
- техническая картина текущего состояния.

## Этап 3. Черновик ТЗ

На основе read-only анализа агент готовит черновик ТЗ текущего stream.

Черновик ТЗ фиксирует:
- цель
- границы
- что меняется и что не меняется
- write-set
- критерии приёмки
- предполагаемую основную среду проверки
- риски и двусмысленности

Если задача потенциально шире одного безопасного шага, это отмечается уже в черновике.

Результат:
- первый рабочий черновик ТЗ по текущему stream.

## Этап 4. Критика ТЗ

Агент обязан критически проверить ТЗ на слабые места по реальному коду и runtime:
- соответствие архитектуре и инвариантам
- наличие нужных runtime-path
- риск scope drift и побочных эффектов
- честность локальной проверки и достаточность локального контура для достижения `Локального MVP`
- что именно должно проверяться на `staging` как на confirmatory integration / environment gate, а не как на первой среде, где фича вообще становится тестируемой
- не нужен ли более сильный уровень делегации

Если найдены слабые места, агент обязан сформулировать их явно.

Результат:
- список замечаний, рисков и слабых мест по черновику ТЗ.

## Этап 5. Финальное ТЗ и slices

После критики агент переписывает ТЗ в финальную версию текущего stream.

Если задача шире одного безопасного шага:
- кратко описать все крупные feature-increments или фазы
- подробно описать только активный slice как внутренний инженерный подшаг
- отдельно явно зафиксировать, что считается `Локальным MVP` текущего stream-а
- не активировать следующий крупный increment, пока не закрыт хвост текущего

Результат:
- финальное ТЗ, понятный активный slice и согласованный `Локальный MVP`.

## Этап 6. Согласование ТЗ

Перед запуском в работу агент согласует с пользователем:
- финальное ТЗ
- активный slice
- критерий `Локального MVP`
- уровень делегации
- где именно хранится versioned ТЗ
- если ТЗ внешнее — какие `Spec repo`, `Spec doc` и `Spec revision` являются согласованными

Уровни делегации:
- локальный режим
- `PR в staging`
- `через staging`
- `до merge в main`
- dangerous ops

Для мелких исправлений и коротких локальных действий ТЗ может оставаться в чате.
Для существенных stream-ов должно существовать versioned ТЗ в конкретном `Spec repo` на конкретной `Spec revision`.
Если такой stream реально открыт, его нужно явно зафиксировать во внешнем `active-streams.md`.
По умолчанию согласование нового code stream означает staging-first rollout после достижения `Локального MVP`.
Если пользователь хочет идти в `staging` раньше или позже, это должно быть оговорено отдельно и явно.
По умолчанию это не поднимает execution ceiling выше `draft PR в staging`; `ready`, `merge`, `staging smoke`, `PR в main`, `merge` в `main`, `production deploy` и `production smoke` требуют отдельной явной делегации, если иное заранее не согласовано.
Мелкий публикуемый fix может оставаться на chat-only ТЗ, если stream не признан существенным.
К существенным stream-ам относятся как минимум:
- rollout, заранее делегированный выше уровня `draft PR в staging`
- multi-step implementation
- изменения с runtime/data-flow/delivery риском
- новая интеграционная модель или новый сложный slice внутри интеграции

Результат:
- утверждённое ТЗ и понятный уровень делегации для текущего stream.

## Этап 7. Preflight

Preflight делается непосредственно перед запуском stream.

Проверить:
- локальный diff и незапушенные изменения
- активную ветку
- открытые PR
- незавершённый CI
- хвост предыдущего stream
- хватает ли текущего уровня делегации

Если preflight не чистый или делегации недостаточно, агент останавливается.

Результат:
- подтверждено, можно ли запускать текущий stream.

## Этап 8. Запуск stream

Если ТЗ согласовано и preflight чистый:
- если это новый code stream, первый publish-level branch/worktree создаётся от `origin/staging`
- `origin/main` используется только:
  - для clean PR в `main` после успешного прохождения через `staging`
  - для `docs-only` stream
  - для direct-to-main path, отдельно и явно разрешённого пользователем
- для существенного stream-а сначала зафиксировать `Spec repo`, ссылку на внешнее ТЗ и конкретную `Spec revision`
- для мелкого шага сохранять ТЗ только в чате или как короткий локальный reference-документ при явной договорённости, но не как полный stream-ТЗ в основном репозитории
- запустить implementation stream в рамках активного slice и согласованного уровня делегации

Результат:
- implementation stream корректно запущен.

## Этап 9. Локальная реализация до MVP

Агент реализует активный slice как внутренний инженерный подшаг текущего stream-а.
Отдельный slice может быть слишком мал, чтобы его мог честно проверить пользователь; сам по себе он не считается trigger-ом перехода в `staging`.

По умолчанию stream продолжается локально, пока не выполнено одно из условий:
- достигнут согласованный `Локальный MVP`
- пользователь явно решил выйти в `staging` раньше
- обнаружен blocker
- для честной локальной проверки не хватает среды, данных или доступов

Если `Локальный MVP` достигнут, локальный контур закрыт, и следующим внешним publish-level по умолчанию становится `draft PR в staging`.

Если текущее ТЗ мало и полностью совпадает с одним локально тестируемым feature increment-ом, полная реализация ТЗ допустима как тот же trigger.

Результат:
- локальный diff доведён либо до согласованного `Локального MVP`, либо до честной точки blocker-а или явного handoff к пользователю.

## Этап 10. Review policy по slice-ам

Каждый slice заканчивается обязательным `author self-check`.

`Author self-check` означает:
- проверить, что slice действительно закрывает свой acceptance
- проверить, что diff соответствует активному slice
- проверить, что не появилось scope drift
- проверить, что следующий шаг понятен и честно определён

Полный `formal self-review` выполняется на boundary points, а не после каждого micro-slice.

Boundary point считается наступившим, если slice:
- завершает смысловую единицу
- выводит diff на внешний publish-уровень
- меняет delivery-уровень
- затрагивает рискованный runtime/data-flow/integration контур

Для code stream `formal self-review` обязателен:
- перед внешней публикацией
- после зелёного `CI` на `draft` PR
- после перевода PR в `ready` и перед `merge`

Для docs-only и локальных micro-slice обычно достаточно `author self-check`, если slice не дошёл до boundary point.

Результат:
- каждый slice проходит минимальный контроль
- полный review выполняется в точках, где он реально нужен

## Этап 11. Helper-review

Helper-review применяется не после каждого slice, а на boundary points code stream.

Helper-review подключается, если:
- diff уже прошёл `formal self-review`
- slice находится на boundary point
- среда и разрешения позволяют такой review-контур

Helper-review не заменяет `author self-check` и не заменяет `formal self-review`.

Результат:
- дополнительный review выполняется в точках повышенного риска и публикации, без лишней бюрократии на micro-slice.

## Этап 12. Контрольные точки

Контрольные точки обязательны:
- перед первым неразрешённым действием
- после зелёного `CI` на `draft` PR
- после перевода PR в `ready`
- перед `merge` в `staging`
- перед `merge` в `main`
- перед dangerous ops
- при blocker, конфликте, scope drift или красном `CI`

На контрольной точке агент обязан показать:
- короткий итог
- что осталось открытым
- короткое меню следующих действий
- одну явную рекомендацию
- краткое `Почему`

Варианты нумеруются.
Формат рекомендации: `Рекомендация: 1. ...`

Меню обязательно именно здесь, на точке handoff к пользователю.
Вне точки handoff обычные progress updates и commentary идут без меню.
Если нужен один точный ответ без реальных вариантов выбора, агент задаёт один прямой вопрос без меню.

## Этап 12A. Выбор workflow

Перед рекомендацией следующего шага агент сначала определяет, какой workflow
применим к текущему active stream.

Порядок:
1. определить фактический write-set текущего stream-а
2. определить тип stream-а: `code stream` или `docs-only`
3. определить, достигнут ли согласованный `Локальный MVP`
4. определить целевой delivery-path текущего stream-а
5. определить, есть ли branch/worktree contamination от более раннего stream-а
6. только после этого выбирать следующий шаг процесса

Правило приоритета:
- текущий active stream важнее истории ветки
- текущий write-set важнее прошлого delivery-контура
- `docs-only path` имеет приоритет над обычной цепочкой `staging -> main`,
  если текущий stream удовлетворяет условиям `docs-only`

Если текущий stream является `docs-only`, но рабочая ветка или worktree
содержит историю более раннего stream-а, следующим правильным шагом считается:
1. clean branch/worktree от `origin/main`
2. перенос только текущего `docs-only` diff
3. `draft PR` сразу в `main`

## Выбор базовой ветки и publish-level

1. Новый code stream с runtime/data-flow/integration изменением:
   - локальная реализация от clean worktree/branch на базе `origin/staging`
   - первый внешний publish-level — `draft PR` в `staging`
2. Code stream после успешного `staging` path:
   - clean worktree/branch от `origin/main`
   - отдельный clean PR в `main`
3. `Docs-only` stream:
   - может идти сразу в `main`
4. Direct-to-main code path:
   - допустим только по отдельной явной команде пользователя

Правило рекомендации:
1. Пока согласованный `Локальный MVP` не достигнут и blocker-ов нет, рекомендуемый вариант — `1. Продолжить локальную реализацию`.
2. Если действует локальный режим и `commit` не разрешён, а `Локальный MVP` уже достигнут, рекомендуемый вариант — `1. Остановиться`.
3. Если действует уровень `PR в staging` и `Локальный MVP` уже достигнут, рекомендуемый вариант после локальной готовности — `1. Commit + push + draft PR в staging`.
4. Если действует уровень `PR в staging` и `draft` PR в `staging` уже validated, рекомендуемый вариант — `1. Перевести PR в ready`.
5. Если действует уровень `через staging` и validated PR в `staging` всё ещё `draft`, рекомендуемый вариант — `1. Перевести PR в ready`.
6. Если действует уровень `через staging` и PR в `staging` уже `ready`, рекомендуемый вариант — `1. Merge в staging`.
7. Если действует уровень `до merge в main` и `staging smoke` уже зелёный, рекомендуемый вариант до публикации — `1. Commit + push + draft PR в main`.
8. Если действует уровень `до merge в main` и `draft` PR в `main` уже validated, рекомендуемый вариант — `1. Перевести PR в ready`.
9. Если действует уровень `до merge в main` и PR в `main` уже `ready`, рекомендуемый вариант — `1. Merge в main`.
10. Если `merge` в `main` уже выполнен для code/release stream, рекомендуемый вариант — `1. Ручной production deploy`.
11. Если ручной production deploy уже выполнен для code/release stream, рекомендуемый вариант — `1. Production Post-Deploy Smoke`.
12. Если production smoke закрыт успешно, рекомендуемый вариант — `1. Cleanup` или `1. Следующая задача`.

Правило следующего шага процесса:
1. Правило следующего шага процесса имеет приоритет над локальной паузой на контрольной точке.
2. Если пользователь спрашивает о следующем логичном и правильном шаге, агент обязан назвать следующий delivery-уровень или следующий process-step.
3. Если текущая контрольная точка закрыта, acceptance выполнен и blocker-ов нет, агент рекомендует именно следующий шаг процесса, а не паузу.
4. Если следующий шаг требует отдельной делегации, это указывается отдельно и не заменяет собой рекомендацию следующего шага.
5. Формулировка `Остановиться на контрольной точке` используется как рекомендация только если:
   - есть blocker
   - acceptance текущей точки не закрыт
   - следующий шаг выходит за согласованный execution ceiling
   - пользователь сам хочет паузу
6. Для Abrikosoff Connector после `merge` в `main` следующим шагом процесса считается `Ручной production deploy`, если текущий stream является code/release stream.
7. После production deploy следующим шагом процесса считается `Production Post-Deploy Smoke`, если текущий stream является code/release stream.
8. Статус dangerous op ограничивает исполнение, но не подменяет собой рекомендацию следующего шага процесса.

Результат:
- пользователь видит честную следующую точку выбора без скрытого расширения полномочий агента.

## Этап 13. Уровень `PR в staging`

Это normal default publish-level для code stream после достижения согласованного `Локального MVP` и команды на реализацию, если пользователь явно не запретил публикацию.

Разрешает:
- self-review
- helper-review при доступности
- `commit`
- `push`
- draft PR в `staging`
- `CI`
- исправления в рамках того же scope
- финальный author self-review опубликованного PR после зелёного `CI`

Не разрешает:
- перевод PR в `ready`
- `merge` в `staging`
- staging smoke
- PR в `main`
- `merge` в `main`
- `rebase`
- `force-push`
- `migrate`
- `production deploy`

Готовый PR в `staging` — это публикационная и CI-точка, но не staging-verification.

Результат:
- получен validated `draft` PR в `staging`, готовый к отдельной контрольной точке и отдельному решению о переводе в `ready`.

## Этап 14. Уровень `через staging`

Требует отдельной явной делегации.

`Staging` используется как confirmatory integration / environment gate.
Он не должен быть местом, где фича впервые становится тестируемой; к моменту выхода на `staging` основной пользовательский сценарий уже должен быть честно проверяем локально хотя бы на уровне согласованного `Локального MVP`.

Разрешает:
- при необходимости перевести validated PR в `staging` из draft в `ready`
- отдельную контрольную точку после перевода PR в `ready`
- `merge` в ветку `staging`
- staging deploy-check
- staging smoke
- исправления в том же scope, если staging выявил проблемы

Основная confirmatory-проверка логики процессов и интеграций на средовом контуре происходит именно здесь.

Результат:
- текущий validated diff либо успешно прошёл `staging`, либо честно остановлен на blocker.

## Этап 15. Уровень `до merge в main`

Требует отдельной явной делегации и начинается только после успешного прохождения через `staging`.

Это не `merge staging -> main`.
`PR` в `main` не открывается из накопленного состояния `staging`; источник этого шага — только `validated diff` текущего active stream.

Разрешает:
- draft PR в `main` только из validated diff текущего шага, а не из накопленного состояния `staging`
- `CI`
- self-review и helper-review
- исправления в том же scope
- финальный author self-review опубликованного PR после зелёного `CI`
- перевод PR в `main` из draft в `ready` только после того, как он стал validated PR
- отдельную контрольную точку после перевода PR в `ready`
- `merge` в `main`

### Частая ошибка

Неправильно:
- после успешного прохождения через `staging` описывать следующий шаг как `staging -> main`
- открывать `PR` в `main` из накопленного состояния ветки `staging`

Правильно:
- после успешного этапа `через staging` открывать отдельный `draft PR` в `main`
- строить этот `PR` только из `validated diff` текущего active stream

Для Abrikosoff Connector после `merge` в `main` следующим шагом release-flow считается `Ручной production deploy` только для code/release stream.

Результат:
- validated diff доведён до `merge` в `main` в рамках отдельной явной делегации и передан в production handoff.

### Короткая таблица переходов

| Текущий уровень | Следующий правильный уровень |
| --- | --- |
| `PR в staging` | `через staging` |
| `через staging` | `до merge в main` |
| `до merge в main` | `Ручной production deploy` |
| `Ручной production deploy` | `Production Post-Deploy Smoke` |

## Этап 16. Dangerous ops

К dangerous ops относятся:
- `rebase`
- `force-push`
- любые `migrate`
- `production deploy`

Они всегда требуют отдельного явного разрешения.

Результат:
- операции повышенного риска не смешиваются с обычной delivery-цепочкой.

## Этап 17. Docs-only path

`Docs-only` stream — отдельное исключение и не подчиняется цепочке `staging -> main`.

Допустим только если diff меняет исключительно:
- `AGENTS.md`
- `docs/**`
- `README*.md`
- другие markdown/текстовые регламенты

И только если stream стартует из clean branch/worktree от `origin/main` без недокументального хвоста в рабочем контексте.

Для `docs-only` slice рекомендация следующего шага строится по `docs-only path`,
а не по предыдущему code stream.

Если текущая ветка или worktree содержит историю более раннего stream-а,
агент рекомендует не публикацию этой истории как есть, а clean branch/worktree
от `origin/main` с переносом только текущего `docs-only` slice.

По команде пользователя на документальный путь агент может пройти:
- clean branch/worktree от `origin/main`
- правка документов
- self-review
- `commit`
- `push`
- PR в `main`
- `CI`, если он есть
- финальный self-review
- `ready`
- `merge`
- cleanup

Отсутствие `CI` не блокирует `docs-only` path.

Если в diff появляется недокументальный файл, stream возвращается к обычному workflow.

Результат:
- документальные изменения идут по отдельному честному пути без смешения с code stream.

## Ссылки на ТЗ в implementation stream

Для любого существенного implementation stream агент должен уметь ответить на три вопроса:

1. Где лежит ТЗ?
2. Какая именно revision ТЗ является согласованной?
3. Где в delivery-контуре это зафиксировано?

Минимально допустимые места фиксации:

1. описание PR
2. рабочий implementation summary
3. внешний `active-streams.md`
4. task tracker, если он используется как дополнительный process-layer

Если PR делается по внешнему ТЗ, в описании PR должен быть блок вида:

- `Spec repo:` `<repo-or-location>`
- `Spec doc:` `<path-or-doc-name>`
- `Spec revision:` `<commit-hash>`

`Spec repo` в PR-описании указывает только внешний репозиторий документации и не создаёт живой реестр в основном проекте.

## Этап 18. Закрытие stream

Stream может быть доведён до разных handoff-точек:
- validated PR в `staging`
- успешное прохождение через `staging`
- `merge` в `main`
- полностью закрытый stream со всеми делегированными follow-up

Handoff-точка — это допустимая точка остановки и следующего решения пользователя, но не автоматически закрытый хвост.

Открытый PR, незавершённый `CI`, незавершённый `staging`/`main` path, deploy, smoke и cleanup остаются хвостом до их фактического завершения.

Новый code stream по умолчанию не начинается, пока этот хвост не закрыт или пользователь явно не разрешил исключение после перечисления хвоста и связанных рисков.

Stream считается полностью закрытым только когда выполнены все follow-up для того уровня, до которого он был делегирован.

Для существенного stream-а полное закрытие включает `spec closure`.

Нужно различать два типа хвоста:

1. runtime/release tail: открытый PR, незавершённый `CI`, незавершённый `staging`/`main` path, deploy и smoke; это жёсткие blockers
2. spec/admin tail: `Spec doc` status, `streams/README.md`, запись в `active-streams.md`, `archive pending`; это обязательные follow-up, но не отдельный rollout gate сами по себе

### Spec Closure Checklist

Перед тем как считать существенный stream закрытым, нужно:

1. сверить фактический runtime / validated diff / acceptance с внешним `Spec doc`
2. обновить статус в самом `Spec doc`, если документ всё ещё содержит собственный статусный блок
3. обновить каноническую запись во внешнем `streams/README.md`
4. синхронизировать внешний `active-streams.md`: оставить там только реально открытые существенные stream-ы, а закрытую запись удалить или заменить актуальной
5. если перенос документа в `archive/` не делается в том же шаге, явно оставить документ в состоянии `implemented` с отдельным follow-up `archive pending`

Статус `planned` для уже материализованного acceptance считается process-error и не является допустимым состоянием закрытия stream-а.
Незакрытый `spec/admin tail` нужно явно перечислять перед стартом нового substantial code stream-а, но он сам по себе не запрещает unrelated `docs-only` шаг или малый локальный maintenance step.

Для Abrikosoff Connector `merge` в `main` остаётся только handoff-точкой для code/release stream.
Для code/release stream хвост остаётся открытым до ручного production deploy и успешного production smoke по правилам `docs/post-deploy-smoke.md`.
Для `docs-only` path после `merge` в `main` следующим шагом считается cleanup временных артефактов или переход к следующей задаче.

Результат:
- у stream есть честная точка завершения без путаницы между локальной готовностью, `staging` и `main`.

## Этап 19. Cleanup

После полного закрытия stream агент отдельно предлагает cleanup временных артефактов.

По умолчанию cleanup включает только:
- временные `git worktree`
- временные локальные ветки
- remote-ветки после merge
- временные файлы в `/tmp`
- фоновые процессы этого шага

Cleanup не должен затрагивать:
- пользовательские `untracked` файлы
- незавершённые ветки и worktree
- окружения, доступы и deploy-настройки
- любые артефакты без явного безопасного основания

Потенциально опасный cleanup требует отдельного подтверждения пользователя.

Результат:
- временные артефакты шага убраны без затрагивания пользовательских хвостов.

## Короткая формула workflow

`Запрос -> Классификация -> Read-only анализ -> Черновик ТЗ -> Критика ТЗ -> Финальное ТЗ и slices -> Согласование -> Preflight -> Запуск -> Реализация -> Self-review -> Helper-review -> Контрольная точка -> PR в staging -> Через staging -> До merge в main -> Docs-only path при необходимости -> Closure -> Cleanup`
