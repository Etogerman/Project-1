# Технология работы над задачами

## Цель

Этот документ фиксирует однозначный процесс работы над задачами:
- когда можно начинать реализацию
- когда создавать ветку
- как вести implementation stream
- когда публиковать изменения
- когда шаг считается завершённым
- когда можно начинать следующий шаг

## Базовые принципы

1. Сначала смысл и контракт, потом код.
2. Один активный implementation stream за раз.
3. Новый кодовый шаг запрещён, пока не закрыт предыдущий stream.
4. Каждое действие публикации — отдельная точка контроля.
5. Задача считается завершённой только после production-подтверждения.

## Этап 1. Получение задачи

1. Получить задачу.
2. Зафиксировать цель.
3. Понять, что должно измениться для пользователя.
4. Понять, что считается готовым результатом.

Результат:
- понятная цель задачи.

## Этап 2. Уточнение контракта

1. Проверить, нет ли двусмысленности.
2. Уточнить продуктовый смысл.
3. Уточнить границы.
4. Уточнить, что точно не входит.
5. Не начинать реализацию, пока контракт не ясен.

Результат:
- согласованный контракт задачи.

## Этап 3. Read-only анализ

1. Изучить текущую реализацию в коде.
2. Найти существующие точки расширения.
3. Определить, какой слой является источником истины.
4. Проверить ограничения и риски.
5. На этом этапе не менять код.

Результат:
- техническая картина текущего состояния.

## Этап 4. Подготовка ТЗ

1. Составить первое ТЗ.
2. В ТЗ обязательно указать:
- цель шага
- границы
- что меняется
- что не меняется
- минимальный write-set
- тестовую стратегию
- критерии приёмки
- компромиссы и риски

Результат:
- первый рабочий вариант ТЗ.

## Этап 5. Проверка ТЗ на слабые места

1. Проверить ложные предположения.
2. Проверить, существуют ли нужные runtime-path.
3. Проверить, не врёт ли будущий UI.
4. Проверить рискованные migration/backfill моменты.
5. Проверить, не слишком ли широк scope.
6. Проверить побочные эффекты.

Результат:
- список рисков и дыр в ТЗ.

## Этап 6. Улучшение ТЗ

1. Убрать ложные обещания.
2. Уточнить scope.
3. Согласовать UI и runtime.
4. Зафиксировать честный контракт.

Результат:
- реализуемое и честное ТЗ.

## Этап 7. Разбиение на steps или slices

1. Решить, делать задачу одним шагом или несколькими.
2. Делить на slices, если меняются разные слои, есть рискованные миграции или задача слишком широкая.
3. Для каждого slice зафиксировать:
- цель
- scope
- write-set
- критерии приёмки

Результат:
- план реализации по шагам.

## Этап 8. Preflight перед новым кодовым шагом

Перед началом нового кода обязательно проверить:
1. есть ли локальный незавершённый diff
2. есть ли открытый draft PR в `staging` или `main`
3. есть ли открытый обычный PR в `staging` или `main`
4. есть ли смерженный PR в `staging` без завершённого staging deploy или staging smoke
5. есть ли staging smoke без отдельного PR в `main` для того же diff
6. есть ли смерженный PR в `main` без завершённого production deploy, если production входит в release flow
7. есть ли production deploy без завершённого post-deploy smoke
8. есть ли другой активный implementation stream

Если найден хотя бы один хвост:
- новый кодовый шаг не начинается

Разрешено только:
- доводить текущий stream
- делать read-only анализ
- по явной команде пользователя закрыть или отменить текущий шаг

Результат:
- решение, можно ли начинать новый step.

## Этап 9. Создание ветки

Ветка создаётся только если:
1. ТЗ согласовано
2. scope шага уже определён
3. preflight чистый
4. действительно начинается кодовая реализация

Правила:
1. branch создаётся только от `origin/main`
2. на branch переходят сразу при создании
3. один branch = один implementation step
4. старые mixed-ветки не используются как база

Результат:
- новый clean branch и активный implementation stream.

## Этап 10. Реализация шага

1. Определить точный write-set.
2. Прочитать только нужные файлы.
3. Внести изменения в рамках согласованного scope.
4. Не расползаться в соседние задачи.
5. Если обнаружилась новая двусмысленность, остановиться и уточнить контракт.

Результат:
- локальный diff по одному step.

## Этап 11. Локальный review

1. Проверить diff как reviewer, а не как автор.
2. Проверить баги.
3. Проверить leakage за scope.
4. Проверить честность UI/runtime контракта.
5. Проверить migration/backfill gaps.
6. Проверить соответствие ТЗ.

Если findings есть:
1. исправить
2. ещё раз быстро review

Результат:
- консистентный локальный diff.

## Этап 12. Commit

1. Commit делается после завершённого локального review.
2. Commit не даёт права на push.

Результат:
- локально зафиксированный шаг.

## Этап 13. Push

1. Push выполняется отдельным подтверждённым шагом.
2. Push не даёт права на создание PR автоматически.
3. Если пользователь уже явно выбрал публикацию в текущем implementation stream
   или заранее делегировал `commit` и `push` для этого stream,
   то после локально готового diff рекомендуемым следующим шагом
   считается `COMMIT + PUSH`, а не только `COMMIT`.

Результат:
- опубликованная ветка.

## Этап 14. Draft PR в `staging`

1. После push создаётся draft PR.
2. Draft PR нужен для:
- CI
- review опубликованного diff
- отдельной точки контроля перед merge

Даже если внешний reviewer отсутствует, draft PR всё равно используется.

Результат:
- опубликованный stream в GitHub для интеграционной проверки.

## Этап 15. CI и финальный self-review для `staging`

1. Дождаться CI.
2. Проверить checks.
3. Сделать финальный внутренний review уже на уровне PR.
4. Проверить, что PR действительно закрывает согласованный step.

Результат:
- PR в `staging` готов к решению о merge.

## Правило review после CI

После зелёного CI обязательным quality-gate считается финальный self-review
агента по текущему implementation stream.

Внешний review не считается обязательным шагом по умолчанию.

Если:
1. CI зелёный
2. агент сделал финальный self-review
3. PR переведён в `ready`

то следующий нормальный шаг — решение пользователя о `merge`,
а не ожидание внешнего reviewer-а.

Внешний review используется только если:
1. пользователь явно хочет дополнительную проверку
2. в шаге участвует отдельный reviewer
3. появились внешние замечания, которые нужно разобрать

## Этап 16. Merge в `staging`

1. Merge в `staging` — отдельное действие.
2. Merge в `staging` не означает публикацию в production.
3. Merge в `staging` не даёт права автоматически двигать всё содержимое `staging` в `main`.

Результат:
- проверяемый diff текущего шага попал в интеграционную ветку.

## Этап 17. Staging post-merge контур

После merge в `staging` шаг ещё не считается закрытым.

Нужно проверить:
1. запустился ли staging deploy
2. завершился ли staging deploy успешно
3. прошёл ли staging smoke

Пока staging smoke не завершён:
- step считается незакрытым
- новый кодовый шаг не начинается

Результат:
- подтверждение шага на `staging`.

## Этап 18. PR в `main`

После успешного staging smoke создаётся отдельный PR в `main`.

Правила:
1. PR в `main` идёт не из `staging`.
2. Схема `staging -> main` запрещена.
3. В `main` продвигается только проверенный diff текущего шага.
4. Источник PR в `main` — та же `codex/...` ветка или отдельная clean-ветка с тем же validated diff.

Результат:
- отдельный production PR без накопленного состояния `staging`.

## Этап 19. CI и финальный self-review для `main`

1. Дождаться CI по PR в `main`.
2. Проверить checks.
3. Сделать финальный review уже перед production merge.
4. Проверить, что PR в `main` содержит только нужный diff текущего шага.

Результат:
- PR в `main` готов к решению о merge.

## Этап 20. Merge в `main`

1. Merge в `main` — отдельное действие.
2. Merge в `main` публикует изменения в основной поток.
3. Merge в `main` не означает, что staging или production уже подтверждены.
4. Merge в `main` не заменяет отдельный production deploy, если production выкатывается вручную.

Результат:
- изменения попали в основной поток.

## Этап 21. Production post-merge контур

После merge в `main` шаг ещё не считается закрытым.

Нужно проверить:
1. выполнен ли production deploy, если этот шаг реально выкатывается в production
2. прошёл ли production smoke после фактического production deploy

Пока production smoke не завершён:
- step считается незакрытым
- новый кодовый шаг не начинается

Результат:
- production-подтверждение шага, если production входит в активный release flow.

## Этап 22. Закрытие issue

Issue закрывается только если одновременно выполнено всё:
1. PR в `staging` смержен
2. staging deploy завершён
3. staging smoke зелёный
4. PR в `main` смержен
5. production deploy завершён, если шаг реально выкатывается в production
6. production smoke зелёный после фактического production deploy, если production входит в активный release flow
7. результат соответствует задаче

Если задача закрывалась несколькими PR:
- в issue желательно оставить комментарий со списком закрывающих PR

Результат:
- закрытая issue.

## Этап 23. Выход из ветки и переход к следующему шагу

С ветки уходят только после полного закрытия stream.

Это означает:
1. PR в `staging` смержен и staging smoke завершён
2. PR в `main` смержен
3. production deploy завершён, если шаг реально выкатывается в production
4. production smoke завершён, если production входит в активный release flow
5. шаг формально закрыт

После этого:
1. переключение на `main` или актуальный base
2. следующий step начинается новой clean branch от `origin/main`

## Этап 24. Cleanup временных артефактов

После полного закрытия stream нужно отдельно предложить cleanup
временных артефактов, созданных в рамках этого шага.

В cleanup по умолчанию входят только:
1. временные `git worktree`
2. временные локальные ветки
3. remote-ветки после merge
4. временные файлы в `/tmp`
5. фоновые процессы, запущенные для этого шага

Cleanup не должен затрагивать:
1. пользовательские `untracked`-файлы
2. незавершённые ветки и worktree
3. окружения, доступы и deploy-настройки
4. любые артефакты без явного безопасного основания

Если cleanup включает потенциально опасное удаление:
1. требуется отдельное подтверждение пользователя

Результат:
- убраны временные артефакты шага без затрагивания пользовательских хвостов.

## Когда branch считается активной

Branch активна, пока существует хотя бы одно из состояний:
1. локальный незакоммиченный diff
2. незапушенная работа
3. открытый draft PR или обычный PR в `staging`
4. смерженный PR в `staging` без завершённого staging smoke
5. открытый draft PR или обычный PR в `main`
6. смерженный PR в `main` без завершённого production deploy, если production входит в активный release flow
7. production deploy без завершённого smoke

Пока branch активна:
- новый implementation stream не открывается

## Короткая формула процесса

`Задача -> Уточнение -> Read-only анализ -> ТЗ -> Проверка ТЗ -> Улучшение ТЗ -> Slices -> Preflight -> Branch -> Реализация -> Review -> Commit -> Push -> Draft PR в staging -> CI -> Self-review -> Ready for review -> Merge в staging -> Staging deploy -> Staging smoke -> PR в main из validated diff -> CI -> Self-review -> Ready for review -> Merge в main -> Manual production deploy -> Production smoke -> Close issue -> Cleanup`

Если production deploy для конкретного шага не выполняется сразу, stream не
считается полностью закрытым только по merge в `main` и staging smoke.

## Практическое правило

Новый кодовый шаг можно начинать только тогда, когда предыдущий шаг:
- прошёл через `staging`
- отдельно проведён в `main` без схемы `staging -> main`
- выкачен в production, если production входит в активный release flow шага
- прошёл релевантный post-deploy smoke
- формально закрыт

## Правило рекомендации следующего шага

После локально готового этапа агент обязан предлагать короткое меню
следующих действий, но рекомендация зависит от уже выданных разрешений:

1. Если `push` ещё не разрешён явно, рекомендуемый вариант — `COMMIT`.
2. Если пользователь уже явно выбрал `push` в текущем stream
   или заранее делегировал `commit` и `push`,
   рекомендуемый вариант — `COMMIT + PUSH`.
3. Если пользователь заранее делегировал ещё и создание `draft PR`,
   после успешного `push` можно рекомендовать `COMMIT + PUSH + DRAFT PR`.

Это правило не даёт права автоматически публиковать изменения без уже
полученного разрешения, а только меняет рекомендуемую точку остановки
в меню конца этапа.

## Правило следующего шага после ready

Если PR уже переведён в `ready`, CI зелёный и финальный self-review выполнен,
агент не должен по умолчанию рекомендовать `ждать review по PR`.

По умолчанию агент должен предлагать одно из:
1. `MERGE`
2. `Остановиться`
3. `Запросить внешний review` — только если такой review реально нужен

То есть `ready` в текущем процессе означает
`готово к решению о merge`, а не `обязательно ждём внешнего reviewer-а`.
