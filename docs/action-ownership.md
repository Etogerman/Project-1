# Алгоритм действий и исполнители

Этот документ фиксирует, кто выполняет шаги процесса доставки. Если рекомендация
агента противоречит этой таблице, таблица считается источником истины.

`Исполнитель` означает, кто физически выполняет действие. Решение перейти к
следующему контрольному уровню принимает пользователь или оператор, если это
требуется процессом.

## Правило меню

В пользовательском меню исполнитель должен соответствовать таблице. Агент не
указывает себя исполнителем пользовательских GitHub-контрольных действий.

Правильный формат для таких шагов:

`1. Вы переводите PR в ready. [вы]`

Если PR уже `ready`, правильный следующий checkpoint:

`1. Copilot/reviewer выполняет review. [Copilot/reviewer]`

Если Copilot/reviewer review уже закрыт и агенту доступны review status,
comments/threads и CI status, правильный следующий checkpoint:

`1. Агент читает review и даёт технический вердикт. [я]`

Если review status, comments/threads или CI status недоступны либо неоднозначны,
агент не даёт вердикт `готово к merge` и запрашивает недостающие данные или
решение пользователя.

Copilot/reviewer review считается закрытым для этого checkpoint только когда
review завершён, не находится в pending/in-progress состоянии и агент может
прочитать актуальный результат review.

Если вердикт агента — `готово к merge`, правильный следующий GitHub-шаг:

`1. Вы выполняете merge. [вы]`

Запрещено показывать пункт меню, где исполнитель такого действия — агент.

## Общий алгоритм

| N | Действие | Исполнитель |
|---|---|---|
| 1 | Сформулировать задачу, цель или проблему | Пользователь |
| 2 | Прочитать код, docs, PR, CI и текущее состояние | Агент |
| 3 | Определить тип работы и текущий workflow | Агент |
| 4 | Подготовить черновик ТЗ или уточнение scope | Агент |
| 5 | Утвердить ТЗ, scope, приоритет или риск | Пользователь |
| 6 | Реализовать локальное изменение по согласованному scope | Агент |
| 7 | Запустить локальные проверки, которые доступны агенту | Агент |
| 8 | Выполнить author self-check | Агент |
| 9 | Провести операторскую приёмку локального MVP | Пользователь или оператор |
| 10 | Принять решение о выкладке | Пользователь или оператор |
| 11 | Зафиксировать внешнее ТЗ, если оно требуется | Агент |
| 12 | Сделать commit | Агент |
| 13 | Сделать push ветки и открыть draft PR | Агент |
| 14 | Проверить title/body PR и guard-поля | Агент |
| 15 | Проверить title/body PR и guard-поля до ready; если пользователь вернул красный CI, разобрать логи и предложить исправления | Агент |
| 16 | Проверить CI draft PR; если всё ок, перевести PR из draft в ready; если есть ошибки, вернуть задачу агенту | Только пользователь |
| 17 | Выполнить Copilot/reviewer review после ready | Copilot/reviewer |
| 18 | Прочитать Copilot/reviewer review и дать технический вердикт: готово к merge / нужны правки / нужен выбор пользователя | Агент |
| 19 | Выполнить merge в staging | Только пользователь |
| 20 | Проверить результат merge в staging | Агент |
| 21 | Проверить staging smoke или staging QA, если у агента есть доступ | Агент |
| 22 | Принять staging QA или риск | Пользователь или оператор |
| 23 | Открыть draft PR в main, если этот уровень достигнут | Агент |
| 24 | Проверить PR в main до ready: title/body и guard-поля; если пользователь вернул красный CI, разобрать логи и предложить исправления | Агент |
| 25 | Проверить CI PR в main; если всё ок, перевести PR из draft в ready; если есть ошибки, вернуть задачу агенту | Только пользователь |
| 26 | Выполнить Copilot/reviewer review PR в main после ready | Copilot/reviewer |
| 27 | Прочитать Copilot/reviewer review PR в main и дать технический вердикт: готово к merge / нужны правки / нужен выбор пользователя | Агент |
| 28 | Выполнить merge в main | Только пользователь |
| 29 | Запустить production deploy | Только пользователь |
| 30 | Проверить production smoke, если у агента есть доступ | Агент |
| 31 | Принять production результат или риск | Пользователь или оператор |
| 32 | Сверить все Issues из `Связанные задачи` с принятым результатом | Агент |
| 33 | Решить и выполнить действие по каждой Issue, затем опубликовать closure-запись на merged PR | Только пользователь |
| 34 | Выполнить применимый Spec Closure или зафиксировать `Spec Closure: not_required` с причиной | Агент после отдельной команды пользователя |
| 35 | Выполнить cleanup локальных веток/worktree | Агент |
| 36 | Удалить remote branch после merge | GitHub auto-delete или агент после явной команды пользователя и проверок |
| 37 | Изменить GitHub-настройки, repository rules, secrets или environments | Только пользователь |
| 38 | Проверить, что хвост закрыт | Агент |

Для docs/process path строки 32-34 выполняются после пользовательского merge и
проверки результата. При `Связанные задачи: не требуется` агент фиксирует
`Issue Closure: not_required`. Для `#NNN` пользователь фиксирует каждую Issue как
`closed` или `left_open` по `docs/task-delivery-workflow.md`; `left_open`
становится `issue/admin tail`.

Cleanup по строке 35 доступен только после
`Issue Closure: completed | not_required` и
`Spec Closure: completed | not_required`.

Если применимый `Spec Closure` требует изменения внешнего Spec repo, запись
файлов, commit и push остаются отдельными уровнями разрешения по
`ab-spec-workflow`; одна команда не разрешает следующие уровни автоматически.

Если пользователь выявил проблему CI до `ready`, он возвращает задачу агенту.
Если агент выявил проблему guard-полей, логов или pre-ready проверки, агент
предлагает исправление. Поток возвращается к локальной правке, commit, push,
обновлению `draft PR` и повторной пользовательской проверке CI до ready.

Если проблема выявлена после пользовательского `ready` через Copilot/reviewer
review, технический вердикт агента — `нужны правки`. Агент предлагает
исправление в текущем scope, но не переводит PR обратно в draft и не меняет
GitHub-статус. После fix commit/push поток повторяет CI, Copilot/reviewer review
и технический вердикт агента перед пользовательским merge.

Если проблема выявлена на smoke или QA после merge/deploy, агент предлагает
исправление или rollback/forward-fix вариант по текущему release-level и
запрашивает решение пользователя, если есть риск.

Технический вердикт агента по review:

- `готово к merge` — агент прочитал доступные review status, comments/threads и
  CI status, не видит blocking/actionable замечаний и не видит незакрытого риска,
  требующего решения пользователя;
- `нужны правки` — есть actionable замечание, которое нужно исправить до merge;
- `нужен выбор пользователя` — замечание связано с продуктовым решением, риском,
  спорным trade-off или доступом, которого у агента нет.

Если review status, comments/threads или CI status недоступны, неполны или
противоречат друг другу, агент не использует вердикт `готово к merge`.

Технический вердикт не является GitHub approve, dismiss review, request changes,
переводом статуса или merge.

Шаг `push ветки и открыть draft PR` выполняется агентом как один publish-шаг
только после решения пользователя о публикации текущего изменения.

## GitHub-контрольные действия

Следующие действия выполняет только пользователь:

| N | Действие |
|---|---|
| 1 | Перевести PR из draft в ready |
| 2 | Перевести PR обратно в draft |
| 3 | Выполнить merge PR |
| 4 | Закрыть или переоткрыть PR |
| 5 | Закрыть или переоткрыть Issue |
| 6 | Approve, request changes или dismiss review |
| 7 | Нажать GitHub UI-кнопку deploy, promote, approve environment |
| 8 | Менять branch protection, required checks или repository rules |
| 9 | Управлять GitHub secrets и environment variables |

Агент может читать состояние этих действий, объяснять следующий checkpoint и
проверять результат после того, как пользователь выполнил действие.

Исключение для branch cleanup: после явной команды пользователя агент может
удалить remote head branch уже слитого PR, если проверил, что PR имеет статус
`MERGED`, branch принадлежит этому PR, branch не является `main`, `staging`,
защищённой веткой, активным stream-ом или backup-веткой, и по branch нет другого
открытого PR. Если любой из этих признаков нельзя подтвердить read-only
проверкой, агент не удаляет remote branch и показывает blocker. PR, закрытый без
merge, считается blocker-ом branch cleanup для агента: агент показывает blocker и
ждёт действия пользователя, а remote branch удаляет только пользователь.
