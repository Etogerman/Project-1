# Алгоритм действий и исполнители

Этот документ фиксирует, кто выполняет шаги процесса доставки. Если рекомендация
агента противоречит этой таблице, таблица считается источником истины.

`Исполнитель` означает, кто физически выполняет действие. Решение перейти к
следующему контрольному уровню принимает пользователь или оператор, если это
требуется процессом.

## Правило меню

В пользовательском меню исполнитель должен соответствовать таблице. Агент не
указывает себя исполнителем пользовательских GitHub-контрольных действий.

Правильный формат, когда `draft` PR ждёт CI:

`1. Вы проверяете CI; если он зелёный, возвращаете задачу агенту для обязательной авторской самопроверки до ready. [вы]`

После завершённой авторской самопроверки:

`1. Вы переводите PR в ready, пишете "готово, проведи независимое ревью" и передаёте тот же PR стороннему ИИ-ревьюеру. [вы]`

Если PR уже `ready` и текущий `HEAD` делегирован обеим сторонам, правильный
следующий checkpoint:

`1. Агент и сторонний ИИ-ревьюер параллельно и независимо проверяют один HEAD. [я + сторонний ИИ-ревьюер]`

Если после делегации появился новый commit, сначала:

`1. Вы проверяете CI нового HEAD, повторно пишете "готово, проведи независимое ревью" и передаёте текущий HEAD стороннему ИИ-ревьюеру. [вы]`

Если обе проверки одного текущего `HEAD` уже закрыты и агенту доступны внешний
review, comments/threads и зелёный CI, правильный следующий checkpoint:

`1. Агент сопоставляет обе проверки и даёт сводный технический вердикт. [я]`

Если одна из проверок отсутствует, относится к другому `HEAD` либо review
status, comments/threads или CI status недоступны или неоднозначны, агент не
даёт вердикт `готово к merge` и запрашивает недостающие данные или решение
пользователя.

Если вердикт агента — `готово к merge`, правильный следующий GitHub-шаг:

`1. Вы выполняете merge. [вы]`

Запрещено показывать пункт меню, где исполнитель такого действия — агент.

| 1 | Сформулировать задачу, цель или проблему | Пользователь |
| 2 | Прочитать код, docs, PR, CI и текущее состояние | Агент |
| 3 | Определить тип работы и текущий workflow | Агент |
| 4 | Подготовить черновик ТЗ или уточнение scope | Агент |

| 6 | Реализовать локальное изменение по согласованному scope | Агент |
| 7 | Запустить локальные проверки, которые доступны агенту | Агент |
| 8 | Выполнить author self-check | Агент |
| 9 | Провести операторскую приёмку локального MVP | Пользователь или оператор |
| 10 | Принять решение о выкладке | Пользователь или оператор |
| 11 | Зафиксировать внешнее ТЗ, если оно требуется | Агент |
| 12 | Сделать commit | Агент |
| 13 | Сделать push ветки и открыть draft PR | Агент |
| 14 | Проверить title/body PR и guard-поля | Агент |

| 18 | Самостоятельно проверить текущий HEAD без предварительного чтения выводов стороннего ИИ-ревьюера; выполняется параллельно с шагом 19 | Агент |

| 27 | Выполнить обязательную авторскую самопроверку текущего HEAD PR в main до ready, проверить title/body и guard-поля | Агент |

| 32 | Выполнить merge в main | Только пользователь |
| 33 | Запустить production deploy | Только пользователь |
| 34 | Проверить production smoke, если у агента есть доступ | Агент |

| 39 | Выполнить cleanup локальных веток/worktree | Агент |
| 40 | Удалить remote branch после merge | GitHub auto-delete или агент после явной команды пользователя и проверок |
| 41 | Изменить GitHub-настройки, repository rules, secrets или environments | Только пользователь |
| 42 | Проверить, что хвост закрыт | Агент |

Routes/records — в `docs/task-delivery-workflow.md`: no-result требует отсутствия
materialization; cleanup ждёт оба checkpoint, `deferred` остаётся dormant tail.
Spec write/commit/push разрешаются раздельно.

Если пользователь выявил проблему CI до `ready`, он возвращает задачу агенту.
Если агент выявил проблему guard-полей, логов или pre-ready проверки, агент
предлагает исправление. Поток возвращается к локальной правке, commit, push,
обновлению `draft PR` и повторной пользовательской проверке CI до ready.

Если проблема выявлена после пользовательского `ready` любой из двух независимых
проверок, сводный технический вердикт агента — `нужны правки`. Агент предлагает
исправление в текущем scope, но не переводит PR обратно в draft и не меняет
GitHub-статус. После fix commit/push новый `HEAD` проходит CI, затем пользователь
подтверждает зелёный результат и явно делегирует обе проверки. После этого
повторяются самостоятельная проверка агента, проверка стороннего ИИ-ревьюера и
сводный технический вердикт перед пользовательским merge.

Если проблема выявлена на smoke или QA после merge/deploy, агент предлагает
исправление или rollback/forward-fix вариант по текущему release-level и
запрашивает решение пользователя, если есть риск.

Технический вердикт агента по review:

- `готово к merge` — обе независимые проверки завершены для одного текущего
  `HEAD`, агент прочитал внешний review, все актуальные comments/threads и CI
  того же commit, не видит blocking/actionable замечаний и не видит незакрытого
  риска, требующего решения пользователя;
- `нужны правки` — есть actionable замечание, которое нужно исправить до merge;
- `нужен выбор пользователя` — замечание связано с продуктовым решением, риском,
  спорным trade-off или доступом, которого у агента нет.

Если одна из независимых проверок отсутствует, относится к другому `HEAD` либо
review status, comments/threads или CI status недоступны, неполны или
противоречат друг другу, агент не использует вердикт `готово к merge`.

Технический вердикт не является GitHub approve, dismiss review, request changes,
переводом статуса или merge.

Шаг `push ветки и открыть draft PR` выполняется агентом как один publish-шаг
только после решения пользователя о публикации текущего изменения.

## GitHub-контрольные действия

Следующие действия выполняет только пользователь:

| N | Действие |
|---|---|
| 1 | Перевести PR из draft в ready |
| 2 | Перевести PR обратно в draft |
| 3 | Выполнить merge PR |
| 4 | Закрыть или переоткрыть PR/Issue |
| 5 | Approve, request changes или dismiss review |
| 6 | Нажать GitHub UI-кнопку deploy, promote, approve environment |
| 7 | Менять branch protection, required checks или repository rules |
| 8 | Управлять GitHub secrets и environment variables |
| 9 | Запросить проверку у стороннего ИИ-ревьюера |

Агент может читать состояние этих действий, объяснять следующий checkpoint и
проверять результат после того, как пользователь выполнил действие.

Исключение для branch cleanup: после обоих closure-checkpoint и явной команды пользователя агент может
удалить remote head branch уже слитого PR, если проверил, что PR имеет статус
`MERGED`, branch принадлежит этому PR, branch не является `main`, `staging`,
защищённой веткой, активным stream-ом или backup-веткой, и по branch нет другого
открытого PR. Если любой из этих признаков нельзя подтвердить read-only
проверкой, агент не удаляет remote branch и показывает blocker. Для PR,
закрытого без merge, terminal-route обязателен; remote branch удаляет только
пользователь либо сохраняет как dormant tail.
