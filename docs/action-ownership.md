# Алгоритм действий и исполнители

Этот документ фиксирует, кто выполняет шаги процесса доставки. Если рекомендация
агента противоречит этой таблице, таблица считается источником истины.

`Исполнитель` означает, кто физически выполняет действие. Решение перейти к
следующему контрольному уровню принимает пользователь или оператор, если это
требуется процессом.

## Правило меню

В пользовательском меню исполнитель должен соответствовать таблице. Агент не
указывает себя исполнителем пользовательских GitHub-контрольных действий.

Следующий блок меню относится к code/runtime PR в `staging` и `main`. Для
docs-only/process-only PR обязательный пакет двух проверок применяется только по
явному запросу пользователя.

Зафиксированный снимок PR состоит из полных `base SHA`, `head SHA` и SHA-256,
вычисленного по определению в `docs/workflow/shared/evidence-gateway.md`. Изменение любого
компонента создаёт новый снимок.

Правильный формат, когда `draft` code/runtime PR ждёт CI:

`1. Вы проверяете CI; если он зелёный для того же самопроверенного снимка, сразу переводите PR в ready, пишете "готово, проведи независимое ревью" и передаёте PR стороннему ИИ-ревьюеру с требованием самостоятельно зафиксировать строку Review snapshot. [вы]`

Если снимок изменился после авторской самопроверки, самопроверка не доказана или
`CI` красный/неоднозначный, пользователь возвращает задачу агенту. Сам факт
перехода `CI` в зелёный статус не требует отдельного вызова агента.

Если PR уже `ready` и текущий снимок делегирован обеим сторонам, правильный
следующий checkpoint:

`1. Агент и сторонний ИИ-ревьюер параллельно и независимо проверяют один снимок PR. [я + сторонний ИИ-ревьюер]`

Если после делегации изменились base, head, title или body, сначала:

`1. Вы проверяете применимый CI нового снимка, повторно пишете "готово, проведи независимое ревью" и передаёте тот же снимок стороннему ИИ-ревьюеру. [вы]`

Если обе незагрязнённые проверки одного текущего снимка PR уже закрыты и агенту доступны внешний
review, comments/threads и зелёный CI, правильный следующий checkpoint:

`1. Агент сопоставляет обе проверки и даёт сводный технический вердикт. [я]`

Если одна из проверок отсутствует, загрязнена, относится к другому снимку PR
либо review status, comments/threads или CI status недоступны или неоднозначны, агент не
даёт вердикт `готово к merge` и запрашивает недостающие данные или решение
пользователя.

Если агент увидел внешний review до фиксации собственных findings, его проверка
не засчитывается. Пользователь делегирует агентскую проверку новой изолированной
задаче/контексту, передавая только URL PR и строку `Review snapshot`.

Если вердикт агента — `готово к merge`, правильный следующий GitHub-шаг:

`1. Вы выполняете merge. [вы]`

Запрещено показывать пункт меню, где исполнитель такого действия — агент.

Для docs-only/process-only PR шаги 16–19 и 27–30 не являются обязательным
пакетом. Такой PR следует `docs-only path`: пользователь выбирает применимый
контур проверки и при зелёном `CI` переводит PR в `ready`. Применимые проверки
GitHub и выбранная проверка выполняются без автоматического возврата текущей
задачи Codex агенту. После их завершения пользователь передаёт задачу агенту
короткой командой `готово, проверь PR`; если применимых проверок нет, команда
отправляется сразу после `ready`. До этой команды ответственность за следующий
переход остаётся у пользователя; после команды — у агента. Агент проверяет
актуальное состояние текущего снимка PR, `CI`, выбранной проверки и всех
комментариев и обсуждений и даёт технический вердикт перед пользовательским
merge. Если пользователь явно запросил полный пакет, применяются те же
требования к снимку и независимости.

Routes/records — в `docs/task-delivery-workflow.md`: no-result требует отсутствия
materialization; cleanup ждёт оба checkpoint, `deferred` остаётся dormant tail.
Spec write/commit/push разрешаются раздельно.

## Исполнители цикла исправления открытого PR

Канонический исполнитель каждого состояния хранится в
[реестре состояний](workflow/pr-correction/states.json). Условия переходов и
границы действий определяет только модуль, который возвращает команда:

```bash
node .github/scripts/workflow-docs-check.mjs --state <ID>
```

Этот документ не повторяет каталог состояний. Неизменяемые границы ролей:

- агент собирает доказательства, квалифицирует сигнал, готовит delta-ТЗ,
  реализует разрешённое исправление и даёт технический вердикт;
- пользователь принимает решения по объёму/риску и выполняет GitHub-контрольные
  действия;
- GitHub выполняет CI;
- сторонний ИИ-ревьюер проверяет назначенный снимок независимо;
- владелец внешней системы выполняет явно назначенное операционное действие.

Каждая передача шага использует формат из
[входного документа цикла](workflow/pr-correction/README.md). Подтверждённая
code/runtime-правка проходит delta-ТЗ до реализации. Проблема smoke или QA
после merge возвращается в release-fix маршрут, а не в цикл открытого PR.

## GitHub-контрольные действия

Следующие действия выполняет только пользователь:

| N | Действие |
|---|---|
| 1 | Перевести PR из draft в ready |
| 2 | Перевести PR обратно в draft |
| 3 | Выполнить merge PR |
| 4 | Закрыть или переоткрыть PR/Issue |
| 5 | Approve, request changes или dismiss review |
| 6 | Нажать GitHub UI-кнопку deploy, promote, approve environment |
| 7 | Менять branch protection, required checks или repository rules |
| 8 | Управлять GitHub secrets и environment variables |
| 9 | Запросить проверку у стороннего ИИ-ревьюера |

Агент может читать состояние этих действий, объяснять следующий checkpoint и
проверять результат после того, как пользователь выполнил действие.

Исключение для branch cleanup: после обоих closure-checkpoint и явной команды пользователя агент может
удалить remote head branch уже слитого PR, если проверил, что PR имеет статус
`MERGED`, branch принадлежит этому PR, branch не является `main`, `staging`,
защищённой веткой, активным stream-ом или backup-веткой, и по branch нет другого
открытого PR. Если любой из этих признаков нельзя подтвердить read-only
проверкой, агент не удаляет remote branch и показывает blocker. Для PR,
закрытого без merge, terminal-route обязателен; remote branch удаляет только
пользователь либо сохраняет как dormant tail.
