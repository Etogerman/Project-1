# Алгоритм действий и исполнители

Этот документ фиксирует, кто выполняет шаги процесса доставки. Если рекомендация
агента противоречит этой таблице, таблица считается источником истины.

`Исполнитель` означает, кто физически выполняет действие. Решение перейти к
следующему контрольному уровню принимает пользователь или оператор, если это
требуется процессом.

## Правило меню

В пользовательском меню исполнитель должен соответствовать таблице. Агент не
указывает себя исполнителем пользовательских GitHub-контрольных действий.

Следующий блок меню относится к code/runtime PR в `staging` и `main`. Для
docs-only/process-only PR обязательный пакет двух проверок применяется только по
явному запросу пользователя.

Зафиксированный снимок PR состоит из полных `base SHA`, `head SHA` и SHA-256,
вычисленного по определению в `docs/task-delivery-workflow.md`. Изменение любого
компонента создаёт новый снимок.

Правильный формат, когда `draft` code/runtime PR ждёт CI:

`1. Вы проверяете CI; если он зелёный для того же самопроверенного снимка, сразу переводите PR в ready, пишете "готово, проведи независимое ревью" и передаёте PR стороннему ИИ-ревьюеру с требованием самостоятельно зафиксировать строку Review snapshot. [вы]`

Если снимок изменился после авторской самопроверки, самопроверка не доказана или
`CI` красный/неоднозначный, пользователь возвращает задачу агенту. Сам факт
перехода `CI` в зелёный статус не требует отдельного вызова агента.

Если PR уже `ready` и текущий снимок делегирован обеим сторонам, правильный
следующий checkpoint:

`1. Агент и сторонний ИИ-ревьюер параллельно и независимо проверяют один снимок PR. [я + сторонний ИИ-ревьюер]`

Если после делегации изменились base, head, title или body, сначала:

`1. Вы проверяете применимый CI нового снимка, повторно пишете "готово, проведи независимое ревью" и передаёте тот же снимок стороннему ИИ-ревьюеру. [вы]`

Если обе незагрязнённые проверки одного текущего снимка PR уже закрыты и агенту доступны внешний
review, comments/threads и зелёный CI, правильный следующий checkpoint:

`1. Агент сопоставляет обе проверки и даёт сводный технический вердикт. [я]`

Если одна из проверок отсутствует, загрязнена, относится к другому снимку PR
либо review status, comments/threads или CI status недоступны или неоднозначны, агент не
даёт вердикт `готово к merge` и запрашивает недостающие данные или решение
пользователя.

Если агент увидел внешний review до фиксации собственных findings, его проверка
не засчитывается. Пользователь делегирует агентскую проверку новой изолированной
задаче/контексту, передавая только URL PR и строку `Review snapshot`.

Если вердикт агента — `готово к merge`, правильный следующий GitHub-шаг:

`1. Вы выполняете merge. [вы]`

Запрещено показывать пункт меню, где исполнитель такого действия — агент.

## Общий алгоритм

| N | Действие | Исполнитель |
|---|---|---|
| 1 | Сформулировать задачу, цель или проблему | Пользователь |
| 2 | Прочитать код, docs, PR, CI и текущее состояние | Агент |
| 3 | Определить тип работы и текущий workflow | Агент |
| 4 | Подготовить черновик ТЗ или уточнение scope | Агент |
| 5 | Утвердить ТЗ, scope, приоритет или риск | Пользователь |
| 6 | Реализовать локальное изменение по согласованному scope | Агент |
| 7 | Запустить локальные проверки, которые доступны агенту | Агент |
| 8 | Выполнить author self-check | Агент |
| 9 | Провести операторскую приёмку локального MVP | Пользователь или оператор |
| 10 | Принять решение о выкладке | Пользователь или оператор |
| 11 | Зафиксировать внешнее ТЗ, если оно требуется | Агент |
| 12 | Сделать commit | Агент |
| 13 | Сделать push ветки и открыть draft PR | Агент |
| 14 | Выполнить авторскую самопроверку окончательного опубликованного снимка PR, проверить заголовок, описание и контрольные поля, зафиксировать `Review snapshot` | Агент |
| 15 | Проверить CI draft PR; при зелёном результате того же снимка перейти сразу к ready, при ошибке или неоднозначности вернуть задачу агенту | Только пользователь |
| 16 | Для code/runtime PR: перевести PR в ready, явно делегировать агенту независимую проверку и передать PR стороннему ИИ-ревьюеру с требованием самостоятельно зафиксировать строку `Review snapshot` | Только пользователь |
| 17 | Для code/runtime PR: самостоятельно проверить текущий снимок без предварительного чтения выводов стороннего ИИ-ревьюера; выполняется параллельно с шагом 18 | Агент |
| 18 | Для code/runtime PR: независимо проверить тот же снимок; выполняется параллельно с шагом 17 | Сторонний ИИ-ревьюер |
| 19 | Для code/runtime PR: сопоставить обе незагрязнённые проверки, актуальные comments/threads и CI одного снимка; дать сводный вердикт: готово к merge / нужны правки / нужен выбор пользователя | Агент |
| 20 | Выполнить merge в staging | Только пользователь |
| 21 | Проверить результат merge в staging | Агент |
| 22 | Проверить staging deploy-check, staging smoke и staging QA, если у агента есть доступ | Агент |
| 23 | Принять staging QA или риск | Пользователь или оператор |
| 24 | Открыть draft PR в main, если этот уровень достигнут | Агент |
| 25 | Выполнить авторскую самопроверку окончательного опубликованного снимка PR в main, проверить заголовок, описание и контрольные поля, зафиксировать `Review snapshot` | Агент |
| 26 | Проверить CI PR в main; при зелёном результате того же снимка перейти сразу к ready, при ошибке или неоднозначности вернуть задачу агенту | Только пользователь |
| 27 | Для code/runtime PR: перевести PR в ready, явно делегировать агенту независимую проверку и передать PR стороннему ИИ-ревьюеру с требованием самостоятельно зафиксировать строку `Review snapshot` | Только пользователь |
| 28 | Для code/runtime PR: самостоятельно проверить текущий снимок PR в main без предварительного чтения выводов стороннего ИИ-ревьюера; выполняется параллельно с шагом 29 | Агент |
| 29 | Для code/runtime PR: независимо проверить тот же снимок PR в main; выполняется параллельно с шагом 28 | Сторонний ИИ-ревьюер |
| 30 | Для code/runtime PR: сопоставить обе незагрязнённые проверки, актуальные comments/threads и CI одного снимка; дать сводный вердикт: готово к merge / нужны правки / нужен выбор пользователя | Агент |
| 31 | Выполнить merge в main | Только пользователь |
| 32 | Запустить production deploy | Только пользователь |
| 33 | Проверить production smoke, если у агента есть доступ | Агент |
| 34 | Принять production результат или риск | Пользователь или оператор |
| 35 | Определить result/no-result route и сверить Issues/evidence | Агент |
| 36 | Выбрать terminal outcome при необходимости, решить Issues и опубликовать records | Только пользователь |
| 37 | Выполнить Spec Closure или записать `not_required` с причиной | Агент после отдельной команды пользователя |
| 38 | Выполнить cleanup локальных веток/worktree | Агент |
| 39 | Удалить remote branch после merge | GitHub auto-delete или агент после явной команды пользователя и проверок |
| 40 | Изменить GitHub-настройки, repository rules, secrets или environments | Только пользователь |
| 41 | Проверить, что хвост закрыт | Агент |

Для docs-only/process-only PR шаги 16–19 и 27–30 не являются обязательным
пакетом. Такой PR следует `docs-only path`: пользователь выбирает применимый
review-контур, агент по отдельной команде проверяет результат и даёт технический
вердикт перед пользовательским merge. Если пользователь явно запросил полный
пакет, применяются те же требования к снимку и независимости.

Routes/records — в `docs/task-delivery-workflow.md`: no-result требует отсутствия
materialization; cleanup ждёт оба checkpoint, `deferred` остаётся dormant tail.
Spec write/commit/push разрешаются раздельно.

Если пользователь выявил проблему CI до `ready`, он возвращает задачу агенту.
Если агент выявил проблему guard-полей, логов или pre-ready проверки, агент
предлагает исправление. Поток возвращается к локальной правке, commit, push,
обновлению `draft PR` и повторной пользовательской проверке CI до ready.

Если проблема выявлена после пользовательского `ready` любой из двух независимых
проверок, сводный технический вердикт агента — `нужны правки`. Агент предлагает
исправление в текущем scope, но не переводит PR обратно в draft и не меняет
GitHub-статус. После fix commit/push формируется новый снимок PR и проходит
применимый CI, затем пользователь подтверждает результат и явно делегирует обе
проверки. После этого
повторяются самостоятельная проверка агента, проверка стороннего ИИ-ревьюера и
сводный технический вердикт перед пользовательским merge.

Если проблема выявлена на smoke или QA после merge/deploy, агент предлагает
исправление или rollback/forward-fix вариант по текущему release-level и
запрашивает решение пользователя, если есть риск.

Технический вердикт агента по review:

- `готово к merge` — обе незагрязнённые независимые проверки завершены для
  одного текущего снимка PR, агент прочитал внешний review, все актуальные
  comments/threads и актуальный CI, не видит blocking/actionable замечаний и не видит незакрытого
  риска, требующего решения пользователя;
- `нужны правки` — есть actionable замечание, которое нужно исправить до merge;
- `нужен выбор пользователя` — замечание связано с продуктовым решением, риском,
  спорным trade-off или доступом, которого у агента нет.

Если одна из независимых проверок отсутствует, загрязнена, относится к другому
снимку PR либо review status, comments/threads или CI status недоступны, неполны или
противоречат друг другу, агент не использует вердикт `готово к merge`.

Технический вердикт не является GitHub approve, dismiss review, request changes,
переводом статуса или merge.

Шаг `push ветки и открыть draft PR` выполняется агентом как один publish-шаг
только после решения пользователя о публикации текущего изменения.

## GitHub-контрольные действия

Следующие действия выполняет только пользователь:

| N | Действие |
|---|---|
| 1 | Перевести PR из draft в ready |
| 2 | Перевести PR обратно в draft |
| 3 | Выполнить merge PR |
| 4 | Закрыть или переоткрыть PR/Issue |
| 5 | Approve, request changes или dismiss review |
| 6 | Нажать GitHub UI-кнопку deploy, promote, approve environment |
| 7 | Менять branch protection, required checks или repository rules |
| 8 | Управлять GitHub secrets и environment variables |
| 9 | Запросить проверку у стороннего ИИ-ревьюера |

Агент может читать состояние этих действий, объяснять следующий checkpoint и
проверять результат после того, как пользователь выполнил действие.

Исключение для branch cleanup: после обоих closure-checkpoint и явной команды пользователя агент может
удалить remote head branch уже слитого PR, если проверил, что PR имеет статус
`MERGED`, branch принадлежит этому PR, branch не является `main`, `staging`,
защищённой веткой, активным stream-ом или backup-веткой, и по branch нет другого
открытого PR. Если любой из этих признаков нельзя подтвердить read-only
проверкой, агент не удаляет remote branch и показывает blocker. Для PR,
закрытого без merge, terminal-route обязателен; remote branch удаляет только
пользователь либо сохраняет как dormant tail.
