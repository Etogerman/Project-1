# Работа с ТЗ и внешним Spec

Этот skill помогает работать с ТЗ, внешним репозиторием документации, `Spec doc`
и `Spec revision` для AB Connector.

По умолчанию skill работает read-only: помогает найти, проверить или подготовить
ТЗ, но не меняет файлы, git-состояние и внешние репозитории.

## Режимы работы

`Проверить или подготовить` — read-only режим. Агент может анализировать,
готовить черновик ТЗ в чате, критиковать ТЗ и показывать расхождения.

`Записать или зафиксировать` — write-режим. Допустим только по явной команде
пользователя. Этот режим может менять внешний Spec repo, но не основной repo без
отдельного разрешения.

Команда на подготовку ТЗ не означает разрешение записать его в файл.
Команда на запись во внешний Spec repo не означает разрешение на commit.
Команда на commit во внешнем Spec repo не означает разрешение на push.

У write-режима есть отдельные уровни:

1. `Записать файлы во внешний Spec repo` — меняет только выбранные файлы внешнего
   repo и оставляет локальный diff.
2. `Сделать commit во внешнем Spec repo` — фиксирует уже проверенный diff внешнего
   repo.
3. `Опубликовать push внешнего Spec repo` — отправляет уже созданный commit во
   внешний GitHub repo.

Каждый уровень требует отдельной явной команды пользователя.

## Границы

Skill не меняет код, конфиги, тесты, runtime-окружения и git-состояние основного
репозитория.

Skill не сохраняет полное ТЗ в основном репозитории.

Skill не обновляет `docs/reference/active-specs.md` автоматически после изменения
внешнего Spec.

Skill не выбирает “правильную” версию молча, если код, чат, локальные документы и
внешний Spec расходятся.

Skill не делает commit, push или PR без отдельной явной команды пользователя.

Изменение внешнего Spec repo считается изменением source of truth и требует
отдельного разрешения, проверки хвоста и отчёта о статусе.

Перед любой записью во внешний Spec repo проверь его ветку, рабочее состояние и
незавершённые хвосты. Если есть незакоммиченные, незапушенные или непонятные
изменения, которые не относятся к текущей задаче, остановись и покажи их
пользователю. Не добавляй в commit чужие или несвязанные файлы.

## Когда использовать

Используй этот skill, если вопрос связан с:

- ТЗ текущего stream-а;
- черновиком ТЗ;
- внешним репозиторием документации;
- `Spec repo`;
- `Spec doc`;
- `Spec revision`;
- substantial stream;
- `Spec pending`;
- `spec/admin tail`;
- `docs/reference/active-specs.md`;
- расхождением между кодом, локальными документами и внешним ТЗ;
- подготовкой stream к publish/release boundary.

## Источники

Используй активные правила:

1. `AGENTS.md`
2. `docs/task-delivery-workflow.md`
3. `docs/reference/active-specs.md`
4. внешний репозиторий документации

Если `docs/agent-routing.md` или `docs/agent-docs-lifecycle.md` существуют только
как локальные черновики, скажи об этом и не используй их как активные правила.

Стандартный внешний репозиторий документации:

```text
GitHub: Etogerman/Project-1-specs
Local path: /Users/abrikosov/Documents/Project-1-specs
```

Если внешний репозиторий документации недоступен, substantial stream ставится на
паузу перед publish/release действием.

Если пользователь просит сохранить, записать или зафиксировать полное ТЗ, а
стандартный внешний репозиторий документации недоступен, не создавай заменитель в
основном repo и не придумывай временный путь. Остановись и запроси целевой
репозиторий или доступ к стандартному внешнему repo.

## Классификация ТЗ

Определи тип ситуации:

- мелкое локальное исправление;
- локальный режим до `Локального MVP`;
- substantial stream;
- срочный hotfix со статусом `Spec pending`;
- publish/release boundary;
- spec/admin cleanup;
- закрытие или архивирование Spec doc.

Для мелкого локального исправления ТЗ может оставаться в чате.

Для substantial stream до операторского решения о выкладке допустим черновик ТЗ в
чате или в явно указанном локальном месте вне основного репозитория и вне
внешнего репозитория документации.

Перед первым publish/release действием substantial stream требует:

- `Spec repo`;
- `Spec doc`;
- `Spec revision`.

`Spec revision` появляется только после commit, который меняет сам `Spec doc` во
внешнем Spec repo. До этого можно говорить только о черновике Spec doc или
будущем Spec doc.

## Черновик ТЗ

При подготовке ТЗ сначала работай в read-only режиме.

Черновик ТЗ должен фиксировать:

- цель;
- границы;
- что меняется;
- что не меняется;
- затронутую область изменений;
- активный slice;
- критерий `Локального MVP`;
- критерии приёмки;
- основную среду проверки;
- риски;
- двусмысленности;
- уровень делегации.

Если задача шире одного безопасного шага, опиши крупные фазы кратко, а текущий
активный slice подробно.

## Критика ТЗ

Перед финализацией проверь ТЗ как reviewer:

- соответствует ли оно коду и архитектуре;
- не смешивает ли несколько stream-ов;
- достаточно ли ясен `Локальный MVP`;
- можно ли честно проверить результат локально;
- не используется ли staging как первая среда проверки;
- есть ли integration/runtime риск;
- не нужен ли внешний versioned Spec до следующего шага;
- не расходится ли ТЗ с текущим кодом или уже активным Spec doc.

Если есть расхождение между кодом, чатом, локальными документами и внешним ТЗ,
покажи расхождение пользователю. Не выбирай правильную версию молча.

## Запись во внешний Spec

Этот раздел применяется только в режиме `Записать или зафиксировать`.

Если пользователь явно просит сохранить, записать или зафиксировать полное ТЗ,
используй стандартный внешний репозиторий документации, если пользователь не
указал другой.

При записи во внешний Spec:

1. проверь branch, git status и хвосты внешнего repo;
2. если рабочее состояние внешнего repo чистое или содержит только согласованный
   хвост текущей задачи, выбери логичный `Spec doc` в `streams/` по структуре
   внешнего repo;
3. обнови сам `Spec doc`;
4. обнови `streams/README.md`, если структура внешнего repo этого требует;
5. обнови `active-streams.md`, если stream реально открыт;
6. коротко сообщи практический статус изменения; список файлов, diff и технические детали показывай только по запросу пользователя, при риске или неоднозначности;
7. commit во внешнем repo выполняй только по отдельному разрешению;
8. push во внешний GitHub repo выполняй только по отдельному разрешению после
   commit.

`Spec revision` двигается только commit-ом, который меняет сам `Spec doc`.
Коммиты, меняющие только индексы или реестры, `Spec revision` не меняют.

## Active specs в основном repo

`docs/reference/active-specs.md` хранит только stream-level ссылку на уже открытый
substantial stream.

Он не заменяет внешний Spec repo и не хранит полное ТЗ.

Обновление `docs/reference/active-specs.md` в основном repo — отдельное docs-only
изменение. Оно не происходит автоматически после изменения внешнего Spec и требует
отдельного разрешения пользователя.

## Publish/release boundary

Перед publish/release действием проверь:

- внешний repo доступен;
- `Spec doc` существует;
- `Spec revision` указан конкретным commit/hash;
- статус stream-а во внешнем repo согласован;
- `active-streams.md` и `streams/README.md` не противоречат `Spec doc`;
- основной repo не хранит полное ТЗ вместо внешнего Spec.

К publish/release действиям относятся ready, merge, staging, VPS, секреты,
миграции, deploy, smoke внешней среды и действия во внешних системах.

Для срочного hotfix пользователь может явно разрешить ранний push branch и draft
PR в `staging` как `Spec pending`.

`Spec pending` разрешает только ранний draft PR в `staging` для CI/review. Он не
разрешает ready, merge, deploy, smoke, секреты и миграции без зафиксированного
`Spec revision`.

## Результат

Верни короткий отчёт:

- режим: read-only или write;
- тип ТЗ-ситуации;
- substantial stream: да или нет;
- текущий источник ТЗ;
- нужен ли внешний Spec сейчас;
- `Spec repo`;
- `Spec doc`;
- `Spec revision`;
- найденные расхождения;
- spec/admin tail;
- практический статус изменения, если был write-режим;
- следующий допустимый шаг;
- требуется ли отдельная команда пользователя.
