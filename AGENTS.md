# AB Connector: конституция агента

Этот файл содержит только правила, обязательные для любой задачи. Детали
загружаются пошагово через `docs/workflow/README.md`; агент не читает весь
delivery-playbook без необходимости.

## Универсальные инварианты

1. Общение с пользователем, commit messages, заголовки и описания PR и
   человекочитаемые GitHub-комментарии ведутся на русском языке, кроме команд,
   путей, имён инструментов и терминов без точного перевода.
2. Перед работой агент открывает `docs/workflow/README.md`, определяет тип
   потока, текущий этап, предел полномочий и только необходимые модули.
3. Без явной команды пользователя на реализацию и согласованного ТЗ агент не
   меняет код, конфигурацию, тесты, документацию, git-состояние и окружения.
   Анализ, review, критика, план и подготовка ТЗ выполняются только для чтения.
4. Локальная правка, commit, push, PR, внешняя мутация и deploy — отдельные
   уровни полномочий. Разрешение одного уровня не разрешает следующий.
5. По умолчанию активен один существенный code/release stream. Перед новым
   stream проверяются хвосты и точная рабочая копия; изменения разных worktree
   не смешиваются молча.
6. При неоднозначности агент сначала исчерпывает безопасный сбор фактов. Затем
   фиксирует точную блокировку, решение пользователя или состояние процесса;
   безымянное ожидание запрещено.
7. Каждый законченный slice завершается авторской проверкой. Смысловая,
   рискованная и публикационная граница требует полной авторской проверки.
8. Существенный stream до внешней публикации имеет зафиксированные `Spec repo`,
   `Spec doc` и `Spec revision`. Полные живые ТЗ не хранятся в основном repo.
9. Новый code stream по умолчанию идёт через локальный MVP и операторскую
   приёмку, затем staging-first rollout. Зелёные тесты не заменяют приёмку.
10. Перед операторской приёмкой агент доказывает идентичность runtime: URL,
    процесс/контейнер, worktree, ветку, commit и совпадающий UI `rev` marker.
11. Любой нетривиальный PR создаётся как draft. GitHub-контрольные действия
    ready/draft, merge, approve/request changes/dismiss, repository rules,
    secrets и environment approvals выполняет только пользователь.
12. Для code/runtime PR после ready агент и сторонний ИИ независимо проверяют
    один зафиксированный снимок. Изменение base/head/title/body обнуляет пакет.
13. Красный/неоднозначный CI, замечание review, обсуждение, ошибка guard,
    метаданных или авторской проверки открывает `C01` канонического цикла
    исправления. Подтверждённая code/runtime-правка проходит delta-ТЗ до кода.
14. Агент рекомендует точный следующий этап текущего потока, а не удобный общий
    git-шаг. Если действие требует новой команды, это указывается отдельно.
15. После materialized result обязательны применимые Issue Closure, Spec Closure
    и cleanup; закрытие Issue и merge выполняет пользователь.

## Обязательная пошаговая загрузка

1. Открыть `docs/workflow/README.md`.
2. Для любого изменяющего действия прочитать
   `docs/workflow/shared/work-authority.md`.
3. Открыть только профильный модуль, указанный маршрутизатором.
4. Для состояния цикла PR выполнить:

   ```bash
   node .github/scripts/workflow-docs-check.mjs --state <ID>
   ```

5. Общий `docs/task-delivery-workflow.md` открывать только для этапа, который
   ещё не вынесен в модуль.

## Передача шага пользователю

Ответ начинается с результата или следующего действия. Меню используется
только при реальном выборе, запросе разрешения, блокировке или handoff:

```text
МЕНЮ
1. Первый конкретный вариант. [исполнитель]
2. Второй конкретный вариант. [исполнитель]
3. Третий конкретный вариант. [исполнитель]

Рекомендую выбрать: <номер>

Почему: <краткое обоснование>
```

Если существует один точный следующий шаг, агент сообщает его прямо без
фиктивного меню.
