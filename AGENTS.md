# Abrikosoff Connector

## Критичные правила для агента

Термины:
- `ТЗ` — согласованный контракт текущего stream. Для мелких локальных исправлений ТЗ может фиксироваться в чате. Для существенных stream-ов ТЗ хранится во внешнем spec-repo.
- `Spec repo` — внешний репозиторий с versioned ТЗ.
- `Spec doc` — конкретный документ во внешнем spec-repo.
- `Spec revision` — конкретный commit/hash внешнего ТЗ, на который опирается implementation stream.
- `Активный slice` — внутренний инженерный подшаг текущего stream-а. Slice может быть меньше пользовательски видимого результата и сам по себе не является trigger-ом выхода в `staging`.
- `Локальный MVP` — минимальный локально тестируемый feature increment текущего stream-а. Это состояние, в котором основной пользовательский сценарий уже можно честно проверить end-to-end в локальном контуре. По умолчанию именно `Локальный MVP` является trigger-ом перехода из локалки в `staging`.
- `Хвост` — незавершённые обязательства текущего или предыдущего stream: локальный diff, незапушенные изменения, открытый PR, незавершённый CI, незавершённый `staging`/`main` path, cleanup или другой follow-up.

Базовые правила:
1. Без явной команды пользователя на реализацию и без согласованного ТЗ агент не меняет код, конфиги, тесты, документацию, git-состояние и окружения.
2. Если пользователь просит анализ, review, критику, сравнение вариантов, план или подготовку ТЗ, агент работает только в read-only режиме.
3. По умолчанию одновременно допускается только один активный substantial code/release stream; параллельно с ним без отдельного exception допускаются только `docs-only/spec/admin` stream, `spec/admin tail`, cleanup или другой документальный follow-up уже завершённого stream-а, если они не затрагивают runtime/code diff и не поднимают execution ceiling текущего code/release stream-а.
4. Перед новым code/release stream агент обязан проверить хвост предыдущего implementation stream; если хвост substantial stream не закрыт, новый substantial code/release stream по умолчанию не начинается.
5. Исключение для второго параллельного code stream возможно только по отдельному явному решению пользователя после перечисления хвоста и связанных рисков и только если одновременно выполнены все условия:
   - явно зафиксировано, какой stream `primary`, а какой `secondary`
   - нет общего `staging` / deploy blocker
   - нет пересечения по rollout, ownership и delivery-path
   - у `secondary` stream есть отдельный active slice и отдельный execution ceiling
   - `secondary` stream не маскирует незакрытый runtime/release tail `primary` stream-а
6. Любой нетривиальный `PR` сначала создаётся как `draft`.
7. После зелёного `CI` на `draft` PR агент останавливается на отдельной контрольной точке перед переводом в `ready`.
8. После перевода PR в `ready` агент снова останавливается на отдельной контрольной точке перед `merge`.
9. Уровень `PR в staging` не включает `merge` в `staging`, staging smoke, PR в `main` и `merge` в `main`.
10. Если пользователь спрашивает о следующем логичном и правильном шаге, агент называет следующий delivery-уровень потока, если текущий уровень уже закрыт и blocker-ов нет.
11. Если следующий delivery-уровень требует отдельной явной делегации, агент рекомендует именно этот шаг процесса и отдельно указывает, что для исполнения нужна команда пользователя.
12. Если по ходу работы появляется двусмысленность, blocker, scope drift или нехватка данных, агент обязан остановиться и запросить следующий шаг.
13. Короткое меню с пронумерованными вариантами следующих действий обязательно только на точке handoff к пользователю: когда агент ждёт ответ, выбор, разрешение, дошёл до контрольной точки или упёрся в blocker. Если нужен один точный ответ без реальных вариантов выбора, агент задаёт один прямой вопрос без меню. Когда меню показано, формат рекомендации: `Рекомендация: 1. ...` и отдельной строкой `Почему: ...`.
14. Подробный delivery-playbook, уровни делегации и procedural flow описаны в `docs/task-delivery-workflow.md`; `AGENTS.md` фиксирует только верхнеуровневые рамки, инварианты и ограничения.
15. Существенный stream по умолчанию требует versioned ТЗ во внешнем spec-repo до продолжения code stream.
16. Перед продолжением реализации для существенного stream-а должны быть явно зафиксированы `Spec repo`, `Spec doc` и `Spec revision`. Если внешний spec-repo, нужный `Spec doc` или согласованная `Spec revision` недоступны, существенный stream ставится на паузу и не продолжается по памяти.
17. Основной репозиторий хранит код, process-docs, policy-docs, reference-docs и ссылки на внешние ТЗ.
18. Полные ТЗ для существенных stream-ов запрещено сохранять в основном репозитории в любых каталогах, включая `docs/`, `.tools/`, временные локальные папки и игнорируемые файлы.
19. До фиксации во внешнем spec-repo полное ТЗ может существовать только как временный draft в чате.
20. В основном репозитории допускаются только короткие ссылки, указатели и reference-записи на внешний `Spec repo`, `Spec doc` и `Spec revision`, но не полный текст stream-ТЗ.
21. Если пользователь просит сохранить, записать или зафиксировать полное ТЗ, агент не выбирает destination самостоятельно. Если путь к `spec-repo`, `Spec doc` или другой явный внешний destination не передан, агент обязан остановиться и запросить его.
22. Отсутствие явного destination для сохранения полного ТЗ считается blocker-ом и двусмысленностью. В этом случае агент не создаёт локальные файлы-заменители и не придумывает временный путь в основном репозитории.
23. Если код, локальные документы и внешнее ТЗ расходятся, агент сначала показывает расхождение пользователю и не придумывает «правильную» версию молча.
24. Каждый slice заканчивается обязательным `author self-check`.
25. Завершение отдельного slice само по себе не означает готовность к выходу в `staging`.
26. Для нового code stream default trigger перехода из локалки в `staging` — достижение согласованного `Локального MVP`, если пользователь явно не решил иначе.
27. `Решение пользователя` может явно разрешить более ранний или более поздний переход в `staging`, но такое решение считается override относительно default-правила, а не его заменой.
28. Полная реализация ТЗ считается корректным trigger-ом перехода в `staging` только если текущее ТЗ мало и само совпадает с одним локально тестируемым feature increment-ом.
29. Полный `formal self-review` выполняется не после каждого micro-slice, а на boundary points.
30. Boundary point считается наступившим, если slice:
   - завершает смысловую единицу
   - выводит diff на внешний publish-уровень
   - меняет delivery-уровень
   - затрагивает рискованный runtime/data-flow/integration контур
31. Для code stream `formal self-review` обязателен:
   - перед внешней публикацией
   - после зелёного `CI` на `draft` PR
   - после перевода PR в `ready` и перед `merge`
32. Helper-review для code stream выполняется на boundary points, если среда и разрешения это поддерживают.
33. Если пользователь спрашивает `какой следующий логичный и правильный шаг?`, агент обязан рекомендовать следующий шаг процесса, если текущая контрольная точка закрыта, acceptance выполнен и blocker-ов нет.
34. Контрольная точка ограничивает исполнение, но не подменяет собой следующий шаг процесса.
35. Формулировка `Остановиться на контрольной точке` используется как рекомендация только если:
   - есть blocker
   - acceptance текущей точки не закрыт
   - следующий шаг выходит за согласованный execution ceiling
   - для продолжения не хватает данных
   - пользователь сам хочет паузу
36. Если следующий шаг требует отдельной команды пользователя, агент рекомендует именно этот следующий шаг процесса и отдельной строкой указывает: `Для исполнения нужна команда пользователя.`
37. Для Abrikosoff Connector production release code/runtime stream-а включает ручной production deploy после `merge` в `main`.
38. Если пользователь спрашивает о следующем логичном и правильном шаге после `merge` в `main` для code/release stream, агент рекомендует `Ручной production deploy`.
39. После завершённого production deploy для code/release stream следующим шагом процесса считается `Production Post-Deploy Smoke` по `docs/post-deploy-smoke.md`.
40. Статус dangerous op ограничивает исполнение, но не подменяет собой рекомендацию следующего шага процесса.
41. Перед рекомендацией следующего шага агент сначала определяет workflow текущего active stream по фактическому write-set, статусу согласованного `Локального MVP` и целевому delivery-path.
42. Рекомендация следующего шага строится по текущему active stream и статусу `Локального MVP`, а не по имени ветки, истории предыдущего stream или прошлому delivery-контуру.
43. Перед рекомендацией следующего delivery-шагa агент обязан назвать точный delivery-level из `docs/task-delivery-workflow.md` и не имеет права выводить шаг из общей топологии веток или заменять именованный этап общим git-ярлыком вроде `staging -> main`.
44. Для уровня `до merge в main` агент обязан явно проговаривать, что `draft PR` в `main` строится из `validated diff` текущего active stream, а не из состояния ветки `staging`.
45. Если текущий active stream удовлетворяет условиям `docs-only path`, агент рекомендует следующий шаг только из `docs-only path`.
46. Если текущий `docs-only` diff находится на ветке или в worktree с более ранней историей другого stream-а, следующим правильным шагом считается clean branch/worktree от `origin/main` с переносом только текущего `docs-only` diff.
47. После любого локального изменения файлов агент обязан явно сообщить:
   - какие файлы изменены
   - опубликованы ли изменения или остаются только локальным diff
   - является ли это новым хвостом stream-а
48. Если согласованный `Локальный MVP` достигнут, acceptance локального контура закрыт и blocker-ов нет, агент обязан рекомендовать следующий delivery-шаг процесса, а не останавливаться на констатации локального статуса.
49. Для docs-only, policy-only и reference-only изменений следующим шагом по умолчанию считается отдельный docs-only stream: commit -> draft PR, если пользователь явно не выбрал revert, pause или отказ от публикации.
50. Если публикация требует отдельной команды пользователя, агент всё равно обязан назвать именно следующий publish-шаг и отдельно указать: `Для исполнения нужна команда пользователя.`
51. Для любого нового code stream, кроме `docs-only` stream и явно разрешённого пользователем direct-to-main exception, normal default rollout path: `локальная реализация до локального MVP -> draft PR в staging -> ready/merge в staging -> staging smoke -> draft PR в main -> ready/merge в main -> production deploy -> production smoke`.
52. Этот rollout path не расширяет execution ceiling текущей делегации. Если пользователь просто сказал `реализовать` для нового code stream, агент по умолчанию доводит его до согласованного `Локального MVP`, а ближайший внешний publish-level после этого — `draft PR в staging`; `ready`, `merge`, `staging smoke`, `PR в main`, `merge` в `main`, `production deploy` и `production smoke` требуют отдельной явной делегации, если иное заранее не согласовано.
53. Первый внешний publish-level для нового code stream по умолчанию — `staging`. Прямой `PR` в `main` для нового code stream запрещён без отдельной явной команды пользователя.
54. Агент не имеет права самовольно переориентировать уже согласованный staging-first stream на main-first только потому, что `main` ближе к production runtime, выглядит свежее или кажется удобнее для сборки diff.
55. Если локальная реализация закрыла отдельный slice, но согласованный `Локальный MVP` ещё не достигнут, это само по себе не считается основанием для выхода в `staging` без отдельного решения пользователя.
56. Truth текущего runtime используется для анализа и диагностики, но не отменяет staging-first rollout после достижения `Локального MVP`.
57. Для мелкого publishable fix chat-only ТЗ остаётся допустимым, если stream не признан существенным; staging-first rollout после `Локального MVP` сам по себе не делает любой новый code stream существенным stream-ом.
58. Если пользователь не сказал иное, формулировка `реализовать` для нового code stream означает: локально довести текущую задачу до согласованного `Локального MVP`, а дальше двигаться по staging-first rollout path в рамках текущего execution ceiling.
59. Существенный stream не считается полностью закрытым, пока не синхронизирован обязательный spec-контур: статус `Spec doc` и канонический статус в `streams/README.md`. Локальный `docs/reference/active-specs.md` остаётся stream-level реестром и обновляется в том же открывающем/закрывающем шаге или отдельным `docs-only` fallback, но не требует отдельного PR по умолчанию.
60. Если acceptance существенного stream-а уже материализован в основном repo, соответствующий `Spec doc` не может оставаться в статусе `planned`.
61. Если acceptance `Spec doc` закрыт, но перенос документа в `archive/` выполняется отдельным шагом, документ обязан быть помечен как минимум `implemented`, а архивный перенос считается явным `docs-only` follow-up.
62. Перед стартом нового несвязанного существенного code stream-а агент обязан проверить, не осталось ли `spec/admin tail` от предыдущего существенного stream-а: `spec status`, `streams/README`, `active-specs.md` или `archive pending`. Такой хвост перечисляется явно и не скрывается молча. Сам по себе он не подменяет runtime/release blocker и не запрещает unrelated `docs-only` шаг или малый локальный maintenance step, если пользователь явно не делает его частью нового substantial stream.

## Стиль взаимодействия

1. Ответ начинается с текущего действия, результата или следующего шага.
2. Меню используется только на точке handoff к пользователю, а не в обычных рабочих updates и commentary-сообщениях.
3. Если нужен один точный факт или одно короткое решение без реальных вариантов выбора, агент задаёт один прямой вопрос без меню.
4. Если выбор уже сделан пользователем, обычные рабочие updates идут без меню до следующей реальной точки handoff.
5. Формулировки строятся через желаемое действие, целевое состояние и практический следующий шаг.
6. Коммуникация остаётся короткой, прямой и полезной для движения задачи.

## Архитектурные и доменные инварианты

Архитектура:
- проект — прагматичный Laravel-монолит
- transport-логика остаётся локализованной в сервисных классах
- критичная бизнес-логика живёт вне контроллеров и UI
- ветвление по провайдерам делается через `match($channel->platform)` в сервисах
- общий интерфейс провайдера — преждевременная абстракция, пока не появится третий провайдер или реальная проблема с дублированием

Рабочий UI-принцип:
- `Contact` — обзорная карточка клиента и ownership-сущность
- `Dialog` — канальный thread и основное рабочее место оператора
- ownership остаётся на `Contact`, не на `Dialog`

Стабильные доменные инварианты:
- `Dialog` уникален на пару `[contact_id, channel_id]`
- `Dialog` хранит route context канала и используется как точка точного manual reply route
- `Message.provider_event_key` участвует в идемпотентности сообщений
- active collector имеет приоритет над обычным auto-reply
- collector progression идёт по зафиксированному flow, с максимум двумя попытками на поле и мягким skip после исчерпания попыток
- `region` — канонический российский business-region для фильтров, а не обязательно административный субъект
- `distance_to_moscow_*` — best-effort квалификационное поле только для России; считается асинхронно, не управляет progression collector-а и для ambiguous-city кейсов запускается только после подтверждения `region`
- live bridge Bitrix24 идёт через `Dialog` / `Message`; missed inbound recovery допустим только внутри подтверждённого Open Lines happy-path

## Критичные интеграционные и конфигурационные инварианты

- `config/bots.php` — источник платформенных настроек, текстов phone capture / collector и Gemini settings
- `config/bitrix24.php` — источник callback URL, интеграционных настроек Bitrix24 и rate-limit правил публичных callback endpoints
- `config/russian_region_cities.php` — deterministic source of truth для `российский город -> exact candidate regions` и geocode hints
- `config/services.php` хранит настройки `yandex_geocoder` и reference point для Москвы
- `BITRIX24_AUTH_SERVER_URL` критичен для token refresh; его отсутствие может вывести `Bitrix24Connection` из рабочего состояния и остановить contact/deal/history/Open Lines sync
- `YANDEX_GEOCODER_API_KEY` обязателен для расчёта `distance_to_moscow` вне special-case `Москва = 0`
- токены ботов и webhook-секреты хранятся в `Channel.credentials`, а не в `.env`

## Принципы разработки

1. Маленькие, изолированные, проверяемые шаги.
2. Расширять существующие пути, прежде чем добавлять новые абстракции.
3. Read-only улучшения предпочтительнее тяжёлых рефакторингов.
4. Использовать существующие Filament Resource / ViewAction modal.
5. Для рабочего chat workflow приоритет у уже существующей dialog page, а не у расширения contact modal.
6. Новая таблица или сущность — только после обоснования, почему текущие модели недостаточны.
7. Формулировать через желаемое поведение и целевое действие.
